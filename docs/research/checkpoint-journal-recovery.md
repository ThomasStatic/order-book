# How event-sourced matching engines do checkpoint-plus-journal recovery

Research for [issue #22](https://github.com/ThomasStatic/order-book/issues/22) on the wayfinder map, [#37](https://github.com/ThomasStatic/order-book/issues/37). Read 2026-10-28.

This survey records what Martin Fowler's LMAX and Event Sourcing articles, the LMAX engineers' talks and blog, Aeron Cluster and Aeron Archive (wiki, aeron.io docs, and the source on `master`), and two event-sourcing framework references (Axon Framework, Kurrent/EventStoreDB) say about snapshots, journals, durability, recovery, and determinism. It records facts and recommends no design. Citations are reference links (for example [aeron-readme]), resolved in [Sources](#sources) at the end. "Not stated" means the pages read say nothing about it; nothing has been filled in from memory.

## Facts the decisions wait on

- **Append before processing is the rule in the engines; after is the rule in the one framework example.** LMAX journals and replicates every input event before the Business Logic Processor sees it [fowler-lmax] [lmax-journalling]; Aeron Cluster appends ingress to a Raft log and lets services consume it only up to the quorum commit position [aeron-readme] [aeron-component]. Fowler's Event Sourcing example logs the event after `e.Process()` [fowler-es]. Nobody read here fsyncs per command by default: LMAX wrote to the page cache [lmax-journalling], and Aeron Archive's `fileSyncLevel` defaults to 0 (page cache, background writeback), with 1 and 2 for data and data-plus-metadata syncs [aeron-archive-readme] [aeron-cm]. "Group commit" is not named anywhere read; the closest is Thompson's "if you're going to go to disk, you want to fill that disk block" [thompson-2020].
- **A snapshot is tied to the journal by a position recorded next to it.** Aeron writes the log position and leadership term into the snapshot's BEGIN and END markers and into a `recording.log` entry per service plus one for the consensus module [aeron-snapshot-taker] [aeron-recording-log]. Axon stores a snapshot as an event with the aggregate's sequence number, replacing the stream up to and including it [axon-eventstore]. Kurrent's post stores the snapshotted stream revision in the snapshot's metadata [kurrent-snapshots]. Fowler and the LMAX material say only "snapshot plus the journal since" [fowler-lmax] [fowler-mi].
- **A consistent snapshot while processing continues is handled three ways.** Aeron does not continue: the snapshot is a `SNAPSHOT` action in the log itself, the leader stops polling ingress, and each service stops polling the log while it writes [aeron-cm-agent] [aeron-cs-agent]. LMAX snapshots nightly in quiet periods and relies on replicas for zero-downtime restarts [fowler-lmax]. Axon and Kurrent build the snapshot from the event stream on another thread or a background subscription, so it is a point in the stream, not a copy of a live object [axon-5] [kurrent-snapshots].
- **Validation on recovery is version and structure, not checksums of state.** Aeron checks an `appVersion` (default: SemanticVersion major) read from the snapshot and from each leadership-term event, requires BEGIN and END markers, requires a snapshot entry for the consensus module and every service at the same term and position, and can invalidate the latest snapshot to fall back [aeron-cs-agent] [aeron-recording-log] [aeron-cluster-tool]. Axon filters snapshots by `@Revision` [axon-5]. Kurrent says delete and regenerate [kurrent-snapshots]. Fowler and LMAX: not stated.
- **Determinism rules converge: no system clock, time arrives as data.** LMAX's single-threaded in-memory processor does no I/O [fowler-lmax]; Thompson: "You can't read the system clock" [thompson-2020]; Aeron supplies every timestamp from the log, trusts only the leader's clock, appends timer expiries to the log, forbids direct I/O except via a cluster client, and wants randomness seeded from state or a message and collections iterated in a known order [aeron-tutorial] [aeron-timers] [aeron-ebl] [aeron-cs].
- **Truncating the journal after a snapshot is manual or framework-specific.** Aeron's `ClusterTool` has no purge command; the Archive offers truncate (after a position, stopped recording) and purge (whole segments before a segment boundary) [aeron-cluster-tool] [aeron-archive-wiki] [aeron-purge]. Aeron's own log truncation happens only in an election when a follower's log diverges [aeron-election] [aeron-cm-agent]. Axon: event stores "may choose to ignore or delete snapshots", and events covered by a snapshot can be archived [axon-eventstore] [axon-5]. Kurrent: keep one snapshot with `$maxCount` [kurrent-snapshots].

## 1. When a command counts as durable

**LMAX.** The input disruptor's journaler, replicator, and unmarshaler "all need to be done before the Business Logic Processor works on a message"; "Event Sourcing relies on keeping a durable journal of all the input events", streamed onto the disk, one journal per node [fowler-lmax]. Output events are not journaled: the logic is deterministic and fast, so "there's no gain from storing the results" (footnote 12) [fowler-lmax]. Mark Price (2015): the core services "journal every inbound message to disk before they are processed by business-logic", "giving us recoverability in the event of a crash" [lmax-journalling]. Thompson (2020): "Most people will take a log of the inputs, deal with that and replicate it"; the append position tracks "what have we appended to disk"; the commit index is what the cluster has agreed by consensus, and "We cannot let the service go beyond the commit index"; quorum is "the number of items in the cluster divided by two plus one" [thompson-2020].

**Aeron Cluster.** "Aeron Archive records the log to durable storage" and "Services consume the log once a majority of the cluster members have safely recorded the log to durable storage" [aeron-readme]. The leader records its log publication locally; followers set up a remote recording of the leader's log channel; `appendPosition` is the Archive recording position; followers send it as `AppendPosition`; the leader publishes `CommitPosition` on quorum; the service container's `BoundedLogAdapter` reads a spy of the log and "is bounded because the log may contain entries not yet agreed by consensus" [aeron-component]. In the source, the service agent polls `logAdapter.poll(commitPosition.get())` [aeron-cs-agent]; followers consume up to the lesser of the notified commit position and their own recorded append position; the leader's quorum position is bounded by its own append position [aeron-cm-agent]. The order is therefore: append to the leader's log, record locally and remotely, quorum ack, commit, then process.

**fsync.** Aeron Archive: `aeron.archive.file.sync.level` 0 "for normal writes to the OS page cache for background writing to disk", 1 "for forcing the dirty data pages to disk", 2 "for forcing the dirty data pages and file metadata to disk"; when above zero, set the catalog's sync level to the same value [aeron-archive-readme] [aeron-archive-wiki]. `ConsensusModule.Context.fileSyncLevel` has the same three levels, default "normal writes" [aeron-cm]. `RecordingLog.force` is documented as `FileChannel.force(true)` but the code forces only when `fileSyncLevel > 0` and includes metadata only when `> 1` [aeron-recording-log]. LMAX: the 2015 post benchmarked preallocation on ext3, ext4 (`noatime,barrier=0`) and xfs (`noatime`), both on a battery-backed RAID cache; ext4's `jbd2` lock caused stalls of hundreds of milliseconds; xfs is "a safer option than ext4 from a data-integrity point of view" but its file read-write lock blocks mixed readers and writers [lmax-journalling]. The post does not discuss fsync or group commit.

**Fowler.** The Event Sourcing example's `EventProcessor.Process` calls `e.Process()` and then `log.Add(e)`; the trade-off is not discussed [fowler-es]. Memory Image: events are "the primary persistence mechanism" and you must "ensure you can reliably store the events and process them"; the order relative to processing is not stated [fowler-mi].

## 2. What is in a snapshot and how it is versioned

**LMAX.** "They take a snapshot every night during periods of low activity"; LMAX "can make snapshots of the Business Logic Processor state and restore from the snapshots" [fowler-lmax]. Contents and versioning are not stated.

**Aeron Cluster.** A service snapshot is an Archive recording on the snapshot channel. `ServiceSnapshotTaker` writes a BEGIN marker, one `ClientSession` record per session (cluster session id, response stream id, response channel, encoded principal), then calls `service.onTakeSnapshot(publication)` for the application's state, then an END marker [aeron-cs-agent] [aeron-service-snapshot-taker]. Each marker holds `typeId` ("type to identify snapshot within a cluster"), `logPosition`, `leadershipTermId`, `index` ("so the snapshot can be sectioned"), `mark` (BEGIN or END), `timeUnit` "of the cluster timestamps stored in the snapshot", and `appVersion` from the container context [aeron-snapshot-taker]. The consensus module's own snapshot holds its state, sessions, timers, and pending service message trackers between the same markers [aeron-cm-agent]. Active timers "are included automatically in snapshots, and they cannot be excluded", so a service must handle a timer event for an object it did not restore [aeron-timers]. `appVersion` is a "User assigned application version which appended to the log as the appVersion in new leadership events"; the default `appVersionValidator` "uses SemanticVersion major version for checking compatibility" [aeron-cm]. The `ClusteredService` javadoc says the service "should take a snapshot and store its state to the provided archive ExclusivePublication", idling on back-pressure; real applications "must handle consistent writes and state that spans multiple messages" [aeron-cs] [aeron-tutorial].

**Fowler.** "An application state is purely derivable from the event log, you can cache it anywhere you like"; "Application states can be stored either in memory or on disk" [fowler-es]. Memory Image: "it's best to serialize with generic data structures such as maps and lists" rather than event classes, keep events decoupled from the model, and if needed migrate the event log from an old format to a new one [fowler-mi].

**Axon.** A snapshot "summarises an arbitrary amount of events into a single one"; an `AggregateSnapshot` "contains the actual aggregate instance within it"; keep only state needed for decisions [axon-5]. `@Revision` on an aggregate "automatically results in a RevisionSnapshotFilter", and "Any SnapshotFilter present will impact the snapshot events given to your upcasters!" [axon-5].

**Kurrent.** A snapshot is "a way of storing the current state of an aggregate at a particular point in time"; schema changes make old snapshots obsolete; no explicit version field is described [kurrent-snapshots].

## 3. How a snapshot and the journal position are tied together

**Aeron Cluster.** `recording.log` is "A log of recordings which make up the history of a Raft log across leadership terms. Entries are in order." Each entry holds recording id, leadership term id, term base log position, log position "when entry was created or committed", timestamp, service id (for a snapshot), entry type (TERM, SNAPSHOT, STANDBY_SNAPSHOT, with an invalid flag bit), and an archive endpoint [aeron-recording-log]. The latest state is "the latest snapshot plus any leadership log appended after it", and "a snapshot can be taken mid-term" [aeron-recording-log]. After `ClusterTool snapshot`, the tutorial shows a snapshot entry (`serviceId=0`, `type=1`) and a term entry (`serviceId=-1`) at the same `logPosition` (1376 in its example), the term entry marking "the point within the log the service should start recovering from" [aeron-tutorial]. In the source, `takeSnapshot` appends one entry per service (reverse order) and one with `SERVICE_ID` (`Aeron.NULL_VALUE`) for the consensus module, forces the file, rebuilds the recovery plan, and increments the snapshot counter [aeron-cm-agent] [aeron-cm]. `appendSnapshot` requires "Snapshots must be for the current term"; `appendTerm` requires ascending terms [aeron-recording-log].

**Axon.** `storeSnapshot` "replaces the segment of the event stream identified by the snapshot's Aggregate Identifier up to (and including) the event with the snapshot's sequence number" [axon-eventstore].

**Kurrent.** Store the stream revision of the last included event (the post's `snapshottedStreamRevision`) in the snapshot's metadata, in a separate stream [kurrent-snapshots].

**Fowler, LMAX.** Only that recovery is the snapshot plus the journal since; the mechanism is not stated [fowler-lmax] [fowler-mi].

## 4. How a consistent snapshot is taken while processing continues

**Aeron Cluster.** The snapshot is itself a log message. On the leader, the `SNAPSHOT` toggle (a counter that moves from NEUTRAL to the requested state, applicable only to the leader) is checked during slow-tick work in the ACTIVE state; `appendAction` appends `ClusterAction.SNAPSHOT` to the log, the consensus module enters `State.SNAPSHOT` ("In the process of taking a snapshot"), and followers enter the same state when they replay the action [aeron-control] [aeron-cm] [aeron-cm-agent]. In SNAPSHOT the leader's `consensusWork` does not poll ingress [aeron-cm-agent]. Each service agent sees the action at its log position, sets `logPosition` and `clusterTime` from it, starts a recording, writes markers and state, waits for the recording to reach the publication position, then acks the consensus module with the recording id; during this the agent idles and does not call `logAdapter.poll`, so log consumption resumes only after the snapshot returns [aeron-cs-agent]. The consensus module takes its own snapshot only when every service has acknowledged with a non-null id, then returns to ACTIVE with reason "snapshot complete" and resets the toggle [aeron-cm-agent]. A failed service snapshot still acks with a null id and rethrows [aeron-cs-agent]. `STANDBY_SNAPSHOT` triggers "a snapshot that will only occur on a cluster standby" [aeron-control]; the consensus module has a standby snapshot delay that "starts after the commit position passes the snapshot's log position" [aeron-cm]. A `totalSnapshotDurationThreshold` increments a counter when exceeded [aeron-cm]. `SHUTDOWN` is "taking a snapshot first then terminating"; `ABORT` terminates "without taking a snapshot" [aeron-control].

**LMAX.** Nightly in low activity; replication lets the nightly restart happen "without downtime"; a full restart "including restarting the JVM, loading a recent snapshot, and replaying a days worth of journals, takes less than a minute" [fowler-lmax]. How the snapshot is taken is not stated.

**Fowler.** "New snapshots can be made at any time in parallel without bringing down the running application" [fowler-es]. Memory Image: frequency and concurrency not stated [fowler-mi].

**Axon.** "By default, snapshots are created in the thread that calls the scheduleSnapshot() method", which is "generally not recommended for production"; "it is recommended to run the snapshotter in a different thread" [axon-5]. `AbstractSnapshotter` "uses a task executor to creates snapshots" and the subclass builds the snapshot from `eventStream`, "The event stream containing the aggregate's past events" [axon-snapshotter]. The only shipped trigger is `EventCountSnapshotTriggerDefinition`, firing when loading needs more events than a threshold [axon-5].

**Kurrent.** Options are after each event, every N events, on a specific event, or on a schedule; the post recommends a background process subscribed to `$all` with server-side filtering that stores a checkpoint; because subscriptions lag, reading the stream may return events newer than the triggering event [kurrent-snapshots].

## 5. How the log after a snapshot is found, and truncated

**Aeron Cluster.** `createRecoveryPlan` should bring the cluster "back to its latest stable state when its steps are replayed"; the code takes the most recent valid consensus-module snapshot that has a matching snapshot for every service, then the latest valid term's log after it. `validateSnapshotEntries` requires the `serviceCount` entries before the consensus-module entry to be SNAPSHOT entries with the same `leadershipTermId` and `logPosition`. `RecoveryPlan` carries `appendedLogPosition`, `committedLogPosition`, the snapshots, and the appended local log [aeron-recording-log]. On start the service agent reads the recovery counter for log position, cluster time, term id, and its snapshot recording id, replays that recording from the Archive, polls a `ServiceSnapshotLoader` to the END marker, checks version compatibility, and only then calls `service.onStart(cluster, image)` (null image if no snapshot) [aeron-cs-agent] [aeron-cs]. In the election, `LEADER_REPLAY` replays the local log from `logPosition` to `appendPosition` once the quorum has reached it; `FOLLOWER_REPLAY` replays to the lesser of `appendPosition` and the notified commit position [aeron-election]. Replay calls the same `onSessionMessage` callbacks [aeron-tutorial].

Truncation in Aeron is two different things. Raft truncation: `onNewLeadershipTerm` truncates when the local append position is ahead of the next term's base position and the logs diverge; `truncateLogEntry` calls `archive.truncateRecording`, commits the truncated position to `recording.log`, and the election restarts [aeron-election] [aeron-cm-agent]. Storage reclamation: `ClusterTool` has `describe`, `recording-log`, `snapshot`, `suspend`, `resume`, `shutdown`, `abort`, `invalidate-latest-snapshot`, `seed-recording-log-from-snapshot` ("creates a new recording log based on the latest valid snapshot" with positions reset to zero and the original backed up as `recording.log.bak`), and `sort-recording-log`; it has no purge command, and nothing in the consensus module or service agent deletes old recordings or segments [aeron-cluster-tool] [aeron-cm-agent] [aeron-cs-agent]. The Archive API offers truncate ("enables the removal of data after a position", on a stopped recording; truncating to the start position effectively deletes it), purge ("deletion of data by segment, typically at some point before the current segment in use"; "The new start position specified during a purge must be the same as the start of a segment"), detach, and delete; segments are named `<recordingId>-<segment base position>.rec` and are a multiple of `termBufferLength` [aeron-archive-wiki] [aeron-archive-readme] [aeron-purge]. The aeron.io replicated-state-machines page states the principle: once a snapshot is saved, the input commands up to and including it can be truncated [aeron-rsm].

**Axon.** `readEvents(aggregateIdentifier, firstSequenceNumber)` filters out events "with a sequence number smaller than firstSequenceNumber"; "Event Store implementations may choose to ignore or delete snapshots", and snapshots "do not change the events returned by" tracking streams [axon-eventstore]. "Normally, you can archive all events once they are part of a snapshot event", but rebuilding state from before a snapshot needs the earlier events kept [axon-5].

**Kurrent.** Read the last snapshot, then only the events after its revision; a snapshot stream with `$maxCount` = 1 keeps the latest only, so regeneration is "delete the last snapshot event and regenerate it"; keeping snapshots in the same stream can double its size [kurrent-snapshots].

**Fowler, LMAX.** "loading the latest snapshot and replaying any events since that snapshot" [fowler-mi]; "replaying a days worth of journals" [fowler-lmax]. Truncation: not stated.

## 6. How recovery validates the result

**Aeron Cluster.** When loading a snapshot the service agent compares its `appVersion` with the one read from the snapshot and throws `ClusterException` if incompatible; on each new leadership term event it compares against the version in the log and terminates if incompatible [aeron-cs-agent]. The recovery plan accepts only valid, complete snapshot sets (one per service and one for the consensus module at one term and position) [aeron-recording-log]. `invalidate-latest-snapshot` "marks the latest snapshot as a invalid so the previous is loaded", or the log alone if there is none [aeron-cluster-tool] [aeron-recording-log]. The Archive stores checksums in segment files, which `ArchiveTool checksum` can rewrite [aeron-archive-wiki]. Snapshot bytes reach `recording.log` only after the recording position has caught up with the publication position, and a service failure acks a null id so no entry is written [aeron-cs-agent] [aeron-cm-agent]. No content check of the restored state beyond the markers and version is described.

**LMAX.** Not stated. Fowler notes three processors "All three process input events" and "all but one processor has its output ignored" [fowler-lmax], but no comparison between them is described.

**Axon.** A `SnapshotFilter` screens out unwanted snapshots while loading; `@Revision` gives a revision-based filter; deleting all outdated snapshots is the alternative [axon-5].

**Kurrent.** The system must still work without snapshots, since a missing snapshot only means reading the full stream; snapshot storage adds partial-failure modes across two writes [kurrent-snapshots].

## 7. What each design says about determinism

**LMAX.** The Business Logic Processor takes input "sequentially (in the form of a method invocation)", "operates entirely in-memory, there is no database or other persistent store", and "the central idea of Business Logic Processor is that it avoids doing any IO"; it runs on a single thread; calls to external services are split into an output event and a later input event; "The leader node provides a deterministic sequence for the rest of the processing"; footnote 12 calls the logic "deterministic" [fowler-lmax]. Clocks are not discussed there. Thompson (2020): "Every state machine must get the same ordered set of inputs to come to the same result"; "We need to make sure all our state changes are deterministic"; Java `HashMap` iteration is his example of a non-deterministic structure; "You can't read the system clock", events are timestamped on arrival, and timers are driven by timestamps pulsed into the log [thompson-2020].

**Aeron Cluster.** "Cluster services deterministically process the log and respond to cluster clients" [aeron-readme]. The tutorial's pitfalls are timestamps, random numbers, reading configuration files, and iterating `HashMap`-style collections: "Cluster also provides a reliable timestamp as a parameter to this method", "Use this value as the timestamp within your application state, so it will be consistent under replay"; "Random numbers are best avoided or use a seed fixed in the initial state or via a message"; "Configuration changes should be pushed into the application logic via messages"; use a sorted `TreeMap`, `LinkedHashMap`, or Agrona collections [aeron-tutorial]. "whatever business logic you write MUST be deterministic" and "Aeron Cluster business logic should never interact directly with any I/O unless via a cluster client" (logging, metrics, observability excepted) [aeron-ebl]. Timers: "the timer wheel is polled, but only if the node is the leader"; expiries "are appended to the log as a TimerEvent and are replicated to follower nodes"; "Aeron cluster can only trust one clock - the current leader's clock"; "it is unsafe to access resources such as an external clock from within a clustered service container"; a timer fires "no-sooner-than the scheduled time" [aeron-timers]. In `ClusteredService`, every callback's timestamp comes from the log (session open and close, message "received", timer "expired", new term); `doBackgroundWork` is for tasks "not related to the deterministic state machine", "must not be used to directly, or indirectly, update the service state", and its `nowNs` "is not Cluster#time()" [aeron-cs]. The agent sets `logPosition` and `clusterTime` from each log message before invoking the service, and `time()` returns that value [aeron-cs-agent]. External writes go through a gateway reading an in-cluster Archive with a high watermark, so "there are no commands that need to flow via the cluster log to replay or recover" [aeron-db].

**Fowler.** "the domain logic should never care about the context of the running of the events"; external systems "don't know the difference between real processing and replays", so gateways are disabled during replay (an `isActive` flag), and a query gateway "remembers the responses to its queries and uses them during replay", with "The log of requests" persisted like events [fowler-es]. Memory Image: the model avoids I/O and remote calls during processing; clocks and randomness are not discussed [fowler-mi].

**Axon, Kurrent.** Not stated in the pages read.
