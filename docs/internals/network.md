# Network library

Library `order_book_network` (namespace `order_book::network`, headers in `include/order_book/network/`, sources in `src/network/`), linking `order_book_runtime`. It is not public API: its contract to the outside is [`../wire-protocol.md`](../wire-protocol.md). Terms are in `GLOSSARY.md`, and the decision in ADR 0012. It holds the pure half and the gateway thread's logic, which runs on any `SocketSet`, so far only the in-memory one, with no real sockets and no thread of its own yet.

- **Shared with the log.** A `Command` frame's body is bytes 4 to 39 of a log record. `replay::packCommandBody` and `replay::unpackCommandBody` in `command_log.hpp` are the one place those fields are read or written, and `RawCommand` is unchecked, because the log and the wire must report the same bad byte differently. Reusing the layout saves no copy at runtime: it saves a second field table. `little_endian.hpp` holds the byte helpers both use.
- **`FrameReader`** (`wire_codec.hpp`). Built for a `FrameSource`, the side whose frames it reads, since the two sides differ: a reader of a client's frames accepts only `Hello` then `Command`s of the exact length, and a reader of the engine's frames skips an unknown type and trailing bytes. `feed` appends to one buffer, first dropping what `next` has taken, and `next` returns a `Frame`, `NeedMore`, or a `FrameError`, which sticks. A length under 12 fails once its 2 bytes are in, with correlation 0, since such a frame has none. Anything else waits for the whole 12-byte header, so a chunk boundary can't change an error or its correlation, then is judged at once, so nobody waits for a body that would be refused. The checks run in the order type and `Hello` order, then flags, then exact length, then the body: magic, version, the reserved bytes, and for a `Command` the command byte and its unused fields. A `Frame`'s `body` is a view, good until the next `feed` or `next`.
- **Encoders and decoders.** `encodeEvent` and the rest never allocate or throw, and return 0 if the frame doesn't fit, writing nothing. `decodeEvent` returns nothing for a frame this release can't read, rather than a wrong event: a reason code it doesn't know, or a side or symbol that isn't one. It exists for the client and the tests, and it checks the frame is an event first, since other frames' bodies are too short for a symbol.
- **Values.** `FrameType`, `ProtocolError`, and `RefusedCode` carry the document's numbers, and `reasonCode` and `reasonFromCode` map `RejectionReason` through a switch, never its enumerator values. `wire_codec_tests` pins all of them.
- **`checkEntry`** (`entry_check.hpp`). Pure, in the gateway thread, after `FrameReader` has passed the frame's shape. Each byte maps to its enumerator or to `unknownValue`, past every enumerator, so the check itself is the book's own `malformedReason` and can't disagree with it. An `EntryAccepted` carries the `BookLocation` and a decoded `Command`, an `EntryRefused` a code, and an `EntryMalformed` the event to send. `encodeLogRecord` requires what `checkEntry` passes, which `entry_check_tests` proves on random bodies.
- **`SocketSet`** (`socket_set.hpp`). A plain virtual interface, since each call wraps a system call of 2 µs or more and no per-frame work crosses it. Nothing but `wait` blocks. A `read` reports `ENDED` for a half-close only after everything sent has been taken, and `write` returns nothing for a connection that is gone, which is how a connection nobody is reading is found to be dead. Once `closeListener` has run, `accept` finds nothing, so the gateway needs no check of its own. `InMemorySocketSet` (`in_memory_socket_set.hpp`) has no sockets: a test plays the clients, limits how many bytes one read or write moves, counts every call, and runs its own check inside `wait`, which then returns at once. It is for one thread.
- **`GatewayThread`** (`gateway_thread.hpp`). What a gateway thread does, as a plain object the way `Shard` is, so one thread can step it. `pass` sleeps if `mayWait`, accepts, drains every response ring into per-connection `unsent` buffers, retries parked connections, reads, rings the doorbells of shards it pushed to, then makes one `write` per connection with bytes to send, with no timer. So answers from one drain share a write and batches grow only under load. Within a pass, responses drain before reads so a full response ring empties even when every connection is parked, which is why a waiting matching thread can't deadlock.
  - **Reading.** At most `framesPerPass` (64, the matching thread's batch) frames per connection and one `read`, so a streaming client can't use up another's turn. Frames can sit in a `FrameReader` past the budget, so `framesWaiting` keeps the thread from sleeping on them. `Hello` needs no special state here, since `FrameReader` already refuses a command before it and a second one, and commands may follow it in the same read. What the entry check answers itself goes straight to `unsent`, so it can overtake what is queued, as the wire protocol says.
  - **Parking.** `queue` only ever uses `tryPush`. On a full ring the connection holds its element and stops being read, so TCP carries the backpressure and nothing is refused or dropped, and a connection parked on one shard holds its commands for the others too, since its stream is ordered. `parkedOldestFirst` retries in age order, `shardBlocked` stops a younger one taking room in a pass where an older one on that shard failed, which only a concurrent matching thread can reach, and `parkedOnShard` makes a command read now park behind them rather than slip in.
  - **Sleeping.** `mayWait` means nothing in flight, parked, read and waiting, or unsent, so no response can arrive during a sleep and a matching thread never makes a system call on the way back. `inFlight` counts commands pushed whose last event hasn't come back, whoever sent them, so a dead connection's commands still keep the thread awake.
  - **Connection handles.** A command element's 32-bit connection is the index in the low 16 bits and a generation in the high 16, moved on at close. A response whose handle doesn't match the open connection at that index is discarded, so a reused index hears nothing of the dead. A handle could only collide after 65,536 closes of one index while a response stays in the rings.
  - **A connection going away.** A `FrameError` or half-close clears `reading` and sets `finishing`, and `sendTo` closes the connection once its own `inFlight` reaches 0 and `unsent` is empty, with `shutdownSend` first so the client reads to the end of its stream. A `FrameError` waits in `error` until then, so the commands before it are answered first and the `ProtocolError` is the last thing said. A failed read or write, or passing `hardLimit`, closes at once and discards what is unsent. Those are the only closes that lose answers. A closed connection's queued commands still run, with responses dropped by the handle check, and its parked one is dropped.
  - **Backlog.** Past `highWaterMark` of unsent bytes a connection isn't read, and past `hardLimit` it closes, checked once per pass after the write, so a pass can overshoot by what it drained. Both are `GatewaySettings`, with the spec's 1 MiB and 16 MiB as defaults. Past `connectionsPerThread`, `acceptConnections` still accepts, so the client can hear `TOO_MANY_CONNECTIONS` before being closed.
  - **Stop.** `beginStop` closes the listener, refuses parked commands with `ENGINE_STOPPING`, and owes each shard a marker, retried each pass, since its ring may be full. Commands read from then on go to `checkEntry` as stopping, so unknown symbols and malformed commands get their usual answers and only what would have queued is refused, and backlogged connections stay unread. Once `SHARD_STOPPED` has come from every shard, `beginFlush` stops all reading and starts the grace, read from `settings.clock`, the gateway's only clock. Whatever hasn't flushed when the grace ends is closed anyway. `mayWait` stays false from `beginStop` on, since the shards' answers are on their way with nothing else to wake the thread.
  - **What is missing.** `SocketSet::wait` has no way to ask for writability, so a connection with unsent bytes keeps the thread spinning, and a stop arrives only through a `pass`. Both wait for the real `poll`. So does draining a socket's unread bytes between `shutdownSend` and `close`: over TCP, closing with unread data can reset the connection, and that could cost a client its `ProtocolError`.
- **`gateway_tests`.** The real `GatewayThread`, `MatchingLoop`, and `Shard` on `InMemorySocketSet`, on one thread, with no sleep. A matching thread's `waitInPlace` runs one gateway pass, and a read hook can play a matching thread in the middle of a pass. Its stepper chooses each actor from a seeded source, with rings of capacity 2 and reads and writes split anywhere, through 100 schedules of 1,000 commands, then 100 more with a stop landing mid-stream. One connection owns each instrument, so its answers must equal a single-threaded run's, or after a stop a single-threaded run of just the commands that ran, which must end each connection's stream with those refused or never read, and at each sleep the test counts commands from the bytes the gateway took against the frames the client holds, using nothing the gateway reports. Three lines can be removed with no test noticing, each for a known reason. `mayWait`'s check of `parkedOldestFirst` is implied, since a retry follows every drain and a ring that stays full has commands in flight. `reading` after a `FrameError` changes nothing, since the reader's error is sticky and the socket is never reached. `shardBlocked` needs room to appear between two `tryPush`es, so only real threads can reach it.
- **Tests.** `wire_codec_tests` takes `tests/wire` as its argument. Golden frames come from the standalone `tests/wire/make_golden.py`, marked `-text`, so expected bytes never come from the encoder, and passing on Linux and Windows proves platform identity. It covers every frame's bytes and size, every event's round trip, one case per protocol error, every split point and small chunks of both sides' streams, a byte sweep under the sanitizers, and no allocation per frame on a warm reader. `entry_check_tests` asks a real `OrderBook` about 200,000 seeded bodies, reading the bytes its own way.
