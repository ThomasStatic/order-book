# Network library

Library `order_book_network` (namespace `order_book::network`, headers in `include/order_book/network/`, sources in `src/network/`), linking `order_book_runtime`. It is not public API: its contract to the outside is [`../wire-protocol.md`](../wire-protocol.md). Terms are in `GLOSSARY.md`, and the decisions in ADRs 0012 and 0013. It holds the pure half, the gateway thread's logic, which runs on any `SocketSet`, and the real one over TCP (the tests listen on loopback), with `runGateway` as the thread itself, and the client `order_book_cli send` uses, which `order_book_cli` links it for. It links `ws2_32` on Windows.

- **Shared with the log.** A `Command` frame's body is bytes 4 to 39 of a log record. `replay::packCommandBody` and `replay::unpackCommandBody` in `command_log.hpp` are the one place those fields are read or written, and `RawCommand` is unchecked, because the log and the wire must report the same bad byte differently. Reusing the layout saves no copy at runtime: it saves a second field table. `little_endian.hpp` holds the byte helpers both use.
- **`FrameReader`** (`wire_codec.hpp`). Built for a `FrameSource`, the side whose frames it reads, since the two sides differ: a reader of a client's frames accepts only `Hello` then `Command`s of the exact length, and a reader of the engine's frames skips an unknown type and trailing bytes. `feed` appends to one buffer, first dropping what `next` has taken, and `next` returns a `Frame`, `NeedMore`, or a `FrameError`, which sticks. A length under 12 fails once its 2 bytes are in, with correlation 0, since such a frame has none. Anything else waits for the whole 12-byte header, so a chunk boundary can't change an error or its correlation, then is judged at once, so nobody waits for a body that would be refused. The checks run in the order type and `Hello` order, then flags, then exact length, then the body: magic, version, the reserved bytes, and for a `Command` the command byte and its unused fields. A `Frame`'s `body` is a view, good until the next `feed` or `next`.
- **Encoders and decoders.** `encodeEvent` and the rest never allocate or throw, and return 0 if the frame doesn't fit, writing nothing. `decodeEvent` returns nothing for a frame this release can't read, rather than a wrong event: a reason code it doesn't know, or a side or symbol that isn't one. It exists for the client and the tests, and it checks the frame is an event first, since other frames' bodies are too short for a symbol.
- **Values.** `FrameType`, `ProtocolError`, and `RefusedCode` carry the document's numbers, and `reasonCode` and `reasonFromCode` map `RejectionReason` through a switch, never its enumerator values. `wire_codec_tests` pins all of them.
- **`checkEntry`** (`entry_check.hpp`). Pure, in the gateway thread, after `FrameReader` has passed the frame's shape. Each byte maps to its enumerator or to `unknownValue`, past every enumerator, so the check itself is the book's own `malformedReason` and can't disagree with it. An `EntryAccepted` carries the `BookLocation` and a decoded `Command`, an `EntryRefused` a code, and an `EntryMalformed` the symbol and the event to send. `encodeLogRecord` requires what `checkEntry` passes, which `entry_check_tests` proves on random bodies.
- **`SocketSet`** (`socket_set.hpp`). A plain virtual interface, since each call wraps a system call of 2 µs or more and no per-frame work crosses it. Nothing but `wait` blocks, and only with `SLEEP`: it takes each connection's read and write interest, and `LOOK` sees what is ready without waiting, so a later read or accept costs a system call only where one can succeed. A `read` reports `ENDED` for a half-close only after everything sent has been taken, and `write` returns nothing for a connection that is gone, which is how a connection nobody is reading is found to be dead. Once `closeListener` has run, `accept` finds nothing, so the gateway needs no check of its own; a set with no listener has nothing to close. `wake`, from any thread, ends a sleeping wait now or the next one. `release` gives a connection up without closing it, as a `HandedSocket`, a trivially copyable 64-bit value, and another set's `adopt` takes it on as if just accepted: that is how a connection moves between gateway threads. `InMemorySocketSet` (`in_memory_socket_set.hpp`) has no sockets: a test plays the clients, limits how many bytes one read or write moves, and counts every call. The first set made is the network, with the clients' side and the listener, and a member made from it is another gateway thread's set over the same connections, with no listener. Each connection records which set holds it, and a set using one it doesn't hold, a second hand-off of one connection, or an adopt of one nobody released throws `std::logic_error`, so a connection staying on its thread for life is checked on every call. `STEPPED`, the default, is for one thread: a sleeping wait runs the test's check and returns at once. `THREADED` is for real gateway threads beside a test's clients: every call takes the network's one lock, a sleeping wait blocks on a condition variable until something it watches is ready, a connection waits on the listener, or the set is woken, and `clientReceiveWaiting` blocks for the engine's bytes, so no thread spins.
- **`TcpSocket` and `Poller`** (`tcp.hpp`). The thin wrapper over Winsock and POSIX: a move-only socket, `listenLoopback`, and `connectIpv4`, a blocking connect that `connectLoopback` wraps, a non-blocking `accept` that turns on `TCP_NODELAY` itself since Linux doesn't pass a listener's flags on, and `receive`, `send`, and `shutdownSend` that report rather than throw. Byte order is built by hand, since `htons` can be a macro that trips `-Wconversion`, and `send` uses `MSG_NOSIGNAL` on Linux. Setting a socket up and a failed `poll` throw `std::system_error`, and reading and writing report instead. Nothing native escapes `tcp.cpp`.
- **`PollSocketSet`** (`poll_socket_set.hpp`). The real `SocketSet`: one listener, which its first constructor binds to loopback and listens on at once, and its second binds to any IPv4 address without listening until `startListening`, so no client connects before the engine is ready. A third, given `NoListener`, is a further gateway thread's, which takes connections only by `adopt`. `release` hands out the native socket, open, and frees its slot; `adopt` holds it in a slot of its own, marked readable since the client may already have sent, and the socket keeps its non-blocking mode and `TCP_NODELAY`. A listener takes its address exclusively on Windows and with `SO_REUSEADDR` elsewhere. The set holds the connections it accepts, and runs `poll` or `WSAPoll` over them all, rebuilt each wait. `read` and `accept` make a system call only for a socket the last wait found ready, and `read` assumes a socket is drained when it returns less than it asked for. `wake`, the one thing another thread may call, sends a byte on a loopback pair of the set's own, once until the gateway thread drains it, and the constructor throws `std::runtime_error` if that pair can't connect. Every change to the flag is a sequentially consistent exchange, as a doorbell's is, and the flag clears only after the drain. A wake that finds it already set sent nothing, but whoever woke had already set what it woke for, and in the one order of those operations the thread's next look comes after both, so no wake is lost. That needs the stop flag `runGateway` reads to be stored and loaded sequentially consistent too. After `shutdownSend`, `close` lingers, reading and discarding what the client still sends until it closes too, or 16 MiB or 5 s has gone, since closing with unread bytes resets a TCP connection and can cost the client the frames before it, its `ProtocolError` included. A sleeping wait with lingerers times out when the soonest is due. The linger reads a clock the constructor takes, so it is injected like the stop grace, though no test steps it yet.
- **`runEngine`** (`engine.hpp`). The one way to run an engine, which `apps/order_book_engine.cpp` only wraps. It checks each value (`--gateway-threads 0` is refused), reads and parses the instrument list, binds gateway thread 0's set with `PollSocketSet`'s second constructor so a busy port fails before anything starts, recovery included, and gives every other gateway thread a set with no listener, all sharing one `ConnectionHandOff`. It builds each shard on a matching thread of its own (the books' owner), with a pair of rings for every gateway thread, then starts gateway threads 1 to M-1, each waiting for the one before to be built, then thread 0, which listens, and prints `listening ADDR:PORT` flushed. So no client connects to a start that fails. Each thread first pins itself and sets its priority, from `--pin-matching` by shard number, `--pin-gateway` by gateway thread, and `--thread-priority`, before it builds or listens, so the books are built on their core and a refusal (`cannot pin matching thread 1 to core 5: <reason>`, `cannot pin gateway thread 1 to core 5: <reason>`, or `the gateway thread` when there is one, `--thread-priority high was denied: <reason>`) stops the start with exit 1 before anything listens; a pin list of the wrong length is refused before any thread starts. Each gateway thread reports through a `std::promise` the engine holds, as each shard's is. The destructor first sends the shards the markers of every gateway thread that never started or failed before it was ready, since a gateway thread that is ready waits for every shard to stop, and a shard for a marker on every ring; then it releases the rest to stop, and joins them all. A gateway thread that fails once running sends no markers, so its shards can't stop: the engine records the first such failure and forces the stop, `gateway thread 1 failed: <what>` (or `gateway thread failed:` with one), abandoning every thread. A matching thread holds an `AbortScope` for its shard while it runs. **With `--log-dir`**, which the command line requires and must be an existing directory, and which only an in-process caller can leave empty, each shard also has a log writer thread with a log ring of `--log-ring` records, which places itself from `--pin-log-writers` and `--thread-priority` (`cannot pin log writer 1 to core 5: <reason>`), then waits for its shard's recovery and makes the shard's next log file where the log ended, through the engine's one `Housekeeping`, on a `FileLogStorage` at `--durability` and in files of `--log-file-size`, before it is ready, so a failed recovery or a file that can't be made refuses the start; a size below `leastLogFileBytes` is refused first, `--log-file-size must be at least <n> bytes, the largest shard's header and one record, not <size>`. **Recovery** (`recovery.hpp`, in [`runtime.md`](runtime.md)) runs in the spec's order. On the main thread, once the port is bound and the stop action installed, the engine takes the directory's lock, which it holds for its life, refused as `start refused: <lock file> is locked: another engine or command is using <dir>`, each a path in the system's own separators, then `surveyLog` reads the headers, and the engine deletes what a crash left being made. Each matching thread builds its books, then runs `recoverShard` on its shard's files before anything else and tells its log writer, through a `std::promise`, where the log ended, or why it couldn't, so the writer makes nothing; the matching thread starts before its writer for that reason. The stop report's capacities are what recovery warmed each book to, and growths, a book's or a result's, count from ready, after the replay. Once every shard is ready the main thread prints one line per shard in shard order, `shard 0: recovered books=3 replayed=120 tail-cut-bytes=40`, then starts the gateway threads. A `RecoveryError` becomes `start refused: <cause>` with exit 1, `start refused: placement changed: <cause>` with exit 4, or `recovery stopped: <cause>` with exit 5; a stop request during recovery, which a replaying shard sees within 1,024 records, makes a failed start exit 6 instead, whatever it failed on. Once every shard is ready the unpinned housekeeping thread starts, but makes nothing until `listening` is printed, as the gateway threads wait, so a thread that can't start refuses the start and a start that ends first, whose destructor stops it before releasing it, makes no next file; from then it makes each shard's next file ahead. Every start opens a new file, where its log ended; a file already there, which recovery would have read, is refused as `<path> already exists`. The matching thread watches the durable position, and every gateway thread's `ShardLink` carries it. A start that never became ready, refused or stopped, removes the log files it made, next files included, which hold only headers, so the log is as recovery left it; `engine_start_allocation_tests` checks that after every allocation fails in turn, with no log and recovering one. The lock file stays. The destructor joins the matching threads, then the log writers, first sending a STOP to any whose matching thread never ran its loop, whose ring is then empty, then stops and joins the housekeeping thread, which a writer may wait on until then, and removes each next file no writer took. A first request from its `StopSource` sets the stop flag and wakes every gateway thread's set, and each begins its stop, after which every matching thread stops on the markers of every gateway thread, every gateway thread finishes, and the stop report prints. A second forces the stop: the engine and its threads are abandoned to the process's exit, which `apps/` takes at once with `std::_Exit`. A clean stop joins the gateway threads, the matching threads, then the log writers, each of which has written the rest of its log, cut, flushed, and closed it once its matching thread's STOP came, then the housekeeping thread, and deletes each unused next file, printing any it can't, before the stop report prints. A forced stop abandons the housekeeping thread too, leaving its next files, headers with no records, which the next start's recovery deletes, and the lock, which the process's exit lets go of. A request before ready stops with exit 6. Every failure before ready is a `Refusal`, or a `bad_alloc` or other exception, and becomes `start refused: <cause>` with exit 1; `Engine`'s destructor stops whatever had started, sending stop markers itself while no gateway thread owns the rings. Each matching thread keeps its `std::promise`, since it may still be inside `set_value` when the starting thread's `get` returns. The stop report is `stopped`, a `book` line per book sorted by symbol (the capacity it was warmed to, from the list and the defaults or by recovery, and its growths since ready), a `shard N: result-growths=` line per shard, with `log-end=` first when it has a log, the position after its last record, and a `total:` line, with the fields that exist so far. `EngineExit` names every exit status the spec gives except 2, which is `apps/`'s, and 3, which only an abort gives.
- **Roll forward in the engine** (`engine.cpp`; spec #58's D4b, [`runtime.md`](runtime.md)). With a log, recovery's start also lists the checkpoints in the directory, and each shard's new instruments are those named in no log header with none; its log writer publishes an empty-book checkpoint for each at the recovered end, after the tail is cut and before it makes its first file through a `ClosedLog`, so a crash between the two leaves the symbol still new, and a failure refuses the start. Once every shard is ready, `startRollWorkers` makes `--roll-workers` `RollWorker`s (1 by default, at most one per shard; 0 or more than `--shards` is refused, `--roll-workers must be from 1 to the 2 shards, not 3`), worker w rolling shards w, w + W, and so on, then their threads, which wait for `gatewaysReleased` as the housekeeper does, so `engine_start_allocation_tests` fails only start-up's allocations. A failure prints `order_book_engine: <what>` as it happens, under a lock of their own. A clean stop stops their running loop once the log writers are joined, a pass under way finishing first and none starting once `ClosedLog` stops, then makes its last roll on the same threads (below). A forced stop detaches them, and a checkpoint cut short is a `.tmp` the next start removes. A start that never became ready removes the empty checkpoints it published, as it does the log files it made. The stop report's shard lines gain `checkpoint-writes-failed`, `passes-lost`, and `files-behind`, and the total `checkpoint-writes-failed` and `passes-lost`, with a log only. Since D5, `--checkpoint-dir`, refused without `--log-dir` (`--checkpoint-dir needs --log-dir, since there are no checkpoints without a log`) and unless it is an existing directory (`cannot use checkpoint directory <dir>: no such directory`), and refused if `equivalent` itself fails rather than taken for another directory, gives checkpoints a `FileLogStorage` and a lock of their own when it names another directory than the log's (`std::filesystem::equivalent`), and `checkpointStore()` is the one every checkpoint goes through: recovery's survey and restore, the empty checkpoints, the workers, and a refused start's removal. Recovery's start deletes the log's and the checkpoints' leftover `.tmp` files, and `newBooks` comes from `surveyLog`. Each matching thread publishes its shard's recovered end as the durable position before its log writer starts. The workers' `Rolled` callback passes each floor to `Housekeeping::retain`, which `--keep-log` turns off. The recovery line gains `from=`, where the replay began, and `fell-back=`, the books restored from an older checkpoint.
- **The clean stop's comparison in the engine** (`engine.cpp`; spec #58's D6a, [`runtime.md`](runtime.md)). Each matching thread, once its loop returns, runs `captureLiveImages` into its `ShardRuntime::live`: the full `Shard::checkInvariants`, aborting on a violation, then, with a log, every book's image, or none if a buffer could not be allocated. `waitForStop` then joins the gateway and matching threads and the log writers, stops the workers' running loop (`stopRolling`), finishes the housekeeping, which deletes each unused next file, and `finishRolling` fills `atStop` with each shard's log end and live images and sets `finalRoll` to `MADE`, on which each worker's thread, waiting after `run` returns, calls `RollWorker::finish`, counts itself in `rollsFinished`, and ends; the main thread waits on `happenings` for every one, and a second stop meanwhile forces the stop, exit 8, the workers left to the process's exit, as before any other step. `RollWorker::finish` catches what one shard's `finish` throws, so the worker's other shards still roll. `reportUnpublished` prints `formatStoppedBook`'s line for every book not published, in shard and slot order, and the run returns `NOT_PUBLISHED` (exit 7) if there was any, after the stop report, which prints either way. The destructor and a forced stop set `finalRoll` to `SKIPPED`, so a worker never makes a last roll on a start that failed or an engine being abandoned. `engine_tests`' `testACleanStopThatLeavesABookUnpublished` takes AAPL's checkpoint name at the log's end with a directory, so its publish fails at the rename on real files: exit 7, the line, a stop report counting the failed write and the file behind, MSFT published, and a restart recovering AAPL from 0 and publishing it at its stop. `testACleanStopThatFindsADifference`, with no hook into a live book, rewrites the checkpoint the roll starts from once the engine is ready, AAPL's empty book at 0 with a next trade ID of 5, so what the log rebuilds differs from the live book at byte 28: exit 7, #34's line, nothing published at the end, and a `.live` holding the live image. With every book matching, a restart recovers from the clean stop's checkpoints at each log's end and replays nothing, which `testALoggedRun` pins (`from=3`, `from=5`).
- **A placement change at start** (`engine.cpp`; D6b, [`runtime.md`](runtime.md)). `recoverOnThisThread` surveys; when the survey's `PlacementChange` has rewraps or drops, it removes the checkpoints' leftover `.tmp` files first, so a rewrap's own is free, runs `changePlacement` on the checkpoint store, prints `placement changed: <symbol> from shard <a> of <n> at <p> to shard <b> of <m> at <q>` for each rewrap, and surveys again; a refusal is the survey's `PLACEMENT_CHANGED`, exit 4. `engine_tests`' `testAPlacementChange` runs three starts on real files: MSFT on shard 1 of 2, then moved to shard 0, then on shard 2 of 3, which rewraps AAPL in place and MSFT onto a shard with no log, each start printing its lines and holding the orders the runs before rested; `testRecoveryRefusals` removes MSFT's end checkpoint after a clean stop, as a crash before the last roll leaves it, so a changed count and a moved symbol each exit 4 with #34's message.
- **`apps/engine_handlers.cpp`.** The only code touching signals and the abort handler, built into `order_book_engine` and into `engine_signal_tests`. `prepareStopSignals` runs first in `main`: on Linux it blocks SIGINT, SIGTERM, and SIGHUP, which every later thread inherits, so none is ever delivered to a handler, and ignores SIGPIPE. `forwardStopSignals` then turns each into a `StopSource::request`: on Linux a detached thread loops on `sigwait`, and on Windows `SetConsoleCtrlHandler` takes Ctrl-C, Ctrl-Break, close, logoff, and shutdown, first undoing the Ctrl-C a new process group starts with ignored, and for the last three sleeps for ever, since returning would end the process at once; the system still ends it when its timeout passes, which `docs/OPERATIONS.md` warns of. Signals forward whether or not `--stop-on-stdin-close` is given. The `StopSource` is allocated and never destroyed, since the forwarding thread or handler may outlive `main`. `installAbortHandler` sets `std::signal(SIGABRT, ...)` to write `runtime::describeAbort`'s line from a buffer on the aborting thread's stack, so two threads aborting at once can't mix lines, with `write` or `_write`, then restores the default action and raises SIGABRT again, so one sent from outside ends the process as an abort would. On Windows it turns off the crash dialog with `_set_abort_behavior`. `-h` or `--help` anywhere prints the usage on stdout and exits 0, as in `order_book_cli`.
- **`StopSource`** (`stop_source.hpp`). Requests, counted, from any thread, each running the action the engine installed, under a lock, so replacing that action waits for a request running it. `StdinStopSource` reads stdin on a detached thread and requests a stop at its end: that thread can't be cancelled, so it shares only a pointer the destructor clears.
- **`ConnectionHandOff`** (`gateway_thread.hpp`). How M gateway threads share connections (#27). Gateway thread 0 owns the listener, so there is no extra thread, and deals each connection it accepts to the next thread round-robin, itself included, by a counter only it keeps: connection i lands on thread i mod M, which a test can know in advance. Round-robin drifts as connections close, and a connection dealt to a full thread is turned away with `TOO_MANY_CONNECTIONS` though another may have room. A hand-off is one `Ring<HandedSocket>` of 64 slots per other thread, which thread 0 alone writes and that thread alone reads, then a wake of that thread's set. If that ring is full, thread 0 holds the released connection, accepts nothing more until it fits, and stays awake (`mayWait` is false), so the listener's backlog holds the rest; its stop adopts the held one back and closes it, as closing a listener resets what waited, since its markers may let the other thread finish before the ring has room. The wake is `PollSocketSet::wake`, so no hand-off is lost for the same reason no stop is: the ring's push comes before the wake's exchange, and the receiving thread drains its ring only after its wait has drained the wake byte and cleared the flag. A connection stays where it lands for life.
- **`GatewayThread`** (`gateway_thread.hpp`). What a gateway thread does, as a plain object the way `Shard` is, so one thread can step it. Given a `ConnectionHandOff` and its number it is one of several; given none it is the only one. `runGateway` is the real thread: it passes until a stop has run its course, starting one when its flag is set, and yields after a pass that moved nothing. Whoever sets the flag wakes the `SocketSet`. `pass` waits, unless a connection's reader still holds frames, so a lone streaming client pays no system call per 64 frames, though never for more than `mostWaitsSkipped` (16) passes in a row, since `PollSocketSet` reads and accepts only what the last wait found ready, and a client that never runs dry would otherwise leave every other socket and the listener unlooked at. It then drains every response ring into per-connection `unsent` buffers, accepts (thread 0, dealing what isn't its own) or adopts what thread 0 handed it (any other), retries parked connections, reads, rings the doorbells of shards it pushed to, then makes one `write` per connection with bytes to send, with no timer. So answers from one drain share a write and batches grow only under load. Accepting comes after the drain so that a connection thread 0 handed on before its stop markers is seen, at the latest, by the pass that sees the last shard stop: thread 0 pushes it before its markers, the markers reach every shard before its `SHARD_STOPPED`, and so the receiving thread's ring holds it by then. Taken before the drain, a thread with nothing open could finish in that pass and never close it. Only real threads can separate the two points, so no single-thread test sees the order. Once its stop has begun, a thread closes anything handed to it at once. Within a pass, responses drain before reads so a full response ring empties even when every connection is parked, which is why a waiting matching thread can't deadlock.
  - **The hold** (ADR 0013). A shard with a log gives its `ShardLink` its `DurablePosition`. Draining that shard's responses, a `HOLD` marker whose position the durable position hasn't reached stops the drain there, through `drainWhile`, and the thread remembers the position in `heldUntil` and serves its other rings, without blocking; a later pass looks again, reading the atomic only when a marker needs more than it last saw. So nothing behind a marker is released before every command of its take is durable. A held response is still in flight, so `mayWait` stays false and the thread spins, with a yield after a pass that moved nothing, until the log writer catches up, and no system call is needed to release it. A shard with no log has no durable position, and a marker on its ring holds nothing. `SHARD_STOPPED` sits behind the last marker, so a gateway thread hears a shard has stopped only once all that shard's answers on its ring are released.
  - **Reading.** At most `framesPerPass` (64, the matching thread's batch) frames per connection and one `read`, so a streaming client can't use up another's turn. Frames can sit in a `FrameReader` past the budget, so `framesWaiting` keeps the thread from sleeping on them. `Hello` needs no special state here, since `FrameReader` already refuses a command before it and a second one, and commands may follow it in the same read. What the entry check answers itself goes straight to `unsent`, so it can overtake what is queued, as the wire protocol says.
  - **Parking.** `queue` only ever uses `tryPush`. On a full ring the connection holds its element and stops being read, so TCP carries the backpressure and nothing is refused or dropped, and a connection parked on one shard holds its commands for the others too, since its stream is ordered. `parkedOldestFirst` retries in age order, `shardBlocked` stops a younger one taking room in a pass where an older one on that shard failed, which only a concurrent matching thread can reach, and `parkedOnShard` makes a command read now park behind them rather than slip in.
  - **Sleeping.** `mayWait` means no stop has begun and nothing is in flight, parked, or read and waiting, so no response can arrive during a sleep and a matching thread never makes a system call on the way back. Unsent bytes don't count, since the wait watches that socket for room: a backlogged client sleeps the thread rather than spinning it. With `mayWait`, the thread still looks for `spinWindow`, the matching thread's setting, before it sleeps, and after waking it spins again before the next sleep. `inFlight` counts commands pushed whose last event hasn't come back, whoever sent them, so a dead connection's commands still keep the thread awake.
  - **Connection handles.** A command element's 32-bit connection is the index in the low 16 bits and a generation in the high 16, moved on at close. A response whose handle doesn't match the open connection at that index is discarded, so a reused index hears nothing of the dead. A handle could only collide after 65,536 closes of one index while a response stays in the rings.
  - **A connection going away.** A `FrameError` or half-close clears `reading` and sets `finishing`, and `sendTo` closes the connection once its own `inFlight` reaches 0 and `unsent` is empty, with `shutdownSend` first so the client reads to the end of its stream. A `FrameError` waits in `error` until then, so the commands before it are answered first and the `ProtocolError` is the last thing said. A failed read or write, or passing `hardLimit`, closes at once and discards what is unsent. Those are the only closes that lose answers. A closed connection's queued commands still run, with responses dropped by the handle check, and its parked one is dropped.
  - **Backlog.** Past `highWaterMark` of unsent bytes a connection isn't read, and past `hardLimit` it closes, checked once per pass after the write, so a pass can overshoot by what it drained. Both are `GatewaySettings`, with the spec's 1 MiB and 16 MiB as defaults. Past `connectionsPerThread`, `acceptConnections` still accepts, so the client can hear `TOO_MANY_CONNECTIONS` before being closed.
  - **Stop.** `beginStop` closes the listener, refuses parked commands with `ENGINE_STOPPING`, and owes each shard a marker, retried each pass, since its ring may be full. Commands read from then on go to `checkEntry` as stopping, so unknown symbols and malformed commands get their usual answers and only what would have queued is refused, and backlogged connections stay unread. Once `SHARD_STOPPED` has come from every shard, `beginFlush` stops all reading and starts the grace, read from `settings.clock`, the gateway's only clock. Whatever hasn't flushed when the grace ends is closed anyway. `mayWait` stays false from `beginStop` on, since the shards' answers are on their way with nothing else to wake the thread.
  - **A dead parked connection.** A parked connection isn't read, which is what keeps TCP's backpressure, so a client that dies while parked is found only by a failed `write`, when its earlier commands are answered, or by a read once it is unparked. Its parked command is dropped only when that comes first, and otherwise runs with its answer discarded. A reset might be seen sooner through `poll`'s error flags, and isn't yet.
  - **What is missing.** Past a lingering socket's bounds, or if the process exits, an unread byte can still reset a connection. A thread that fills up isn't skipped when connections are dealt.
- **`ClientStream`** (`client_stream.hpp`). The client's side of one connection, bytes in and bytes out, which `order_book_cli send` drives. It writes `Hello` under correlation 0, then each `ClientCommand` under its own, encoding 64 KiB of frames at a time, so a large file isn't held twice. It reads with a `FrameSource::ENGINE` reader, so a type it doesn't know is skipped and a `Welcome` for another version is the reader's `UNSUPPORTED_VERSION`. A command is answered once a frame flagged last comes under its correlation. A `ProtocolError` is the last thing an engine says, so a frame after it, a frame the reader refuses, a second `Welcome`, an answer before `Welcome`, an answer to a correlation that awaits none, an answer under another symbol than its command's, and an event `decodeEvent` can't read (a reason it doesn't know) each break the stream, which stops counting anything. `end` is `LOST` after a break, with no `Welcome`, or with any command unanswered; otherwise `REFUSED` if any `Refused` came, else `ANSWERED`, so a loss wins over a refusal. A `ProtocolError` always goes to the diagnostics, but is a loss only when it comes before every answer, as #34's exit table says: after them all, everything that ran is known. `sections` prints `replay --events --no-statistics`'s bytes: a section per symbol with an answer, sorted by symbol bytes, and lines sorted by correlation with a stable sort, since one connection's answers for one instrument already come in command order and only a refusal or a malformed command's event overtakes. Symbols come from the commands sent, which every frame must echo. A refusal prints `Refused symbol=<symbol> id=<id> code=<name>`, from `refusedCodeName`; `protocolErrorName` names a `ProtocolError`. Diagnostics carry no program name.
- **`exchange`** (`client_stream.hpp`). `send`'s one `poll` loop over a connected socket, made non-blocking: each turn it watches for reading always and for writing while bytes wait, writes what the socket takes, and reads up to 64 KiB.
