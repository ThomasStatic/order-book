# Network library

Library `order_book_network` (namespace `order_book::network`, headers in `include/order_book/network/`, sources in `src/network/`), linking `order_book_runtime`. It is not public API: its contract to the outside is [`../wire-protocol.md`](../wire-protocol.md). Terms are in `GLOSSARY.md`, and the decision in ADR 0012. It holds the pure half, the gateway thread's logic, which runs on any `SocketSet`, and the real one over TCP (the tests listen on loopback), with `runGateway` as the thread itself, and the client `order_book_cli send` uses, which `order_book_cli` links it for. It links `ws2_32` on Windows.

- **Shared with the log.** A `Command` frame's body is bytes 4 to 39 of a log record. `replay::packCommandBody` and `replay::unpackCommandBody` in `command_log.hpp` are the one place those fields are read or written, and `RawCommand` is unchecked, because the log and the wire must report the same bad byte differently. Reusing the layout saves no copy at runtime: it saves a second field table. `little_endian.hpp` holds the byte helpers both use.
- **`FrameReader`** (`wire_codec.hpp`). Built for a `FrameSource`, the side whose frames it reads, since the two sides differ: a reader of a client's frames accepts only `Hello` then `Command`s of the exact length, and a reader of the engine's frames skips an unknown type and trailing bytes. `feed` appends to one buffer, first dropping what `next` has taken, and `next` returns a `Frame`, `NeedMore`, or a `FrameError`, which sticks. A length under 12 fails once its 2 bytes are in, with correlation 0, since such a frame has none. Anything else waits for the whole 12-byte header, so a chunk boundary can't change an error or its correlation, then is judged at once, so nobody waits for a body that would be refused. The checks run in the order type and `Hello` order, then flags, then exact length, then the body: magic, version, the reserved bytes, and for a `Command` the command byte and its unused fields. A `Frame`'s `body` is a view, good until the next `feed` or `next`.
- **Encoders and decoders.** `encodeEvent` and the rest never allocate or throw, and return 0 if the frame doesn't fit, writing nothing. `decodeEvent` returns nothing for a frame this release can't read, rather than a wrong event: a reason code it doesn't know, or a side or symbol that isn't one. It exists for the client and the tests, and it checks the frame is an event first, since other frames' bodies are too short for a symbol.
- **Values.** `FrameType`, `ProtocolError`, and `RefusedCode` carry the document's numbers, and `reasonCode` and `reasonFromCode` map `RejectionReason` through a switch, never its enumerator values. `wire_codec_tests` pins all of them.
- **`checkEntry`** (`entry_check.hpp`). Pure, in the gateway thread, after `FrameReader` has passed the frame's shape. Each byte maps to its enumerator or to `unknownValue`, past every enumerator, so the check itself is the book's own `malformedReason` and can't disagree with it. An `EntryAccepted` carries the `BookLocation` and a decoded `Command`, an `EntryRefused` a code, and an `EntryMalformed` the symbol and the event to send. `encodeLogRecord` requires what `checkEntry` passes, which `entry_check_tests` proves on random bodies.
- **`SocketSet`** (`socket_set.hpp`). A plain virtual interface, since each call wraps a system call of 2 µs or more and no per-frame work crosses it. Nothing but `wait` blocks, and only with `SLEEP`: it takes each connection's read and write interest, and `LOOK` sees what is ready without waiting, so a later read or accept costs a system call only where one can succeed. A `read` reports `ENDED` for a half-close only after everything sent has been taken, and `write` returns nothing for a connection that is gone, which is how a connection nobody is reading is found to be dead. Once `closeListener` has run, `accept` finds nothing, so the gateway needs no check of its own. `InMemorySocketSet` (`in_memory_socket_set.hpp`) has no sockets: a test plays the clients, limits how many bytes one read or write moves, counts every call, and runs its own check inside `wait`, which then returns at once. It is for one thread.
- **`TcpSocket` and `Poller`** (`tcp.hpp`). The thin wrapper over Winsock and POSIX: a move-only socket, `listenLoopback`, and `connectIpv4`, a blocking connect that `connectLoopback` wraps, a non-blocking `accept` that turns on `TCP_NODELAY` itself since Linux doesn't pass a listener's flags on, and `receive`, `send`, and `shutdownSend` that report rather than throw. Byte order is built by hand, since `htons` can be a macro that trips `-Wconversion`, and `send` uses `MSG_NOSIGNAL` on Linux. Setting a socket up and a failed `poll` throw `std::system_error`, and reading and writing report instead. Nothing native escapes `tcp.cpp`.
- **`PollSocketSet`** (`poll_socket_set.hpp`). The real `SocketSet`: one listener, which its first constructor binds to loopback and listens on at once, and its second binds to any IPv4 address without listening until `startListening`, so no client connects before the engine is ready. A listener takes its address exclusively on Windows and with `SO_REUSEADDR` elsewhere. The set holds the connections it accepts, and runs `poll` or `WSAPoll` over them all, rebuilt each wait. `read` and `accept` make a system call only for a socket the last wait found ready, and `read` assumes a socket is drained when it returns less than it asked for. `wake`, the one thing another thread may call, sends a byte on a loopback pair of the set's own, once until the gateway thread drains it, and the constructor throws `std::runtime_error` if that pair can't connect. Every change to the flag is a sequentially consistent exchange, as a doorbell's is, and the flag clears only after the drain. A wake that finds it already set sent nothing, but whoever woke had already set what it woke for, and in the one order of those operations the thread's next look comes after both, so no wake is lost. That needs the stop flag `runGateway` reads to be stored and loaded sequentially consistent too. After `shutdownSend`, `close` lingers, reading and discarding what the client still sends until it closes too, or 16 MiB or 5 s has gone, since closing with unread bytes resets a TCP connection and can cost the client the frames before it, its `ProtocolError` included. A sleeping wait with lingerers times out when the soonest is due. The linger reads a clock the constructor takes, so it is injected like the stop grace, though no test steps it yet.
- **`runEngine`** (`engine.hpp`). The one way to run an engine, which `apps/order_book_engine.cpp` only wraps. It checks each value, reads and parses the instrument list, binds with `PollSocketSet`'s second constructor so a busy port fails before anything starts, builds each shard on a matching thread of its own (the books' owner), then listens, prints `listening ADDR:PORT` flushed, and starts the gateway thread. A first request from its `StopSource` begins the gateway's stop, after which every matching thread stops on its marker and the stop report prints. A second forces the stop: the engine and its threads are abandoned to the process's exit, which `apps/` takes at once with `std::_Exit`. A request before ready stops with exit 6. Every failure before ready is a `Refusal`, or a `bad_alloc` or other exception, and becomes `start refused: <cause>` with exit 1; `Engine`'s destructor stops whatever had started, sending stop markers itself while no gateway thread owns the rings. Each matching thread keeps its `std::promise`, since it may still be inside `set_value` when the starting thread's `get` returns. The stop report is `stopped`, a `book` line per book sorted by symbol (the capacity it was warmed to, from the list and the defaults, and its growths since ready), a `shard N: result-growths=` line per shard, and a `total:` line, with the fields that exist so far. `EngineExit` names every exit status the spec gives except 2, which is `apps/`'s, and 3, which only an abort gives.
- **`StopSource`** (`stop_source.hpp`). Requests, counted, from any thread, each running the action the engine installed, under a lock, so replacing that action waits for a request running it. `StdinStopSource` reads stdin on a detached thread and requests a stop at its end: that thread can't be cancelled, so it shares only a pointer the destructor clears.
- **`GatewayThread`** (`gateway_thread.hpp`). What a gateway thread does, as a plain object the way `Shard` is, so one thread can step it. `runGateway` is the real thread: it passes until a stop has run its course, starting one when its flag is set, and yields after a pass that moved nothing. Whoever sets the flag wakes the `SocketSet`. `pass` waits, unless a connection's reader still holds frames, so a lone streaming client pays no system call per 64 frames, though never for more than `mostWaitsSkipped` (16) passes in a row, since `PollSocketSet` reads and accepts only what the last wait found ready, and a client that never runs dry would otherwise leave every other socket and the listener unlooked at. It then accepts, drains every response ring into per-connection `unsent` buffers, retries parked connections, reads, rings the doorbells of shards it pushed to, then makes one `write` per connection with bytes to send, with no timer. So answers from one drain share a write and batches grow only under load. Within a pass, responses drain before reads so a full response ring empties even when every connection is parked, which is why a waiting matching thread can't deadlock.
  - **Reading.** At most `framesPerPass` (64, the matching thread's batch) frames per connection and one `read`, so a streaming client can't use up another's turn. Frames can sit in a `FrameReader` past the budget, so `framesWaiting` keeps the thread from sleeping on them. `Hello` needs no special state here, since `FrameReader` already refuses a command before it and a second one, and commands may follow it in the same read. What the entry check answers itself goes straight to `unsent`, so it can overtake what is queued, as the wire protocol says.
  - **Parking.** `queue` only ever uses `tryPush`. On a full ring the connection holds its element and stops being read, so TCP carries the backpressure and nothing is refused or dropped, and a connection parked on one shard holds its commands for the others too, since its stream is ordered. `parkedOldestFirst` retries in age order, `shardBlocked` stops a younger one taking room in a pass where an older one on that shard failed, which only a concurrent matching thread can reach, and `parkedOnShard` makes a command read now park behind them rather than slip in.
  - **Sleeping.** `mayWait` means no stop has begun and nothing is in flight, parked, or read and waiting, so no response can arrive during a sleep and a matching thread never makes a system call on the way back. Unsent bytes don't count, since the wait watches that socket for room: a backlogged client sleeps the thread rather than spinning it. With `mayWait`, the thread still looks for `spinWindow`, the matching thread's setting, before it sleeps, and after waking it spins again before the next sleep. `inFlight` counts commands pushed whose last event hasn't come back, whoever sent them, so a dead connection's commands still keep the thread awake.
  - **Connection handles.** A command element's 32-bit connection is the index in the low 16 bits and a generation in the high 16, moved on at close. A response whose handle doesn't match the open connection at that index is discarded, so a reused index hears nothing of the dead. A handle could only collide after 65,536 closes of one index while a response stays in the rings.
  - **A connection going away.** A `FrameError` or half-close clears `reading` and sets `finishing`, and `sendTo` closes the connection once its own `inFlight` reaches 0 and `unsent` is empty, with `shutdownSend` first so the client reads to the end of its stream. A `FrameError` waits in `error` until then, so the commands before it are answered first and the `ProtocolError` is the last thing said. A failed read or write, or passing `hardLimit`, closes at once and discards what is unsent. Those are the only closes that lose answers. A closed connection's queued commands still run, with responses dropped by the handle check, and its parked one is dropped.
  - **Backlog.** Past `highWaterMark` of unsent bytes a connection isn't read, and past `hardLimit` it closes, checked once per pass after the write, so a pass can overshoot by what it drained. Both are `GatewaySettings`, with the spec's 1 MiB and 16 MiB as defaults. Past `connectionsPerThread`, `acceptConnections` still accepts, so the client can hear `TOO_MANY_CONNECTIONS` before being closed.
  - **Stop.** `beginStop` closes the listener, refuses parked commands with `ENGINE_STOPPING`, and owes each shard a marker, retried each pass, since its ring may be full. Commands read from then on go to `checkEntry` as stopping, so unknown symbols and malformed commands get their usual answers and only what would have queued is refused, and backlogged connections stay unread. Once `SHARD_STOPPED` has come from every shard, `beginFlush` stops all reading and starts the grace, read from `settings.clock`, the gateway's only clock. Whatever hasn't flushed when the grace ends is closed anyway. `mayWait` stays false from `beginStop` on, since the shards' answers are on their way with nothing else to wake the thread.
  - **A dead parked connection.** A parked connection isn't read, which is what keeps TCP's backpressure, so a client that dies while parked is found only by a failed `write`, when its earlier commands are answered, or by a read once it is unparked. Its parked command is dropped only when that comes first, and otherwise runs with its answer discarded. A reset might be seen sooner through `poll`'s error flags, and isn't yet.
  - **What is missing.** One gateway thread: handing connections round-robin to M of them comes with `--gateway-threads`. Past a lingering socket's bounds, or if the process exits, an unread byte can still reset a connection.
- **`ClientStream`** (`client_stream.hpp`). The client's side of one connection, bytes in and bytes out, which `order_book_cli send` drives. It writes `Hello` under correlation 0, then each `ClientCommand` under its own, encoding 64 KiB of frames at a time, so a large file isn't held twice. It reads with a `FrameSource::ENGINE` reader, so a type it doesn't know is skipped and a `Welcome` for another version is the reader's `UNSUPPORTED_VERSION`. A command is answered once a frame flagged last comes under its correlation. A `ProtocolError` is the last thing an engine says, so a frame after it, a frame the reader refuses, a second `Welcome`, an answer before `Welcome`, an answer to a correlation that awaits none, an answer under another symbol than its command's, and an event `decodeEvent` can't read (a reason it doesn't know) each break the stream, which stops counting anything. `end` is `LOST` after a break, with no `Welcome`, or with any command unanswered; otherwise `REFUSED` if any `Refused` came, else `ANSWERED`, so a loss wins over a refusal. A `ProtocolError` always goes to the diagnostics, but is a loss only when it comes before every answer, as #34's exit table says: after them all, everything that ran is known. `sections` prints `replay --events --no-statistics`'s bytes: a section per symbol with an answer, sorted by symbol bytes, and lines sorted by correlation with a stable sort, since one connection's answers for one instrument already come in command order and only a refusal or a malformed command's event overtakes. Symbols come from the commands sent, which every frame must echo. A refusal prints `Refused symbol=<symbol> id=<id> code=<name>`, from `refusedCodeName`; `protocolErrorName` names a `ProtocolError`. Diagnostics carry no program name.
- **`exchange`** (`client_stream.hpp`). `send`'s one `poll` loop over a connected socket, made non-blocking: each turn it watches for reading always and for writing while bytes wait, writes what the socket takes, and reads up to 64 KiB. It half-closes once `allWritten`, stops writing after a failed write and leaves the read to say how the connection ended, and ends at the end of the stream, a failed read, or a break, then calls `ended`. There is no timer and no retry. If `poll` itself fails it throws, and `send` still prints what came. `order_book_cli` connects with `connectIpv4` to an address `runtime::parseListenAddress` reads, the same as `--listen`, and maps `ConnectionEnd` to its exit status.
- **`gateway_tests`.** The real `GatewayThread`, `MatchingLoop`, and `Shard` on `InMemorySocketSet`, on one thread, with no sleep. A matching thread's `waitInPlace` runs one gateway pass, and a read hook can play a matching thread in the middle of a pass. Its stepper chooses each actor from a seeded source, with rings of capacity 2 and reads and writes split anywhere, through 100 schedules of 1,000 commands, then 100 more with a stop landing mid-stream. One connection owns each instrument, so its answers must equal a single-threaded run's, or after a stop a single-threaded run of just the commands that ran, which must end each connection's stream with those refused or never read, and at each sleep the test counts commands from the bytes the gateway took against the frames the client holds, using nothing the gateway reports. Three lines can be removed with no test noticing, each for a known reason. `mayWait`'s check of `parkedOldestFirst` is implied, since a retry follows every drain and a ring that stays full has commands in flight. `reading` after a `FrameError` changes nothing, since the reader's error is sticky and the socket is never reached. `shardBlocked` needs room to appear between two `tryPush`es, so only real threads can reach it.
- **`gateway_socket_tests`.** Real loopback sockets and real threads, so it carries `threaded`: the adapter alone, a wake ending a sleep, two clients at once against a single-threaded run, the 65th connection, a protocol error reaching a client still sending a megabyte after it, and a stop waking a sleeping gateway with an idle connection open. `gateway_frames.hpp` builds the frames both gateway suites send, byte by byte. In-memory, `gateway_tests` checks each sleep against the interest it was given: every connection owed answers watched for writing, and every connection with unread bytes watched at all.
- **`client_stream_tests`** plays the engine with the encoders: the exact bytes written, chunked writes, answers out of line order across instruments, every split point and a byte at a time, refusals in place, `REFUSED`, each way to end `LOST` with its diagnostic, a `ProtocolError` after every answer that isn't one, a loss winning over a refusal, a skipped unknown type, and a file with no commands; every check in `take` and `end` fails a test when removed. **`engine_end_to_end_tests`** runs `send` against a real `order_book_engine`, both children, and compares it byte for byte with `replay <file> --events --no-statistics`, exit status and stderr included: every valid sample (v1 and v2 through `--symbol`, each its own instrument on one engine with 3 shards; each v3 file on an engine of its own), `tests/engine/samples/seven_instruments.csv` at 1 and 3 shards, a malformed file sending its good prefix and exiting 1, `log/every_command.oblog` sent as a log, and then what replay can't stand for: a symbol off the list exiting 4 against the hand-written `off_the_list.stdout`, and no engine exiting 1. Each engine must then stop cleanly when stdin closes. It carries `threaded`.
- **Tests.** `wire_codec_tests` takes `tests/wire` as its argument. Golden frames come from the standalone `tests/wire/make_golden.py`, marked `-text`, so expected bytes never come from the encoder, and passing on Linux and Windows proves platform identity. It covers every frame's bytes and size, every event's round trip, one case per protocol error, every split point and small chunks of both sides' streams, a byte sweep under the sanitizers, and no allocation per frame on a warm reader. `entry_check_tests` asks a real `OrderBook` about 200,000 seeded bodies, reading the bytes its own way.
