# Randomized command tests

- **Randomized command testing** (`tests/randomized/`, library `order_book_randomized`, CLI `randomized_tests`; the model is `tests/reference/`, library `order_book_reference`, namespace `order_book::reference`, re-exported into `order_book::randomized`). This is seeded pseudorandom testing, not fuzzing; don't call it fuzzing. `RandomCommandGenerator` (`std::mt19937_64` raw output with its own unbiased `below`, never `std::*_distribution`) draws submissions and cancellations per a `WorkloadProfile` (`balanced` is the agreed 60/25/15 submit/cancel/replace (`submitPercent`, `replacePercent`, the rest cancels), 80/20 valid/invalid, 50/50 sides, near-touch prices, mostly small sizes; the others are `aggressive`, `passive`, `cancel-heavy`, `queue`, `one-sided`, `invalid-heavy`, `limits`, `immediate` (market/IOC/FOK about 60% of submissions, larger sizes), `self-trade` (95% owned by one of 2 owners, half marketable), and `stop-cascade` (stops half of submissions, one tick from the last trade), and `replace-heavy` (40/15/45)). It reads only `ReferenceBook`, an independent plain model of the book, never the engine, so a stream depends only on seed + profile + `generatorVersion`. `ReferenceBook` is its own library (built when `BUILD_TESTING` or `ORDER_BOOK_BUILD_BENCHMARKS` is on), which never touches an `OrderBook` (it uses only the public value types), so the benchmark workloads use it too: `submit(OrderRequest)` and `submitOrder(fields, markedFilled)` model the two overloads, `cancel(id)`, plus best prices, the resting and removed ID pools, `lastTradePrice()`, and `counters()`. It matches through `plan(side, limit, quantity)`, a non-mutating walk of the opposing queues order by order (never a level's aggregate, so a bug in an engine shortcut shows), then applies the plan; each order keeps its queue iterator, so a cancel is O(1). Each `Command` records its `SubmitOverload` (`REQUEST` by default; `ORDER` for every `MARKED_FILLED` fault and a per-profile `orderOverloadPercent` of valid limits, 10% everywhere; request-path valid limits are IOC at `iocPercent`, 12%, and FOK at `fokPercent`, 8% (one roll), after `marketPercent` (10%, 2% in `passive`) become market orders, IOC at `marketIocPercent` 60% else FOK; valid GTC limit requests are post-only at `postOnlyPercent` (10%, 30% in `passive`); valid requests are `MARKET` (`marketPercent` 10), `STOP` (`stopPercent` 8, IOC/FOK), `STOP_LIMIT` (`stopLimitPercent` 12; IOC 20, FOK 10, else GTC), else LIMIT, one roll; a stop price is 1..`stopNearTicks` (5) on the untriggered side of the model's last trade price (the touch before the first trade), or at/past it at `stopPastTriggerPercent` (5); valid cancels pick a pending stop at `cancelPendingPercent` (30) when stops pend; every valid request draws an owner (`ownerPercent` 50% from `1..ownerPool` 4) and always a mode (`cancelRestingPercent` 50, `cancelIncomingPercent` 25, else `CANCEL_BOTH`); faults include `STOP_GTC`, `POST_ONLY_STOP`, `MISSING_STOP_PRICE`, `STOP_PRICE_ON_LIMIT`, `DUPLICATE_ACTIVE_ID` drawn from resting and pending IDs, `INVALID_STP_MODE`, `POST_ONLY_NOT_GTC_LIMIT`, `MARKET_WITH_PRICE`, `MARKET_GTC`, `UNSUPPORTED_TYPE` (`4 + below(6)`, past every planned enumerator), and `TYPE_CANNOT_REST` (a valid non-`LIMIT` type through the `Order` overload); and the `INVALID_TIME_IN_FORCE` fault draws a value past every planned enumerator), and `applyCommand(model, command)` applies it through the matching overload. `CommandReplayer` runs each command against the book and the model, then checks, in order: an unexpected exception, `checkInvariants` (skipped when `invariantChecksAfterCommands`, since the command's boundary has just run it), `BEHAVIOR_VIOLATION` (properties judged from the engine's own result and book alone, segment by segment through the cascade, so a misreading the model shares still fails: no market, IOC, FOK, or `STOP` order rests, and an unfilled one ends its segment with its `OrderExpired`; a FOK trades all or nothing; a post-only order never takes; no two orders of the same nonzero owner trade, judged from a `RequestLedger` of accepted requests; no stop pends past the last trade price; the model's plan steps can be preventions, it discards an unfilling FOK's plan whole, and it runs whole cascades with three ID pools, resting, pending, and removed), the exact result and events against the model's prediction, and every level and FIFO queue, then the pending stops (`findPendingStop` per model ID, `pendingStopCount`) and `getLastTradePrice`, against the model. `PROPERTY_VIOLATION` stays for caller-supplied checks, and `POOL_VIOLATION` ends a stream: `NodePool::check()` must find every free list sound and its live blocks exactly what the book holds, one per resting order, pending stop, and level, plus what an empty list takes on this platform (`blocksPerEmptyList`, measured rather than assumed), so a leak or a double free fails there. `ReferenceBook` also keeps its peaks (`peakRestingCount`, `peakPendingCount`, and `peakLevelCount`, the most on one side, stops or not), tracked at each insertion so what a cascade holds only inside a command counts, for the benchmarks' capacity. It stops at the first failure; `CommandRecorder` then holds the executed prefix, which is saved and shrunk (`shrinkFailingStream`, ddmin to a 1-minimal stream) to `--out-dir`, and `formatFailureReport` prints seed, config, command index, command, failure, book/model state, preceding commands, and replay lines. With automatic checks on, the engine aborts first; `abort_reporter` then prints seed, command, and a reproduce line, and a Release / `ORDER_BOOK_INVARIANT_CHECKS=OFF` build gives the full report and shrinking. `randomized_harness_tests` pins a fingerprint of each profile's output (now under `generatorVersion` 9): any change to what the generator draws or to a profile must bump `generatorVersion` and re-pin. It also checks, on the model alone, that each profile reaches its own target behavior within 2000 commands (`testProfilesHitTheirTargets`); a new profile needs a target there. Make each random draw in its own statement, never as two arguments of one call or two operands of one operator other than `&&`, `||`, `?:`, or `,`: their evaluation order is unspecified, so the stream would differ between compilers (GCC and MSVC evaluate arguments right to left, Clang left to right). Saved streams (`tests/randomized/regressions/*.txt`, replayed by `randomized_regressions`; still `format 1`, each new field printed only when it differs from its default, e.g. `overload=ORDER`) are the durable regressions; the seed list in `randomized_main.cpp` is valid only for its generator version. `submitOrder`, `cancelOrder`, and `replaceOrder` (`CommandType::REPLACE`; valid replaces pick a resting order and split 30/10/35/15/10 into decrease, instructions only, price change, increase, and post-only at the opposing best; faults are zero ID, price, or total, invalid mode, unknown, removed, a pending stop, and a total at or below what has executed) are generated, not `addOrder`. `ModelOrder` carries its `total`, so executed = total − open. `OrderBookTestAccess` is defined once, in `command_replayer.cpp`; don't define another in a file linked with `order_book_randomized`.

- **The engine harness** (`tests/engine/`, library `order_book_engine_testing`, CLI `engine_randomized_tests`, on `--seed` or `--explore`) runs generated commands through the real `checkEntry` and `Shard`, in one thread. `generateEngineStream` makes the whole stream first, on the models alone, from one unchanged `RandomCommandGenerator` and `ReferenceBook` per instrument, chosen by the interleaver: instrument 0 uses the run's seed, so a one-instrument run is exactly today's stream, and every instrument's IDs start at 1, so a leak between books shows. `convertForEngine` turns each command into what can reach the engine: a valid `Order` becomes its identical GTC limit request, `MARKED_FILLED` and `TYPE_CANNOT_REST` are dropped, and a mode with no owner is cleared, as the wire does. `symbolFaultPercent` adds an unknown or a malformed symbol, which must be refused with no book event. `rawCommandOf` gives the bytes a client would send, faults included. Then `runEngineSeed` checks each command: what entry rejects must be the model's own event, and what it passes runs on the shard, whose events must equal the witness's and the model's, and whose book must equal the model. A **witness** per instrument runs through the by-value overloads at a large capacity, while the shard's book runs through the `out` overloads at capacity 1, so every comparison also shows capacity changes no outcome. A run ends on `Shard::checkInvariants`, both books against the model, `compareBooks` for what the model can't see (the next sequence number and trade ID, and each resting order's own numbers and owner), and `checkBookPool` on both. `plantDivergenceBefore` gives a shard's book an order nobody else knows of, and `cancelPlantedOrder` then removes it, leaving only the numbers it used, which `engine_harness_tests` uses to show both failures are caught. **The log.** Each shard has a log ring of `logRingRecords` (64) and a real `LogWriter` on an `InMemoryLogStorage`, in files of 120 records for the shard with the most symbols, so each spans two pages and a machine crash can tear a record or leave a hole that valid records follow, through one `Housekeeping`, played whenever a writer waits for its next file, and the shard watches its durable position. The harness plays the matching thread: each queued command goes to its shard's log ring before it runs, and a full ring makes the writer write first. **Engine actions** are lines of the stream, `EngineAction` beside the commands: `LOG` makes each shard's log writer do one write, so until then commands are unwritten. A `LOG` line follows a command `logWritePercent` (3) percent of the time, from a seeded source of its own, so the commands, and every pinned fingerprint, are the same with or without them, and the stepper's and real-thread runs' streams set it to 0, since their log writers, if any, are actors of their own. Every run ends by stopping each log writer as a clean stop does, checking each `Shard` with its durable position at the end of its log, then removing the unused next files, reading each shard's files back in order through `CommandLogReader`, each closed with no zero tail and starting where the last ended, the last ending at the log's end, replaying them per instrument through `ReplayEngine`, and requiring a book equal to the witness, through `compareBooks`. `engine_harness_tests` requires many files per shard. **Crashes.** With `crashes` on (the default, which the stepper's and real-thread streams turn off), one or two `CRASH_ENGINE` or `CRASH_MACHINE <seed>` lines follow commands picked from a seeded source of their own, so every other line is the same with or without them, and `durability` (`machine` by default) sets every shard's log. A crash first notes each shard's durable position, how far its responses were released. A machine crash then has every log writer make one more pass after `interruptWrites`, the write the crash meets on its way, in the file it has, so never past a full file's flush. The storage crashes, every `LogWriter`, the `Housekeeping`, every `Shard`, and the lock are dropped, and the start runs as the engine's does: the lock again, `surveyLog`, the temporaries removed, a new `Shard` per shard at the run's tiny capacity, and `recoverShard`. Each shard must have recovered no more than it queued, and, at `machine` or after an engine crash, at least what it had released. The queued commands past what survived are dropped from the harness's own record of each shard's log, the model and witness are rebuilt from nothing by replaying the survivors in log order, and every book must equal both; then each shard gets a new log writer where its log ended and the run goes on, so later commands meet books that lost some, and some now reject. #35 expected a machine crash at `process` to leave holes recovery must stop on, ending the run there; the 1 MiB rule came after it, and every file here is far below 1 MiB, so recovery cuts every hole and any stop fails the run, the stop itself being `recovery_tests`'. The stats count crashes, commands lost to them, and the written bytes each recovery cut. `loseLogFilesAtFirstCrash` has the first crash also lose every file of shard 0's log but its oldest, and meet no write on its way, which `engine_harness_tests` uses to show a lost released command is caught. `engine_randomized_tests` takes `--durability machine|process` and `--crashes on|off`, prints a seed's stats when given `--seed`, and runs each committed seed at both durabilities, one spread each. `leaveUnloggedFrom` runs one command everywhere but the log, which only that replay catches. `engine_randomized_seeds` is 12 seeds at 8 instruments and 5,000 commands, under `uniform` and `skewed`. **Restores.** `restores` (10 by default, 0 in the stepper's and real-thread streams) `RESTORE <symbol>` lines, each after a command and for an instrument picked from a seeded source of their own, so every other line is the same with or without them. A restore requires the shard's book's image to equal its witness's byte for byte (the witness runs at a large capacity, so this also shows capacity changes no image), `OrderBook::restore` to rebuild it, and the rebuilt book's image to equal it, then puts the rebuilt book in the shard through `Shard::replaceBook`, so the run goes on with it and restores compound. A running engine never does this. Carrying on with the restored book is what catches a field the image drops consistently: an encoder and decoder that both lose owners agree on the bytes, and the next prevented self-trade differs from the witness. The stats count restores. **Rolls** (D4b). The run starts as the engine does on an empty directory, publishing every instrument's empty-book checkpoint at 0, and each shard's log writer feeds a `ClosedLog`. `rolls` (20 by default, 0 in the stepper's and real-thread streams) `ROLL` lines, each after a command picked from a seeded source of their own, so every other line is the same with or without them, roll each shard through its `ShardRoller` to the end its writer last closed; the files closed since the last `ROLL` are a lagging worker's backlog, and at 120 records a file a seed rolls about 30. After each, every book's newest checkpoint must verify, with no write failed and no pass lost. A crash drops the rollers with the rest of the dead engine and makes new ones on the crashed store, as a start does. After every crash and at the end, each book's newest checkpoint must stand at or before its shard's log end, and restoring it and replaying the logged commands from its position must give the witness's image byte for byte, which is what recovery from checkpoints does; a roller that restored from its older checkpoint fails seed 1 so. Every book has commands in every file at these sizes, so a quiet book's rewrap is `roll_forward_tests`' to catch. The stats count `roll-passes` and `checkpoints`. **Damage and retention** (D5). Recovery restores from checkpoints, the survey and `recoverShard` as the engine runs them. `damages` (3 by default, 0 in the stepper's and real-thread streams) `DAMAGE <symbol>` lines, each after a command and for an instrument from a seeded source of their own, and one more just before every crash, which the roller has no pass to heal first, flip a byte of that book's newest checkpoint, if it has an older one to fall back to, renamed into place so a machine crash keeps it. A roller meeting it removes it and falls back; a recovery falls back too, so books on one shard stand at different positions, and the stats count `damages` and `fell-back`, which `engine_harness_tests` requires above 0 across three seeds. Unless `keepLog`, each `ROLL` passes each shard's retention floor to `Housekeeping::retain` and runs its pass, so crashes meet a log retention trimmed, and the stats count `files-deleted`. A `ROLL` verifies each checkpoint it published; `checkCheckpoints` takes each book's newest that decodes, by name, as a start does. The end replays each shard's whole log only where it still starts at 0; elsewhere each book's checkpoint and the log after it, already checked, stand for it. **Clean stops** (D6). `cleanStops` (2 by default, 0 in the stepper's and real-thread streams and in `harness_test`'s `smallRun`, whose cases ask for them) `CLEAN_STOP <shards> [<symbol> <shard>]` lines, each after a command and with a shard count from 1 to 4, half of them also pinning one instrument to one of those shards, from a seeded source of their own, so every other line is the same with or without them; a pin can move a symbol under the same count. Added instruments stay `recovery_tests`' and `engine_tests`' to cover, since a stream's instruments are fixed before it runs. A clean stop finishes every log writer and removes the unused next files, captures each shard's live books, and makes each shard's last roll, which must publish every book at its log's end; then the engine's start on that placement: the survey, `changePlacement` and the survey again if it changed, and recovery, which must recover exactly what each shard logged with its start at its log's end, so nothing is replayed, every book equal to its witness under its new location, then checkpoints checked as after a crash. `Logged` carries its stream line, so rebuilding a model and witness after a crash takes the commands in stream order across shards, and `logged` keeps a shard that a smaller count left, its log dead, and grows for a new one, its log starting at 0. After any change of count an instrument's commands span two shards' logs, so the end no longer replays whole logs. A DAMAGE line before a clean stop makes its last roll fall back and make the pass again, which `finish` does at once. Clean stops let retention delete several files in one pass, since the floor can jump to a log's end, and a machine crash can then bring back an older one whose removal hadn't reached the drive while a newer one stays gone: `readShardLog` starts a shard's log again at a file that starts past where the last ended, as recovery, which reads from the books' positions, never reads such a file. And after a crash the promise doesn't cover, `released` falls to what survived, so a later crash is held only to what the restarted engine released. D6b's sweep of seeds at both durabilities, over spreads and starting shard counts, found three failures, which these two fixes and retention's three-newest rule ([`runtime.md`](runtime.md)) remove; 2,100 runs then passed. The stats count `clean-stops`, `placement-changes`, and `rewraps` (and, unprinted, `symbolMoves`, changes that kept the count); `engine_harness_tests` requires, over six seeds with crashes and three clean stops each, that every run passes, more than three changes, some of them a symbol moved under the same count, and more rewraps than changes, and that a drift only the counters show, an order placed and cancelled behind the model's back, fails the run at the clean stop's comparison, naming the book and the byte. Saved streams come later.
- **Connection streams** (`tests/engine/connection_streams.hpp`, in `order_book_engine_testing`). What the stepper and the real-thread runs share: `connectionStreams` turns a stream's lines into each connection's bytes, Hello first, with connection i owning every instrument k where k mod connections is i, instrument k named `SYM<k>` and placed by its hash or, `pinned`, on shard k mod shards; line i goes under correlation i + 1. It also works out, through `checkEntry` and a witness `Shard` per shard, every answer a single-threaded run gives, per instrument, how many frames each connection is owed, and how many commands it sends (`answers`), each answered by one frame flagged last. With `connectionsPerInstrument` above 1, `connections` is ignored and instrument k has that many connections of its own, k times it plus j, a command going to the j of its order ID modulo it, so every command about one order is on one connection, in order there, and two connections' next commands are never the same bytes. The take order then decides each instrument's answers, so `expectedFromLog` replaces the single-threaded answers and frame counts with those of the run's own log: each record goes to the one connection whose next command for that instrument it is, and is replayed on a fresh book, and the answers are listed connection by connection, as `differencesFromSingleThreaded` gathers what was received. A record that is no connection's next command, or a command that passed entry but isn't logged, throws. `differencesFromSingleThreaded` names, per instrument, the first answer that differs, then any difference in what entry answers itself. `plantExtraAnswer` expects instrument 0's first answer twice, which no run gives, for testing the triage.
- **The gateway stepper** (`tests/engine/gateway_stepper.hpp`, `gateway_rig.hpp`, `gateway_frames.hpp`, in `order_book_engine_testing`). One thread plays every actor of the gateway path: clients on `InMemorySocketSet`, every `GatewayThread`, each with its own member set and sharing a `ConnectionHandOff`, and each shard's `MatchingLoop`, choosing the next from a seeded source, on rings of capacity 2, with reads and writes split anywhere. A matching thread waiting in place runs one pass of every gateway thread. `runStepperSchedule` takes a seed and a config and returns any failure as data, and an overload takes the stream's lines instead, which is how a failing schedule shrinks with its seed held fixed. The config's `gatewayThreads`, `connections`, `pinned`, and `streamSeed` (the stream's own seed, where `seed` is then the schedule's alone) shape the run. With `log`, every shard logs at `machine` through the rig's log ring and `LogWriter`, in one file of the default size, which the follower assumes, on rings of capacity 2 like the rest, so takes are 2 commands at most; a log writer is a fourth actor, a matching thread waiting in place runs every log writer too, and without `log` a schedule stays what it was. After every step a `LogFollower` decodes whatever each shard's file has gained, record by record through `decodeLogRecord`, so what counts as logged comes from the storage's bytes and never from the writer: no client may hold an answer to a command whose record isn't there yet (one connection owns each instrument and sends in order, so its k-th command to pass entry is its instrument's k-th record), and the durable position may not pass what the storage holds. Each instrument's log must end holding exactly the commands that ran, in order; after a stop each log writer must have finished, flushing its file, once more than its making did, and closing it, and each `Shard`, durable position included, must be sound. Making the gateway's check always pass, or a marker name one position too few, fails every logged schedule tried. Without a stop, each instrument's answers must equal a single-threaded run; with one, requested at a step the seed picks and begun by each gateway thread at its next pass, as `runGateway` does, every accepted command must run, be refused with `ENGINE_STOPPING`, or never be read, in that order per connection, an unanswered one must lie past the bytes the gateway took, and what ran must equal a single-threaded run of just those. At every sleep the sleeping thread's rings must be empty, every connection it holds with bytes to move watched, and it woken if anything was handed to it. Connection i must end on thread i mod M, unless a stop closed it unread. `gateway_tests` runs 100 schedules each way at one gateway thread and 50 each way at two, and `engine_randomized_tests --stepper run|stop` with `--seed` or `--explore` runs one or many, with `--gateway-threads`, `--connections`, `--placement hashed|pinned`, `--stream-seed`, `--lines I,J,...` (only those lines of the stream, a shrunk reproduction's form), and `--log on|off`, printing a line that reproduces a failure. `engine_stepper_cli` runs one stopped schedule through that CLI, and `engine_stepper_lines_cli` one on chosen lines of another seed's stream.
- **Real threads** (`tests/engine/threaded_run.hpp`, in `order_book_engine_testing`; layer 3 of #35). `runThreadedSchedule` runs real `GatewayThread`s through `runGateway` and real `MatchingLoop`s on threads of their own, each `Shard` built on its thread, on a `THREADED` in-memory network, with 8 instruments pinned to shard k mod N and a connection per instrument, every connection waiting before any thread starts so thread 0 deals them all. Every shard logs, as the engine does: a real `LogWriter` on a thread of its own and one real housekeeping thread, on an `InMemoryLogStorage` at `machine` in files of 25 records for the shard with the most symbols, so a run rolls across many, with a log ring of the config's ring size (the engine's 65,536 at 0), each gateway thread's `ShardLink` carrying the durable position and each matching thread watching it, checking its `Shard` once stopped. After the stop the writers are joined, then housekeeping, which removes the unused next files, and each shard's files are read back through `readShardLog` (the engine harness's own reader, `CommandLogReader` file by file), which must end where the writer did and at the durable position. With one connection per instrument each instrument's log must be its commands in order. With `connectionsPerInstrument` 2, each instrument's two connections land on the two gateway threads at M = 2, and its answers are held to `expectedFromLog`'s replay of the log; such a failure's triage skips the single-threaded rerun and the stepper, which hold a connection per instrument to the single-threaded run, and reports it timing-dependent with the run's log. A matching thread logging a take in another order than it runs it fails these runs, as does replaying each record on a book of its own. The test's thread sends each connection's bytes in seeded chunks, takes what comes back as it goes, then blocks for the rest; then it stops the engine as `runEngine` does, joins every thread, and checks each instrument's answers against the single-threaded run, every connection closed, and connection i on thread i mod M. Every thread runs at the config's spin window, so at 0 a lost wake-up hangs, and the CTest timeout fails it; a thread that throws prints at once, since the others may then wait for ever, and a failure on the clients' side still stops and joins every thread before the run reports it, so it reaches the triage. A failure is never shrunk directly. `triageThreadedFailure` saves it: its reproduction (`engine_randomized_tests --threads run --seed S ...`), N, M, ring sizes, spin window, and the first difference per instrument. Then it reruns the same stream through single-threaded `Shard::process` with `runEngineSeed`, and a failure there is a logic bug, reported unshrunk with the harness's own reproduction, since the engine harness has no shrinker yet. Otherwise it tries 1,000 stepper schedules on the same stream, shape, and placement, at rings of capacity 2; the first that fails is a deterministic reproduction, shrunk with its seed held fixed by removing ever smaller runs of lines while it still fails, to a 1-minimal set unless 2,000 attempts run out, and printed as a `--stepper run ... --stream-seed S --lines ...` command. Otherwise the failure is timing-dependent, reported unshrunk with the run's own log: each shard's records and files, each gateway thread's sleeps, and each connection's answers received, commands sent, and thread. `engine_thread_tests` first shows `expectedFromLog` refuses a log missing a command, holding one nobody sent, or out of a connection's order, then runs the 24 shapes of #35 (N = 1, 2, 4 by M = 1, 2 by rings of 2 or the engine's sizes by spin window 0 or the default) at 5,000 commands, then two connections on each instrument at M = 2 and N = 1, 2, 4, on rings of 2 or the engine's, at spin window 0 and 3,000 commands, then plants each verdict's failure (`ThreadedPlant`) to show the triage reaches it. `engine_randomized_tests --threads run` with `--seed` or `--explore`, `--gateway-threads`, `--ring-slots` (0 for the engine's), `--spin-window-ns`, `--connections-per-instrument`, and `--out-dir`, where a triage report is saved as `threaded-<seed>.txt`, runs one or many; `engine_threads_cli` runs one, and `engine_threads_shared_cli` one with two connections per instrument, and the nightly runs each of the 24 shapes, and the 6 with two connections per instrument, 100 times on fresh seeds, under ThreadSanitizer and on Arm too.
- **The interleaver** (`tests/reference/interleaver.hpp`, in `order_book_reference`, so tests and benchmarks share one) chooses whose command comes next when several instruments run. Each instrument keeps one unchanged generator, so `generatorVersion` stays 9 and no fingerprint moves, and the interleaver has its own seeded source, so one instrument's commands never depend on another's. `Spread::UNIFORM`, `SKEWED` (Zipf with exponent 1, instrument `k` weighing `2^40 / (k + 1)` in whole numbers, so instrument 0 of 32 takes about 25%), and `ONE_HOT` (every command is instrument 0's, a test spread). It follows the generator's rules: raw `std::mt19937_64` output, its own unbiased `below`, no `std::*_distribution`, and no floating point. `interleaver_tests` pins each spread's first draws and fingerprints, worked out apart from this code, and a new spread needs a target check there, as a new profile does.
