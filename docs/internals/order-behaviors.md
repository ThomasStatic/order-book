# Order behaviors

How spec #40's behaviors are built on the engine in [`engine.md`](engine.md). The rules as a caller sees them are in the README's "Order behaviors" section and the ADRs.

## Requests

- **`OrderRequest`** (`order_request.hpp`, spec #40, ADR 0001) — a plain aggregate `{id, side, price, quantity, type = LIMIT, timeInForce = GTC}` that never throws and carries no sequence number, taken by `submitOrder(OrderRequest)`; it is never stored (the book builds an `Order` only for what rests, so `Order` stays v1's). Its checks are `checks::requestReason` in `src/order_checks.hpp` (library-internal): the per-field checks `checks::fieldReason` (`checks::amountReason`'s ID, price, and quantity, which `replaceOrder` uses alone, then side), shared with `Order::malformedReason`, then the type (`isValidOrderType`, "is an enumerator"; `Order` keeps `isSupportedOrderType`, "can rest"), then the time in force (`isValidTimeInForce`, `INVALID_TIME_IN_FORCE`). `validateNewRequest` adds the live-ID check. Both overloads validate, then share the private `matchAndRest(incoming, timeInForce)` (number, match into a `ResultRecorder`, which `matchOrder` asks to `makeRoom(1, 1)` before each `executeOnce`; then an IOC remainder `expire`s and a GTC one rests after `finish()`; `submitOrder(Order)` is GTC), so a v1-shaped request gives `submitOrder(Order)`'s exact result and allocations; `submission_tests` shows the first and `allocation_failure_tests` (Release) counts the second.

## Expiry and IOC

- **Expiry and IOC** (ADR 0002) — a well-formed request is always accepted; what it may not trade or rest expires as a trailing `OrderExpired` for the whole remainder, which still counts as the result's remaining quantity (so for a request, remaining > 0 doesn't mean it rests). An IOC trades while it crosses and expires the rest; a non-crossing one, or one facing an empty side, is accepted and wholly expired; it consumes a sequence number, never rests, and keeps v1's (non-atomic) allocation contract. A FOK (`fillOrKill`) first runs the read-only `fillOrKillTrades` walk (level aggregates within the limit, then the orders taken at the last level, O(levels crossed + orders taken there)): unfillable, it is accepted then wholly expired with no trades and no trade ID (two inline events, so it allocates nothing); fillable, it calls `ResultRecorder::reserve(k, k + 1)` *before* it is numbered, then matches, which can no longer throw, so it is strongly atomic (a throw leaves the book and both counters untouched). Keep that ordering. `order_behavior_tests` covers each behavior's exact outcomes and events.

## Market orders

- **Market orders** — `OrderType::MARKET` (price 0, IOC or FOK; request checks 6 `PRICE_NOT_ALLOWED` and 7b `TIME_IN_FORCE_NOT_ALLOWED`, and check 2 skips a type with `hasNoPrice`). The book runs one as an `Order` limited at the furthest price on its side (`Price` max for a buy, 1 for a sell), so crossing, the FOK walk, and `executeOnce` are unchanged; `matchAndRest` takes the `OrderAccepted` to report separately, at price 0, which the recorder reads as "no limit". It never rests (check 7b), so that internal price is never seen.

## Post-only

- **Post-only** — `OrderRequest::postOnly`, GTC `LIMIT` only (check 9, `POST_ONLY_NOT_ALLOWED`). The private `postOnly(incoming)` decides on price alone with `crossesBestOpposing` (the test `addOrder` uses for `WOULD_CROSS_BOOK`; locked counts, an empty side never takes): would take → accepted then wholly expired (inline, never allocates); else it rests like `addOrder` (number assigned, result built, `restOrder`, then `advanceSequenceNum`), so both paths are strongly atomic and numbered last. The flag isn't stored on the resting `Order`. `addOrder` stays exactly v1.

## Self-trade prevention

- **Self-trade prevention** (`self_trade_prevention.hpp`, `OwnerId` in `types.hpp`, the one alias where 0 is valid: no owner) — request fields `owner = 0` and `selfTradePrevention = CANCEL_RESTING` (check 10: an invalid mode is `INVALID_SELF_TRADE_PREVENTION` whatever the owner). The owner lives in the queue node: `OrderQueue` holds `RestingOrder`s (`order_location.hpp`; an `Order` plus `OwnerId owner`, converting from an `Order` with owner 0 and binding to an `Order&`, so queue readers are unchanged), set by `restOrder(order, owner)` through `PriceLevel::addOrder(order, owner)` (`addOrder` and `submitOrder(Order)` give 0), and changed in place by a priority-kept replace and by `moveToBack`. It began in the index slot's padding and moved by spec #40's P2 rule, since the probe's extra index lookup made `matching-heavy-owned` 5.3% slower than `-request` (`benchmarks/results/2026-10-29-owner-probe/`); the index's `value_type` is again `{ first, second }`. Tests read the owner through `OrderBookTestAccess` (the entry's `second.itr->owner`), since no event, snapshot, or query shows it. `matchOrder(incoming, Instructions, recorder)` probes, only for a nonzero incoming owner, the oldest order at the best opposing level (its node's owner, no lookup; the index is searched only on a match, for the removal) before each `executeOnce`: on a match of owners the incoming mode decides, the `SelfTradePrevented` is recorded first (room made), then `CANCEL_RESTING`/`CANCEL_BOTH` remove the resting order through `removeResting` (the removal `cancelOrder` uses, with its level-handle guard), and `CANCEL_INCOMING`/`CANCEL_BOTH` return true so `matchAndRest` expires the remainder even of a GTC order. No trade ID is consumed. A FOK with an owner walks order by order in `fillOrKillPlan`, reading each node's owner (CANCEL_RESTING skips and counts its own orders; the others stop at the first) and reserves k trades + p preventions + 1 events. `Instructions` (time in force, owner, mode) is what `matchAndRest` and `fillOrKill` take.

## Pending stops

- **Pending stops** (#15) — `OrderType::STOP` (no price; IOC or FOK) and `STOP_LIMIT` (a limit price; any time in force), with `OrderRequest::stopPrice` (checks 8a `INVALID_STOP_PRICE`, 8b `STOP_PRICE_NOT_ALLOWED`; 2, 6, and 7b treat `STOP` like `MARKET` via `hasNoPrice`; 9 keeps post-only LIMIT-only). `submitStop`: past its trigger against `lastTradePrice` (buy stop ≤ last, sell stop ≥ last; never before the first trade) it is accepted then wholly expired (inline, no allocation); else the result (a lone `OrderAccepted` at its limit or 0) is built, `storePendingStop` queues a `PendingStop { request, sequenceNum }` at the back of its `StopLevel` (`buyStops` ascending, `sellStops` descending, so `begin()` is nearest to triggering; queue nodes from the `NodePool`, a size class of their own) and indexes it, rolling back on a throw, and only then is the number consumed. **Deviation from #15**: pending stops are indexed in a second table of the same kind, `pendingIndex` (`OrderIndex` is now `BasicOrderIndex<OrderLocation>`; `PendingStopIndex` is `BasicOrderIndex<StopLocation>`), not by a tag in one table: a tag would need a union of two list-iterator types (unsafe with MSVC's checked iterators) or a spare bit the 32-byte slot lacks. So resting slots are untouched, and `isLive(id)` (the `DUPLICATE_ORDER_ID` check for every command) probes both. `cancelOrder` falls through to the pending index (`removePendingStop`, with a stop-level handle guard; never allocates). `findPendingStop` returns the request as accepted; `pendingStopCount` is the pending index's size; `activeOrderCount`, `snapshot`, and `findActiveOrder` stay resting-only; `reserve` sizes only the resting index. `lastTradePrice` (`getLastTradePrice`) is set in `executeOnce` and by nothing else. New members (`pendingIndex`, `buyStops`, `sellStops`, `lastTradePrice`) are declared after the pool and are in the move assignment.

## Triggering and cascades

- **Triggering and cascades** (#14, ADR 0003) — `executeOnce` sets `lastTradePrice` then calls `triggerStops(price)` (noexcept): while a side's nearest stop is reached (buy stop ≤ price, sell stop ≥ price), every stop at that level is unindexed, stamped with `triggeredAt`, and spliced (same pool allocator, so no allocation) onto `triggeredStops`. That queue is a `std::unique_ptr<StopQueue>` created by the first `storePendingStop`: as a plain member, MSVC's list sentinel (allocated through the pool allocator) would stay in the pool after a move and be freed into a destroyed pool. Each submission builds one `ResultRecorder` (its `OrderAccepted` first), runs the submitted order's lifecycle (`runIncoming`/`runFillOrKill`/`runPostOnly`/`submitStop`, all recording into it, none finishing it), then `runCascade`: per stop, `makeRoom(0, 1)` and `recorder.triggered(...)` before it leaves the queue, then `incomingOrder(stop)` (a `STOP` as a market order) through `runIncoming` with its own `Instructions`, numbered fresh; breadth first. A `TriggeredStopsGuard`, declared after the `InvariantBoundary`, clears the queue as any exception unwinds, so triggered-but-unrun stops are discarded. `ResultRecorder::reserve(trades, events)` is now relative (room for that many more), so a FOK stop mid-cascade reserves correctly. **The narrowed v1 guarantee**: the submitted order's lifecycle (rested or expired) completes before anything in the cascade can throw; the cascade can follow it. `STOP_PENDING_PAST_TRIGGER` is checked last, after `CROSSED_BOOK`.

## Cancel-replace

- **Cancel-replace** (#12, ADR 0004) — `replaceOrder(const ReplaceRequest&)` (`replace_request.hpp`; `ReplaceResult` in `replace_result.hpp`, private constructor, built by `ResultRecorder(OrderReplaced, executedBefore)` + `finishReplace()` or `ReplaceResult::rejected`) has an `InvariantBoundary` (and a `invariant_boundary_replaceOrder` test). Checks, all before mutating: zero ID, price, quantity, invalid mode, pending stop (`ORDER_NOT_REPLACEABLE`), not resting (`ORDER_NOT_FOUND`), total ≤ executed (`REPLACE_QUANTITY_TOO_LOW`). Executed = initial − remaining; open = total − executed. Paths: priority kept (same price, total ≤ current initial): in place through the level handle (aggregate, initial, remaining, the index entry's owner), no number consumed, no allocation; post-only that would take: `removeResting`, expire the open quantity, one number consumed; not crossing: `moveToBack` (try_emplace the new level first, the one possible allocation, then splice the order's own node and fix the order, aggregates, and index entry), numbered last; crossing: `removeResting`, then `runIncoming` as a GTC limit under the new owner and mode, then `runCascade`. `ReplaceResult`'s remaining and fill status are over the order's whole life.
