# Latency harness

Implementation notes. Methodology is in [`../../benchmarks/latency/README.md`](../../benchmarks/latency/README.md), and the claims rule in [`../LATENCY.md`](../LATENCY.md).

- **Layout.** Library `order_book_latency` (`benchmarks/latency/`, linking `order_book_benchmarking` for workloads and `BuildInfo`) and program `order_book_latency_benchmarks`, both built by `ORDER_BOOK_BUILD_BENCHMARKS`. Neither is public API. The program exits 3 in an unoptimized build unless given `--allow-unoptimized`, by the same `BuildInfo::optimized()` as `order_book_benchmarks`.
- **`Histogram`** (`histogram.hpp`). 256 exact buckets, then 128 for each further doubling, `bucketCount` 7,424 in all, so it never overflows and needs no maximum. `bucketOf`, `bucketLow`, and `bucketHigh` are `constexpr`. `record` is inline. `valueAt` returns the upper edge of the bucket at the rank, clamped to the exact `maximum()`, so a percentile never understates. A `Percentile` is parts per 100,000, so `rankOf` stays in integers: 0.999 × 1,000,000 is not 999,000 in floating point.
- **`Clock`** (`clock.hpp`). `now()` branches on one bool; a timed path takes a predicted branch and no virtual call. `measureClock` calibrates over 50 ms and takes the step as the gcd of 100,000 successive differences.
- **Drivers** (`timetable.hpp`). Templates over a clock with `now()` and `spinUntil()`, so tests inject `FakeClock`, which jumps on `spinUntil`. A target is called as `target(index, clock)` and returns `Stamps`, its own opening and closing readings, so getting ready and tidying up stay outside the interval without the driver knowing about results. `backlogGrowing` compares the least lateness of the last two tenths of a run, which a drained burst doesn't disturb, where a mean would flag a stall near the end.
- **`CommandTarget`** (`command_target.hpp`). Builds an `Order` before the opening reading, and keeps its result in a local past the closing one, so destruction is untimed. `checkOutcome` compares with `Workload::expected` by the same `recordFinalBook` and `describeOutcome` as the runner, which `benchmark_runner.hpp` exposes along with `preloadBook`. It counts every submission through `countEvents`, which agrees with the runner's v1 tally since a v1 workload has no expiry, prevention, or stop.
- **`HandOffTarget`** (`handoff_target.hpp`). The hand-off interval, built on `benchmark::QueueRun`, so a latency row and a `queue` run use the same matching thread and rings. It prepares each element before the opening reading, and spins on the response ring until the last event is back, so the interval is the sender's. `checkOutcome` stops the matching thread, and proves the books did what was predicted, and that none grew. Hand-off needs `--matching-core` beside `--pin-core`, which the matching thread applies to itself along with `--priority`: a thread started on a pinned one inherits its core on Linux, so pinning only the sender would put both on one core. The ladder's capacity comes from `HandOffTarget` itself, one command at a time, since a hand-off waits for each answer: `core`'s rate and the `queue` kind's, from batches, are both past what it can carry.
- **`DurableWaitTarget`** (`durable_wait_target.hpp`). The durable-wait interval, built on `benchmark::RunLog` (see [`benchmarks.md`](benchmarks.md)), so a latency row and a durable `queue` run use the same log writer and housekeeping thread. It holds one instrument's `InstrumentDirectory`, the workload's records, and a `LogRing`; `operator()` builds the `LogEntry` before the opening reading, pushes it, rings the writer, and spins until the durable position passes it, so the interval is the sender's and no book runs. Its one thread is the ring's only producer, so `checkOutcome`, and the destructor if that never ran, send the writer its STOP; `checkOutcome` then reads the run's files back through `CommandLogReader` and requires exactly the records sent. `--writer-core` pins the writer, which applies it to itself, along with `--priority`, for the reason hand-off's matching thread does. `latency_harness_tests` shows each call returns only once the durable position covers its record, which a target that skips the wait fails, that the files hold every record at both levels, that every run's directory is deleted, checked or not, and that `none` is refused; that case runs a real writer thread, so the test is `threaded`.
- **`RoundTripTarget`** (`round_trip_target.hpp`). The round-trip interval, against a fresh `benchmark::EngineProcess` each run with one book and one connection, logging at `--durability` (`machine` by default) under `--log-dir`, preloaded over the wire through `LoopbackClients` and then taken from it. Closed-loop, `operator()` sends one frame and spins on the socket until the frame flagged last, keeping each event in a reserved vector to count after the closing reading. `runOpenLoop` keeps its two halves on two threads: this one spins to each scheduled send, and a receiver thread, set up first (`RoundTripSetup::setUpReceiver` pins it) and told the start through an atomic, stamps each read once as it returns and hands every frame to an `ArrivalTally`. `ArrivalTally` (`timetable.hpp`) is that thread's bookkeeping, apart from it so `latency_harness_tests` can drive it: response and first-frame histograms from each command's own scheduled send, a discard before which commands go in no histogram, and `sustained` judged as `runTimetable` judges lateness but on the least response time in each of the final two tenths, since the sender never waits. A failure on either thread stops the other and is rethrown. `checkOutcome` half-closes, reads to the end, stops the engine (which refuses any growth), and compares counters from the frames with the prediction, taking the book's shape from the prediction as the `engine` kind does. The program passes `--matching-core`, `--gateway-core`, and `--priority high` to the engine as `--pin-matching`, `--pin-gateway`, and `--thread-priority high`, and a round trip's capacity, like a hand-off's, comes from the target one command at a time.
- **`RunRecord`** (`latency_report.hpp`). A fixed field list, each starting unfilled, and `set` throws on an unknown name, so a misspelling can't leave the real field missing unnoticed. There is deliberately no default.
- **`ReportRow` and `formatRow`.** A row is one interval, rate, and workload. `unquotableReasons` lists what stops it being quoted, in a fixed order. `noiseMarkFactor` (4) is chosen so the ticket's worked example comes out: at 1M commands/s, 35 to 118 gaps a second over 10 µs mark p99.99 (a tail of 100/s) and not `pending-stops`' p99.9 (1,000/s).
- **`thread_setup`**. `pinCurrentThread` and `raiseCurrentThreadPriority` call the engine's own `runtime::pinThisThread` and `setThisThreadPriority` (see [`runtime.md`](runtime.md)), and throw with the system's reason when refused, so a record never claims a setting that didn't apply.
- **Tests.** `latency_harness_tests` takes `tests/latency` as its argument. Report cases compare with hand-written files in `tests/latency/expected/`, read in text mode so CRLF checkouts compare like LF. No test asserts a latency value: the clock case is sanity only. `latency_cli_smoke` and `latency_cli_smoke_response` run tiny closed-loop and timetable sessions with `--allow-unoptimized`, and `latency_cli_smoke_handoff`, `latency_cli_smoke_round_trip`, `latency_cli_smoke_round_trip_response` (with `--discard-seconds 0`), and `latency_cli_smoke_durable_wait` (closed-loop at `machine`) and `latency_cli_smoke_durable_wait_response` (the ladder at `process`), both on real files under the build directory, are `threaded`, as `latency_harness_tests` now is.
