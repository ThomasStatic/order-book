# The browser build (Emscripten)

How the repo builds and tests under Emscripten, the target that runs the whole engine in a visitor's browser tab (spec #127; decisions in #110, #113, #115–#123 and ADRs 0016–0018). This note grows with each slice of v2.2.0. Domain terms (engine worker, page store, engine client, shadow book) are in `GLOSSARY.md` under "In the browser".

## Toolchain

Emscripten **7.0.0**, exactly, locally and in CI. On this machine emsdk is at `C:/dev/tools/emsdk` and is not on `PATH`; a shell needs:

```bash
export EMSDK=C:/dev/tools/emsdk
export PATH="/c/dev/tools/emsdk/upstream/emscripten:/c/dev/tools/emsdk/node/24.19.0_64bit:/c/dev/tools/emsdk/python/3.13.3_64bit:$PATH"
```

`emcmake` uses Ninja (never a Visual Studio generator), so the build gets a directory of its own:

```bash
emcmake cmake -S . -B build-wasm -G Ninja -DCMAKE_BUILD_TYPE=Release -DORDER_BOOK_WARNINGS_AS_ERRORS=ON
cmake --build build-wasm
ctest --test-dir build-wasm -j8 --output-on-failure
```

The Emscripten toolchain file sets `CMAKE_CROSSCOMPILING_EMULATOR` to emsdk's `node`, which CTest puts in front of every test that names a target.

## The CMake branch

The toolchain is the switch: there is no option or preset of its own. `if(EMSCRIPTEN)` near the top of `CMakeLists.txt` adds `-pthread` (real pthreads, on Web Workers) and `-fwasm-exceptions` (legacy wasm exceptions, never `exnref`, until the browser floor passes Safari 18.4) to every target's compile and link. `ORDER_BOOK_ENABLE_TSAN` or `ORDER_BOOK_BUILD_BENCHMARKS` beside it is a configure error: Emscripten has no ThreadSanitizer, and nothing is measured in wasm.

What builds: every library and `order_book_cli`, and every test executable but the six below. `order_book_engine` doesn't, since nothing can `listen` in a tab, so `apps/engine_handlers.cpp` has no wasm branch. Neither do the benchmarks, the profiling tools, or the latency harness.

At the end of the file, once every target exists, each executable but `order_book_wasm_module` gets the link settings for running under `node` in CTest: `-sNODERAWFS=1` (the host's files, so tests read `tests/` and write their scratch directories directly), `-sEXIT_RUNTIME=1`, `-sSTACK_OVERFLOW_CHECK=2` with the shipped module's stacks (`-sSTACK_SIZE=1MB` for the main thread and `-sDEFAULT_PTHREAD_STACK_SIZE=256KB`, where Emscripten's defaults are 64 KiB each, which ASan's frames outgrew once optimized), `-sALLOW_MEMORY_GROWTH=1` with `-Wno-pthreads-mem-growth` (growth makes every pthread re-check its view of memory, which is acceptable in tests only), and a strict pthread pool: `-sPTHREAD_POOL_SIZE_STRICT=2` with 16 threads. A program that asks for one thread more than its pool holds aborts loudly rather than waiting for a thread that never comes. `order_book_wasm_threads(<target> <n>)` raises one executable's pool. `order_book_cli` gets the same settings, since under Emscripten it runs only in the script tests. Under ASan each also links `tests/wasm_asan_options.js` with `--pre-js`, which sets `Module.ASAN_OPTIONS` to `malloc_context_size=0`: Emscripten's ASan reads its options from `Module`, never the environment, and unwinds a JavaScript stack for every allocation and free it records, which made the suites about 50 times slower (22 minutes at `-j4` here, against under 4 without). A report still names the bad access and where it happened, only not where the memory was allocated or freed; `node_pool_poison_tests` still requires its use-after-poison report.

## Portability, in source

Every wasm-only branch is under `__EMSCRIPTEN__`, and the wasm jobs are their only check.

- `FileLogStorage`'s rename takes the plain-`rename` branch, as on systems without `RENAME_NOREPLACE`: Emscripten's libc has no `renameat2`, so a rename there replaces. The browser's log lives in `PageLogStorage`, whose own checks require the refusal.
- `NativeFile::extend` sets the end of the file instead of calling `fallocate`, which Emscripten's libc lacks.
- `FileLogStorage::lock` takes `flock`, which Emscripten accepts without locking anything, then holds the lock in a process-wide registry by path. A module is one process that shares its files with nothing, so that registry is the whole of "one holder at a time".
- `size_t` is 32 bits on wasm32. The 14 conversions only that target saw (`-Wshorten-64-to-32`) are fixed with types or casts, never a `-Wno-` flag: 10 in the command generator, through `indexBelow`, which draws exactly what `below` does, so every pinned fingerprint and `generatorVersion` 9 are unchanged.
- `pastTheLast` in `thread_placement.cpp` is defined only where a branch uses it.
- **`Doorbell`** sleeps on `emscripten_futex_wait` and wakes with `emscripten_futex_wake`, on its own atomic's word, exactly where native calls `std::atomic::wait` and `notify_one`. libc++'s `std::atomic::wait` polls under Emscripten, waking up to every few milliseconds, so idle matching threads and log writers would never quite sleep. Every change to the atomic is still an exchange, so the lost-wake-up reasoning in `runtime.md` holds unchanged, and `wait` loops on a load until the state isn't asleep, as `std::atomic::wait` does. `matching_loop_tests`' `testARingWakesASleeper`, which hangs without the wake, runs in both wasm jobs.

## `order_book_wasm`

A static library that builds and is tested on every platform (`include/order_book/wasm/`, `src/wasm/`; ADR 0018). It links `order_book_cli_commands`, and through it `order_book_network`, and is not public API. Its parts:

- **`settings.hpp`**, the one place the shipped values live. `browserSettings(list)` gives the engine's settings: two shards (N), one gateway thread (M), one roll worker (R); 64 KiB log files with normal retention; rings of 1,024 commands, 4,096 responses, and 4,096 log records per shard; native book capacity; 3 connections; a slow client warned at 64 KiB and cut off at 1 MiB; `process` durability; no log or checkpoint directory, since the page store is injected. Beside it: `pageSocketBuffer` (64 KiB each way per connection), `creditWindow` (W, 64 KiB), and `browserEngineThreads`, 2N + M + R + housekeeping + `runEngine`'s own thread = 8, which the module's strict pool will be.
- **`ShadowBooks`**: a book per instrument, at the directory's capacities, behind one lock, so any thread may ask. `follow(change)` takes each `PageLogStorage` change, under the store's lock and without calling the store. A file's first write at offset 0 that starts with the log's magic is its header, read through `CommandLogReader`; any other file is dropped. Each later write must be whole 40-byte records at the file's next record, each at its shard's next position. Each is checked against the chain by `decodeLogRecord`, must be for an instrument of that file's shard, and runs through `executeCommand`, as its shard ran it. Anything else is a problem: the first is kept, `problem()` says it, and nothing more is followed. `rebuild(store)` runs `surveyLog`, then a read-only `recoverShard` per shard, as `verify` reads a store, on a `Shard` of its own. It restores each book from that shard's image and marks every log file already there closed, since a start always opens a new one, so a later write to one is a problem too. A store recovery refuses leaves the books empty and a problem saying why, and the start that follows refuses it as well. `records(shard)` is the shard's next log position, and `shardOf` comes from the directory.
- **Book views**: `decodeBookImage` reads a `writeImage` image field by field (`docs/checkpoint-format.md`) into a `BookView`: levels best first with their orders' IDs, sequence numbers, quantities and owners, the pending stops in trigger order with every field as submitted, and the last trade price. It throws `std::invalid_argument` for bytes that aren't an image. `ShadowBooks::book(symbol)` is a snapshot, decoded from its image. Nothing is pushed.
- **ID assignment**: `assignOrderId(symbol)` gives 1 + the larger of the highest ID the shadow has seen and the highest it has given. "Seen" is every add record it ran and, after a rebuild, every ID its book holds, resting or pending. A rebuild keeps what was given. So a rebuilt shadow can give again the ID of an order that filled or was cancelled before a checkpoint, which the book allows: only a live ID is a duplicate. It returns nothing once no ID is left.
- **`PageConnection`** and **`PageSend`**: a client connection over the in-page set, driven without blocking, since the module's strict pthread pool leaves the engine worker no thread to wait on. `pump()`, on each wake, writes what fits, half-closes once everything is written if `finish()` was called, reads what came, and ends the `ClientStream` once the connection ended with nothing left. A connection holds its run's set by `shared_ptr`, and its destructor resets a connection still open and releases the slot. `open` and `PageSend::start` only write: every byte is read by a later `pump`, which a credit window may limit, and `received()` counts them all. When the first pump read too, a Welcome or a whole send could slip past a window uncounted, which the ASan jobs showed: the sandbox let in one answer more than W, and a terminal send ended inside a 100-byte window. `PageSend` is `send` of a prepared file over one, ending in `finishSend`'s result. `startSend(sockets, args)` takes send's own arguments: what `prepareSend` refuses, `cannotConnect`'s text (`Connection refused`) when there is no set, the set takes no connection, or `--connect` names any address but `browserListen`, since nothing else listens in the tab, or the send under way.
- **The terminal** (`Terminal`, behind `run(line)`): `buy`, `sell`, `cancel`, `replace`, `book`, and `status`, the CLI's `send`, `replay`, and `verify`, and `ls`, `cat`, and `help`. A client command becomes the 13 fields of one v3 row, checked by `parseRow` exactly as a replay row is, so a bad one prints the parser's column and message and exits 2. `buy` and `sell` are `SYMBOL QUANTITY [PRICE]` with `stop=`, `tif=`, `post-only`, `owner=`, and `stp=`. A price makes a `LIMIT` order and none a `MARKET` one, and `stop=` makes them `STOP_LIMIT` and `STOP`. The time in force defaults to `GTC` for a priced order and `IOC` otherwise, and an owner with no `stp=` is `CANCEL_RESTING`. A symbol off the instrument list, which is fixed, is refused there for all four commands alike (`<verb>: XYZ is not on the instrument list`, exit 2) and takes no line. The ID comes from `assignOrderId` once the row passes, and prints first as `assigned id=N`. `cancel` and `replace` name theirs. The row goes on the standing connection (`connect` on each start's ready; `disconnect` when the run ends, after which a waiting command is reported lost, exit 3). Its correlation is its line in `collected()`, the session's CSV, whose header is line 1, so the Nth client command is `line N+1:`. That is how the session's commands, collected, are a CSV whose `send` prints the same answers under the same lines. The spec's "correlation N" would need a CSV with no header. `run` returns the result at once, or nothing while the answer is due, which `pump` then gives: the lines `answerLines` prints, exit 4 for a refusal, as `send`'s. A command with no engine running prints `the engine isn't running`, exit 1, as `send` with no connection. Errors are `<verb>: <what>`. `book SYMBOL` restores the shadow's image and prints `formatFinalBook` of it, what `replay --book` prints for a final book. `status` prints `shard K: <symbols> records=N` per shard. The CLI's commands are `order_book_cli_commands` and print its bytes (`verify`'s argument errors are the terminal's own, since it takes no directories), and each may keep the program name, as the page's recorded sessions type it (`order_book_cli replay valid/stops.csv --trades`). Their files are named from the working directory, which is the samples' root: `valid/` and `malformed/`, as in `tests/replay`, which the module embeds read-only (M1). So a path prints as typed, as native's does run from `tests/replay` (`malformed/price_zero.csv:4: ...`). `send` adds `--connect 127.0.0.1:9000` when none is typed, since send requires it, and opens a connection of its own (`PageSend`), which `pump` drives to the end; with no engine running it prints native's `cannot connect` line, exit 1. A send under way when the run ends is abandoned (`PageSend::abandon`), so the next `pump` reports it as `send` reports a connection lost. `replay` runs on fresh books, not the engine's. Neither checks where its file is, as the native CLI doesn't: only `ls` and `cat` keep to the samples. `verify [--validate final|per-command]` is `verifyStores` over the page store, which the engine holds locked while it runs, so it prints `order_book_cli: verify: the page store is locked: the engine is using it`, exit 1, until the engine stops, as native's `... is locked`. It takes no `--log-dir`: the store is the page's. `ls [DIRECTORY]` lists a sample directory's entries, sorted, a directory's with a trailing `/`, and `cat FILE` prints a sample's bytes; each refuses an absolute path or one with `..` as no such sample, exit 1. `help` lists every command, the page's own `start`, `stop`, `crash`, `reset`, and `clear` too, which the engine client runs, and the instruments. Anything else prints `<word>: unknown command; help lists them`, exit 2.
- **Client rows** (`src/wasm/client_rows.hpp`, internal): what the terminal's client commands and the sandbox's typed ones share. The v3 row's columns; `fillDefaults`, which gives an `ADD` its order type from its price and stop price and its time in force from its price, and an owner with no mode `CANCEL_RESTING`; and `check`, which parses the row exactly as a replay row and refuses a symbol off the instrument list.
- **`Sandbox`** (`sandbox.hpp`): the sandbox's standing connection, a `PageConnection` that `connect` opens at each start's ready and `disconnect` ends, reporting each command still waiting as lost.
  - `submit(symbol, OrderInput)`, `cancel`, and `replace` take each field as the text its column takes, so the parser judges a number exactly as a row's (a fraction, a negative, or zero refused with its message, never rounded), and make one v3 row each, defaulted and checked as the terminal's (`client_rows.hpp`), and refuse with the parser's text, a symbol off the list, or `the engine isn't running`. A submit's ID comes from `assignOrderId` once the row passes. A sent command's correlation is its count on the connection, from 1.
  - `pump()` gives each command whose answer is whole: every frame decoded (`ClientStream::Answer`: the `BookEvent` or the refusal, its text, and its frame's bytes), the text `send` prints for it under `line N:` with N its correlation, and the frames' total. Then it forgets the answer, so a standing connection keeps nothing.
  - **The worker's side of the credit window**: `pump` reads from the set only while `room()` is above zero. That is W (`creditWindow`, 64 KiB) less the bytes read (after the Welcome) and not yet `consumed` by the page, whether given in answers or part of an answer under way. A read that took all its room may have stopped inside a frame, so `pump` reads again until a read comes up short or the window is full. The bytes still waiting stay in the set, then in the gateway's unsent bytes and its parking, so a page that stops consuming pushes back into the gateway. When everything given has been consumed and the window is still full, an answer larger than W is under way, and the next pump reads another W of it. That is the one way the page holds more than W, and the window never closes on a partly read answer. `consumed` never takes back more than was given.
- **Seeding**: `src/wasm/instruments.csv` pins AAPL and MSFT to shard 0 and NVDA and TSLA to shard 1. `src/wasm/seed.csv` rests three bids and three asks on each, IDs 1 to 6, so the panels' IDs start at 7. `BrowserEngine::startedEmpty()` says whether a run began on an empty store (a first load, or after a reset). Then the engine worker sends the seed with `startSend` before telling the page the engine is ready, and its answers go out as `seeded`, which the terminal doesn't print. Any other start recovers the seed from the log. The engine's nominal address is `127.0.0.1:9000`, which nothing binds, so `send`'s `--connect` can name it.
- **`BrowserEngine`**: the engine as the engine worker runs it. It holds the instrument list's directory, the `PageLogStorage` (made from the page's files), and the shadows, which follow every change before the injected `stored` callback is told it. So the page never sees an answer whose log write the shadows lack. `run(stop, report, diagnostics)` rebuilds the shadows, makes a new `PageSocketSet` whose wake calls the injected `wake`, and calls `runEngine` with those parts and a `ready` that calls the injected one. A run after a clean stop recovers from the same store.

## `order_book_wasm_module` and `engine-worker.js`

The module is the executable `order_book_wasm_module` (`src/wasm/module/engine_module.cpp`), defined only under Emscripten and built as `order_book_wasm.js` and `.wasm`. It holds the embind declarations and the `EM_JS` glue, and links `order_book_wasm`.

- **Flags, on this target alone:** `-sMODULARIZE -sEXPORT_ES6 -sEXPORT_NAME=createOrderBookModule -sENVIRONMENT=worker,node` (`node` for the tests), `-O3`, and `-lembind`, beside the global `-pthread` and `-fwasm-exceptions`. Memory is a fixed `-sINITIAL_MEMORY=128MB` with no growth, the stacks are `-sSTACK_SIZE=1MB` and `-sDEFAULT_PTHREAD_STACK_SIZE=256KB`, and the pool is strict (`-sPTHREAD_POOL_SIZE_STRICT=2`) at exactly the engine's threads. CMake counts the pool from `settings.hpp`'s `browserShards`, `browserGatewayThreads`, and `browserRollWorkers`, as `browserEngineThreads` does (2N + M + R + 2 = 8), and stops configuring if it can't read them; the module gets the size as `ORDER_BOOK_WASM_POOL`, and a `static_assert` holds it to `browserEngineThreads`. Never `-sBUILD_AS_WORKER`, which `-pthread` rejects. `-sEXIT_RUNTIME=0` is said outright, since a sanitizer build turns it on to check for leaks at exit: with it on, the module, which has no `main`, exited its runtime under the engine's threads the first time nothing kept it alive, at the engine's start, and the page hung. Under ASan it takes `src/wasm/module/asan_options.js`: no allocation stacks, as the tests' options, and ASan's quarantine of freed memory cut from wasm32's 64 MiB to 16 MiB, since the module keeps the shipped 128 MiB and the worst-case session ran out of it under ASan alone.
- **Embedded, read-only** (`--embed-file`): `src/wasm/instruments.csv` and `seed.csv` at `/engine/`, and `tests/replay/valid` and `malformed` at `/samples/`. `enterSamples()` makes `/samples` the working directory, as the terminal's file commands expect.
- **The embind class `Engine`**, one per module, made from the page store as the page holds it (`[{name, bytes}]`): `start()` begins a run on a pthread of its own (runEngine's, the pool's eighth) and returns at once, `stop()` requests a stop (a second forces it), `run(line)` is `Terminal::run`, and `takeEvents()` gives what happened. `release()` names the version.
- **One ordered queue.** Every engine thread's report goes into one queue, in the order it happened: each page-store change (`stored`, copied under the store's lock), each whole line of the report and the diagnostics, `ready`, each wake, and the run's end. The first event after a look asks the worker's thread to look again, through `emscripten_async_run_in_main_runtime_thread` and the `EM_JS` function that calls `Module.onEngineEvents`. A look, `takeEvents()`, takes the queue, then pumps the seed's connection and the terminal's, then takes the queue again, and puts what pumping gave last. The engine writes a record to the store before it sends the answer that waited for it, so once pumping has read an answer, that write is in the queue: the second take is what keeps an answer from overtaking its log write. `run(line)` returns the same events for the worker to post before an answer that came at once. A look never runs inside another call into the module: when the worker's thread waits on a lock an engine thread holds (the in-page set's, `malloc`'s), Emscripten runs the calls queued for it meanwhile, the request to look among them, so a look could start inside a pump, ending a send the outer pump was still driving (`connection N is not one this PageSocketSet holds`, or a send that never answers), or inside `run`'s embind wrapper, before the worker had made that request the one waiting for the answer, which then went unclaimed. The worker counts its calls into the module, and a look asked for during one waits for a task of its own once the outermost returns.
- **Seeding and ready.** At the run's `ready`, a start on an empty store sends `/engine/seed.csv` with `startSend` over a connection of its own, pumped on each look. Its result goes out as `seeded`, then the terminal connects and `ready` goes out with the instruments and the placement (each shard's symbols). Any other start posts `ready` at once. At the run's end, a command still waiting is reported lost, then `exited {code, name}`, the `EngineExit`.
- **The sandbox's bindings**: `submit(symbol, order)`, `cancel(symbol, id)`, and `replace(symbol, id, price, quantity)` reply `{ok, correlation, orderId?}` or `{ok: false, error}`, with `events` as `run` does. Each answer is a `sandboxAnswer` event carrying the correlation, the ID, every frame as the page's `AnswerEvent` (a `type` per frame type, its fields as numbers, a market order's price 0, the rejection reason and refusal code by name, and the CLI's text), the text, and the frame bytes, or the loss. `consumed(connection, bytes)` opens the sandbox's or the terminal's window by that much, clamped to a whole count, and gives what it lets through. Each look ends by posting `progress {connection: "terminal", bytes}` for what the terminal read since the last. `book(symbol)` is the shadow's book: levels best first with their orders in queue order, remaining and initial quantities, and owners; pending stops in trigger order with their type, prices, time in force, owner and mode, and post-only; and the last trade price, or null. `status()` is each shard's instruments and records.
- **Errors.** A C++ exception from the terminal becomes `order_book_cli: <what>`, exit 3, and one from `start` its `error`. `takeEvents` posts one as `aborted`. Anything escaping a binding is caught by the worker, which answers the request `{ok: false, error}` and posts `aborted`, as is an abort on any thread, through `Module.onAbort`. The module exports `getExceptionMessage` and `decrementExceptionRefcount` so the worker can say what a C++ exception was. `start` joins the last run's thread, which has already queued its end, so it returns to the strict pool before another starts; the destructor, if the page ever deletes the object, forces a running engine to stop and joins it.

`src/wasm/js/engine-worker.js` is our own ES-module worker, the module's only caller. It imports the module from the URL `init` names, `locateFile` giving the `.wasm`'s, so the module's pthread workers start from that same `.js`. It never blocks, so it services Emscripten's proxied calls. Every call into the module goes through `call()`, which puts off a look asked for meanwhile (above). Requests are `{id, type, ...}`, handled one at a time in order, each answered `{id, ok, ...}`, and no JavaScript exception crosses `postMessage`:

- `init {protocol, module, wasm, store}` comes first, once; one that fails sets nothing and may be sent again. Anything before it is refused (`init comes first`), and a protocol other than `PROTOCOL_VERSION` (1) is refused with the worker's own (`{ok: false, error: "protocol", protocol}`), so either side refuses a mismatch. Its reply carries the protocol and the release.
- `start` (`ready` or `exited` follows), `stop`, and `run {line}`, answered `{stdout, stderr, exit}` once the terminal has the answer; a second `run` while one waits is refused.
- Posted on the same channel, in the module's order: one message per page-store change (`create`, `write {offset, bytes}` with the bytes transferred, `extend {size}`, `cut {size}`, `rename {to}`, `replace {to}`, `remove`, each with its `name`), `line {stream, text}`, `seeded`, `ready {instruments, placement}`, `exited {code, name}`, and `aborted {message}`.

The worker's sandbox requests, `submit`, `cancel`, and `replace`, wait under their correlation for their `sandboxAnswer`, then reply `{ok, orderId?, events, text, frameBytes}`, or `{ok: false, error}` for a refusal or a loss. `book` and `status` reply at once. `consumed {connection, bytes}`, with no id, is a notification and gets no reply.

`src/wasm/js/engine-client.js` is the engine client, the only thing a page imports, plain ES-module JavaScript with JSDoc, and `engine-client.d.ts` its hand-written types. The JSDoc imports its types from the `.d.ts`, `BrowserEngine` `@implements` its `Engine`, and the module's exports are assigned to their declared types at the end, so `tsc --checkJs` holds the one to the other. The worker's replies are `any`, which nothing checks. CMake writes a copy beside the module with `ENGINE_RELEASE` filled in as `v` and the project version (`build-wasm/engine-client/`), which the Node tests and the zip take.
- `checkSupport()` checks `crossOriginIsolated`, posting a `SharedArrayBuffer` through a `MessageChannel`, `WebAssembly.validate` of a module with a shared memory (threads), and of a function with a legacy `try` and `catch_all` (exceptions), and names the first missing. `createEngine({worker, module, wasm})` runs it first and rejects with an `EngineSupportError` carrying `missing`. It starts the worker as a module worker, sends `init` with the protocol and the URLs, refuses a reply with another protocol, and starts the engine. It resolves once the worker is ready, with the state `starting`; `ready` makes it `running`.
- `run(line)`: `start` and `stop` run in the client, and every other line goes to the worker, one at a time, in order. `start` is refused while the engine is starting, running, or stopping (`start: the engine is already <state>`, exit 2). It returns the engine's diagnostics during the start, the recovery's lines included, and exits 0 at ready or with the `EngineExit` of a start that ended. The first `stop` returns the stop report on stdout and its diagnostics, exiting with the `EngineExit`. A `stop` while stopping forces the first, which then reports exit 8, and returns at once, so it doesn't wait behind the first. `stop` with nothing running says `stop: the engine isn't running`, exit 1.
- `submit`, `cancel`, `replace`, `book`, and `status` reject with what refused them, or `the engine isn't running`. An answer is `{orderId?, events, text}`.
- **The page's side of the credit window**: every command frame is 48 bytes (`commandFrameBytes`), and the client posts a sandbox command only while the frames posted and not yet answered stay within W, so a command beyond it waits. An answer means the gateway read its command. A command beyond the window waits its turn, and a freed slot passes straight to the first waiting one, so commands go in the order they were made. A command woken after the engine went down is refused. Once the client has an answer it posts `consumed` for its frame bytes, to the worker that answered and no later one.
- **The terminal's credit window**: send's output prints only at the end, sorted by symbol, so the window counts bytes, not lines. `Terminal` reads its standing connection and its sends only while the bytes it read and has not had acknowledged are under W (`Terminal::room`), reading on past a partly read frame as the sandbox does. `progress()` gives what it read since it last asked, which the module posts as `progress`. The client acknowledges each with `consumed` as it takes the message, so a page too busy to take its messages stops the reading, and the gateway holds the rest. The page's lines run one at a time, so that direction needs no more.
- **The page store** (`PageStore`, inside the client; ADR 0017): every change message, `create`, `write`, `extend`, `cut`, `rename`, `replace`, and `remove`, is applied to a map of files, and each new worker's `init` gets a copy, which `postMessage` clones, so the page keeps its own.
- **The crash path** (`endWorker`, one at a time, in order): the page ends the worker without warning. Every request waiting on it gets `{ok: false, reset: true}`, so a typed call rejects with why, a terminal line exits 3 with `<verb>: <why>`, and a start or stop waiting reports a crash. The state becomes `down`, and a fresh idle worker gets the page store. There, with no engine running, `verify` and `replay` run, `send` can't connect, as natively, and `start` is the ordinary start: the survey, then `recoverShard`. A recovery that refuses or stops (exit 1, 4, or 5) returns its message and leaves the worker idle. A start or stop cut off by a crash exits 3, as a line cut off does. A fresh worker that fails to start is reported on `aborted`. Three things take this path:
  - `crash()` (or `run('crash')`, which doesn't wait behind a line);
  - an `aborted` message, reported first on `aborted`; one that says memory ran out (`OOM`, `out of memory`, `Cannot enlarge memory`) says so and points to `reset`, since recovery would run out again;
  - an `exited` with code 8, a forced stop, which leaves the engine's threads behind in a module whose strict pool then can't start them again.
- **Ended workers are ignored**: each worker's `onmessage` passes a message on only while that worker is the current one, so an ended worker's late writes and lines touch nothing.
- `reset()` (or `run('reset')`) discards the page store, ends the worker, and starts a fresh one, which seeds it.
- Requests made while a fresh worker is being given the store wait for it.
- `on('state' | 'line' | 'aborted' | 'exited', listener)` returns a function that stops listening. Lines are heard as they come, and a start or stop also collects them for its result.

`tests/wasm/node/page.mjs` plays the page for the Node tests: requests and replies, every posted message in order (a write's bytes kept only in its `PageStore`), and `until(predicate)`, checked after each message, so a test waits on what was posted rather than on time. A page that has ended its worker ignores what that worker still posts. `tests/wasm/node/worker-shim.mjs` runs the worker in a Node worker thread as a browser runs a module worker: `self` is the global, over the thread's port. Its `workerData` isn't Emscripten's `em-pthread`, so the module knows it is the main runtime thread rather than a pthread.

## Tests under node

## CI

Two jobs in `ci.yml`, on `ubuntu-24.04` with Ninja and `emscripten-core/setup-emsdk` pinned to Emscripten 7.0.0, with emsdk and the system libraries it builds on first use cached under `emsdk-cache`, keyed by job:

- **Emscripten Release**: invariant checks at their default, so off, as shipped. It also type-checks `engine-client.js` against `engine-client.d.ts` with `tsc --noEmit --allowJs --checkJs --strict`, TypeScript pinned to 6.0.3 and fetched by `npx`, since the repo has no `package.json`.
- **Emscripten ASan+UBSan Debug**: invariant checks on.

Both build with warnings as errors, run every registered test (not only `-L threaded`, a label that keeps meaning the ThreadSanitizer and Arm jobs) and the CLI step under `node`, within the 30-minute job limit.
