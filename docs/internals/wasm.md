# The browser build (Emscripten)

How the repo builds and tests under Emscripten, the target that runs the whole engine in a visitor's browser tab (spec #127; decisions in #110, #113, #115–#123 and ADRs 0016–0018). This note grows with each slice of v2.2.0. Domain terms (engine worker, page store, engine client, shadow book) are in `GLOSSARY.md` under "In the browser".

## Toolchain

Emscripten **7.0.0**, exactly, locally and in CI. On this machine emsdk is at `C:/dev/tools/emsdk` and is not on `PATH`; a shell needs:

```bash
export EMSDK=C:/dev/tools/emsdk
export PATH="/c/dev/tools/emsdk/upstream/emscripten:/c/dev/tools/emsdk/node/24.19.0_64bit:/c/dev/tools/emsdk/python/3.13.3_64bit:$PATH"
```

`emcmake` uses Ninja (never a Visual Studio generator), so the build gets a directory of its own:

```bash
emcmake cmake -S . -B build-wasm -G Ninja -DCMAKE_BUILD_TYPE=Release -DORDER_BOOK_WARNINGS_AS_ERRORS=ON
cmake --build build-wasm
ctest --test-dir build-wasm -j8 --output-on-failure
```

The Emscripten toolchain file sets `CMAKE_CROSSCOMPILING_EMULATOR` to emsdk's `node`, which CTest puts in front of every test that names a target.

## The CMake branch

The toolchain is the switch: there is no option or preset of its own. `if(EMSCRIPTEN)` near the top of `CMakeLists.txt` adds `-pthread` (real pthreads, on Web Workers) and `-fwasm-exceptions` (legacy wasm exceptions, never `exnref`, until the browser floor passes Safari 18.4) to every target's compile and link. `ORDER_BOOK_ENABLE_TSAN` or `ORDER_BOOK_BUILD_BENCHMARKS` beside it is a configure error: Emscripten has no ThreadSanitizer, and nothing is measured in wasm.

What builds: every library and `order_book_cli`, and every test executable but the six below. `order_book_engine` doesn't, since nothing can `listen` in a tab, so `apps/engine_handlers.cpp` has no wasm branch. Neither do the benchmarks, the profiling tools, or the latency harness.

At the end of the file, once every target exists, each executable gets the link settings for running under `node` in CTest: `-sNODERAWFS=1` (the host's files, so tests read `tests/` and write their scratch directories directly), `-sEXIT_RUNTIME=1`, `-sSTACK_OVERFLOW_CHECK=2` with the shipped module's stacks (`-sSTACK_SIZE=1MB` for the main thread and `-sDEFAULT_PTHREAD_STACK_SIZE=256KB`, where Emscripten's defaults are 64 KiB each, which ASan's frames outgrew once optimized), `-sALLOW_MEMORY_GROWTH=1` with `-Wno-pthreads-mem-growth` (growth makes every pthread re-check its view of memory, which is acceptable in tests only), and a strict pthread pool: `-sPTHREAD_POOL_SIZE_STRICT=2` with 16 threads. A program that asks for one thread more than its pool holds aborts loudly rather than waiting for a thread that never comes. `order_book_wasm_threads(<target> <n>)` raises one executable's pool. `order_book_cli` gets the same settings, since under Emscripten it runs only in the script tests. Under ASan each also links `tests/wasm_asan_options.js` with `--pre-js`, which sets `Module.ASAN_OPTIONS` to `malloc_context_size=0`: Emscripten's ASan reads its options from `Module`, never the environment, and unwinds a JavaScript stack for every allocation and free it records, which made the suites about 50 times slower (22 minutes at `-j4` here, against under 4 without). A report still names the bad access and where it happened, only not where the memory was allocated or freed; `node_pool_poison_tests` still requires its use-after-poison report.

## Portability, in source

Every wasm-only branch is under `__EMSCRIPTEN__`, and the wasm jobs are their only check.

- `FileLogStorage`'s rename takes the plain-`rename` branch, as on systems without `RENAME_NOREPLACE`: Emscripten's libc has no `renameat2`, so a rename there replaces. The browser's log lives in `PageLogStorage`, whose own checks require the refusal.
- `NativeFile::extend` sets the end of the file instead of calling `fallocate`, which Emscripten's libc lacks.
- `FileLogStorage::lock` takes `flock`, which Emscripten accepts without locking anything, then holds the lock in a process-wide registry by path. A module is one process that shares its files with nothing, so that registry is the whole of "one holder at a time".
- `size_t` is 32 bits on wasm32. The 14 conversions only that target saw (`-Wshorten-64-to-32`) are fixed with types or casts, never a `-Wno-` flag: 10 in the command generator, through `indexBelow`, which draws exactly what `below` does, so every pinned fingerprint and `generatorVersion` 9 are unchanged.
- `pastTheLast` in `thread_placement.cpp` is defined only where a branch uses it.
- **`Doorbell`** sleeps on `emscripten_futex_wait` and wakes with `emscripten_futex_wake`, on its own atomic's word, exactly where native calls `std::atomic::wait` and `notify_one`. libc++'s `std::atomic::wait` polls under Emscripten, waking up to every few milliseconds, so idle matching threads and log writers would never quite sleep. Every change to the atomic is still an exchange, so the lost-wake-up reasoning in `runtime.md` holds unchanged, and `wait` loops on a load until the state isn't asleep, as `std::atomic::wait` does. `matching_loop_tests`' `testARingWakesASleeper`, which hangs without the wake, runs in both wasm jobs.

## `order_book_wasm`

A static library that builds and is tested on every platform (`include/order_book/wasm/`, `src/wasm/`; ADR 0018). It links `order_book_cli_commands`, and through it `order_book_network`, and is not public API. Its parts:

- **`settings.hpp`**, the one place the shipped values live. `browserSettings(list)` gives the engine's settings: two shards (N), one gateway thread (M), one roll worker (R); 64 KiB log files with normal retention; rings of 1,024 commands, 4,096 responses, and 4,096 log records per shard; native book capacity; 3 connections; a slow client warned at 64 KiB and cut off at 1 MiB; `process` durability; no log or checkpoint directory, since the page store is injected. Beside it: `pageSocketBuffer` (64 KiB each way per connection), `creditWindow` (W, 64 KiB), and `browserEngineThreads`, 2N + M + R + housekeeping + `runEngine`'s own thread = 8, which the module's strict pool will be.
- **`ShadowBooks`**: a book per instrument, at the directory's capacities, behind one lock, so any thread may ask. `follow(change)` takes each `PageLogStorage` change, under the store's lock and without calling the store. A file's first write at offset 0 that starts with the log's magic is its header, read through `CommandLogReader`; any other file is dropped. Each later write must be whole 40-byte records at the file's next record, each at its shard's next position. Each is checked against the chain by `decodeLogRecord`, must be for an instrument of that file's shard, and runs through `executeCommand`, as its shard ran it. Anything else is a problem: the first is kept, `problem()` says it, and nothing more is followed. `rebuild(store)` runs `surveyLog`, then a read-only `recoverShard` per shard, as `verify` reads a store, on a `Shard` of its own. It restores each book from that shard's image and marks every log file already there closed, since a start always opens a new one, so a later write to one is a problem too. A store recovery refuses leaves the books empty and a problem saying why, and the start that follows refuses it as well. `records(shard)` is the shard's next log position, and `shardOf` comes from the directory.
- **Book views**: `decodeBookImage` reads a `writeImage` image field by field (`docs/checkpoint-format.md`) into a `BookView`: levels best first with their orders' IDs, sequence numbers, quantities and owners, the pending stops in trigger order with every field as submitted, and the last trade price. It throws `std::invalid_argument` for bytes that aren't an image. `ShadowBooks::book(symbol)` is a snapshot, decoded from its image. Nothing is pushed.
- **ID assignment**: `assignOrderId(symbol)` gives 1 + the larger of the highest ID the shadow has seen and the highest it has given. "Seen" is every add record it ran and, after a rebuild, every ID its book holds, resting or pending. A rebuild keeps what was given. So a rebuilt shadow can give again the ID of an order that filled or was cancelled before a checkpoint, which the book allows: only a live ID is a duplicate. It returns nothing once no ID is left.
- **`PageConnection`** and **`PageSend`**: a client connection over the in-page set, driven without blocking, since the module's strict pthread pool leaves the engine worker no thread to wait on. `pump()`, on each wake, writes what fits, half-closes once everything is written if `finish()` was called, reads what came, and ends the `ClientStream` once the connection ended with nothing left. A connection holds its run's set by `shared_ptr`, and its destructor resets a connection still open and releases the slot. `PageSend` is `send` of a prepared file over one, ending in `finishSend`'s result. `startSend(sockets, args)` takes send's own arguments: what `prepareSend` refuses, `cannotConnect`'s text (`Connection refused`) when there is no set, the set takes no connection, or `--connect` names any address but `browserListen`, since nothing else listens in the tab, or the send under way.
- **The terminal** (`Terminal`, behind `run(line)`): `buy`, `sell`, `cancel`, `replace`, `book`, and `status`, the CLI's `send`, `replay`, and `verify`, and `ls`, `cat`, and `help`. A client command becomes the 13 fields of one v3 row, checked by `parseRow` exactly as a replay row is, so a bad one prints the parser's column and message and exits 2. `buy` and `sell` are `SYMBOL QUANTITY [PRICE]` with `stop=`, `tif=`, `post-only`, `owner=`, and `stp=`. A price makes a `LIMIT` order and none a `MARKET` one, and `stop=` makes them `STOP_LIMIT` and `STOP`. The time in force defaults to `GTC` for a priced order and `IOC` otherwise, and an owner with no `stp=` is `CANCEL_RESTING`. A symbol off the instrument list, which is fixed, is refused there for all four commands alike (`<verb>: XYZ is not on the instrument list`, exit 2) and takes no line. The ID comes from `assignOrderId` once the row passes, and prints first as `assigned id=N`. `cancel` and `replace` name theirs. The row goes on the standing connection (`connect` on each start's ready; `disconnect` when the run ends, after which a waiting command is reported lost, exit 3). Its correlation is its line in `collected()`, the session's CSV, whose header is line 1, so the Nth client command is `line N+1:`. That is how the session's commands, collected, are a CSV whose `send` prints the same answers under the same lines. The spec's "correlation N" would need a CSV with no header. `run` returns the result at once, or nothing while the answer is due, which `pump` then gives: the lines `answerLines` prints, exit 4 for a refusal, as `send`'s. A command with no engine running prints `the engine isn't running`, exit 1, as `send` with no connection. Errors are `<verb>: <what>`. `book SYMBOL` restores the shadow's image and prints `formatFinalBook` of it, what `replay --book` prints for a final book. `status` prints `shard K: <symbols> records=N` per shard. The CLI's commands are `order_book_cli_commands` and print its bytes, and each may keep the program name, as the page's recorded sessions type it (`order_book_cli replay valid/stops.csv --trades`). Their files are named from the working directory, which is the samples' root: `valid/` and `malformed/`, as in `tests/replay`, which the module embeds read-only (M1). So a path prints as typed, as native's does run from `tests/replay` (`malformed/price_zero.csv:4: ...`). `send` adds `--connect 127.0.0.1:9000` when none is typed, since send requires it, and opens a connection of its own (`PageSend`), which `pump` drives to the end; with no engine running it prints native's `cannot connect` line, exit 1. `replay` runs on fresh books, not the engine's. `verify [--validate final|per-command]` is `verifyStores` over the page store, which the engine holds locked while it runs, so it prints `order_book_cli: verify: the page store is locked: the engine is using it`, exit 1, until the engine stops, as native's `... is locked`. It takes no `--log-dir`: the store is the page's. `ls [DIRECTORY]` lists a sample directory's entries, sorted, a directory's with a trailing `/`, and `cat FILE` prints a sample's bytes; each refuses an absolute path or one with `..` as no such sample, exit 1. `help` lists every command, the page's own `start`, `stop`, `crash`, `reset`, and `clear` too, which the engine client runs, and the instruments. Anything else prints `<word>: unknown command; help lists them`, exit 2.
- **Seeding**: `src/wasm/instruments.csv` pins AAPL and MSFT to shard 0 and NVDA and TSLA to shard 1. `src/wasm/seed.csv` rests three bids and three asks on each, IDs 1 to 6, so the panels' IDs start at 7. `BrowserEngine::startedEmpty()` says whether a run began on an empty store (a first load, or after a reset). Then the engine worker sends the seed with `startSend` before telling the page the engine is ready, and its answers go out as `seeded`, which the terminal doesn't print. Any other start recovers the seed from the log. The engine's nominal address is `127.0.0.1:9000`, which nothing binds, so `send`'s `--connect` can name it.
- **`BrowserEngine`**: the engine as the engine worker runs it. It holds the instrument list's directory, the `PageLogStorage` (made from the page's files), and the shadows, which follow every change before the injected `stored` callback is told it. So the page never sees an answer whose log write the shadows lack. `run(stop, report, diagnostics)` rebuilds the shadows, makes a new `PageSocketSet` whose wake calls the injected `wake`, and calls `runEngine` with those parts and a `ready` that calls the injected one. A run after a clean stop recovers from the same store.

## Tests under node

Every registered test runs under `node`, against the very expected files and fingerprints native uses: passing both is the byte equality, and no job diffs native output against wasm.

- **Script tests** (`replay_cli_*`, the `*_abort_*` cases, `convert`, `checkpoint`, `verify`, `cut-log`): each `add_test` passes `-DEMULATOR=${CMAKE_CROSSCOMPILING_EMULATOR}`, empty natively, and `tests/expect_failure.cmake` and `tests/replay/check_cli_output.cmake` run `${EMULATOR} ${PROGRAM}`, since CMake puts the emulator only in front of a command that names a target.
- **Not built under Emscripten**, each needing TCP, a child process, a signal, or the engine executable: `engine_tests`, `engine_start_allocation_tests`, `gateway_socket_tests`, `engine_process_tests`, `engine_signal_tests`, `engine_end_to_end_tests`.
- `engine_in_process_tests` and `engine_in_process_forced_stop` run the whole engine through the injected-parts entry (`network.md`): start, a session, a clean stop, a recovering restart, and a forced stop, which is what wasm has in place of those six.
- `order_book_wasm_tests` (`threaded`) covers `order_book_wasm`: the settings, an image with owners, a partial fill, and each kind of stop decoded, the shadows following hand-made log files and refusing each kind of bad write, a rebuild, ID assignment, and a whole `BrowserEngine` run over its page store and in-page connections. In that run, a session prints what replay prints, the page's copy equals the store, and each shadow equals the checkpoint the clean stop published at its log's end, before and after a new engine recovers from the copy.
- `wasm_terminal_basic`, `wasm_terminal_options`, `wasm_terminal_errors`, `wasm_terminal_files`, and `wasm_terminal_send` (`threaded`) each play the session `tests/wasm/sessions/<name>.txt` through a `Terminal` on a `BrowserEngine` seeded from the shipped seed, in a copy of `tests/replay/valid` and `malformed` made the working directory. The sessions are byte-exact (`tests/wasm/sessions/.gitattributes`), as the samples are, since `cat` prints a sample's bytes. The transcript must equal `<name>.expected`: each line after `> `, then its output, its stderr lines after `! `, and `[exit N]` when not 0. `collected()` must equal `<name>.csv`. Then the session's `send` lines, which must all come before its first client command, go through `send`'s own code, after the same seed, to a fresh engine, each printing exactly what the terminal printed, and then that CSV, whose `line N:` lines must be what the transcript's `buy`, `sell`, `cancel`, and `replace` printed, line for line, exiting 4 exactly when one of them was refused (`tests/session_transcript.hpp` reads a transcript for those). Natively, `engine_end_to_end_tests` does the same through the real binaries: `order_book_cli send` of the seed, of each session's `send` lines (stdout and exit as the transcript's, the file named under `tests/replay`), and then of each session's CSV to an `order_book_engine` on `src/wasm/instruments.csv`. A changed transcript is written to the build's `wasm-terminal/`. `wasm_terminal_restart` shows a start on a store with a log doesn't seed, and that the terminal counts on across starts; that `send` can't connect before the first start, after a stop, or to another address; and that `verify` reads the store once the engine has stopped.
- `thread_placement_tests` exits 77, which its `SKIP_RETURN_CODE` shows as Skipped.
- `log_writer_tests` skips only "a rename never replaces a file" on real files, printing why.
- `node_pool_tests` sizes its size classes from its `Node`, which is 40 bytes on wasm32 rather than 48, so six sizes still claim six classes and the seventh, past the largest, goes to the heap.

## CI

Two jobs in `ci.yml`, on `ubuntu-24.04` with Ninja and `emscripten-core/setup-emsdk` pinned to Emscripten 7.0.0, with emsdk and the system libraries it builds on first use cached under `emsdk-cache`, keyed by job:

- **Emscripten Release**: invariant checks at their default, so off, as shipped.
- **Emscripten ASan+UBSan Debug**: invariant checks on.

Both build with warnings as errors, run every registered test (not only `-L threaded`, a label that keeps meaning the ThreadSanitizer and Arm jobs) and the CLI step under `node`, within the 30-minute job limit.
