# Engine internals

Core structures and contracts: types, sequence numbers, storage, the index, the node pool, matching, results, events, invariants, and errors. Order behaviors built on these are in [`order-behaviors.md`](order-behaviors.md).

## Layout and types

All code lives in namespace `order_book`; headers in `include/order_book/`, implementations in `src/`.
- **Prices are integer ticks** (`unsigned int`), assuming a fixed $0.01 tick size. IDs, sequence numbers, and quantities are also `unsigned int` (aliases `Price`, `Quantity`, `OrderId`, `TradeId`, `SequenceNum` in `types.hpp`, which public signatures use rather than `unsigned int`), and zero is invalid for all of them. Field checks live once, in the private `Order::malformedReason()` (a zero ID, price, or remaining quantity, an invalid `Side`, or an unsupported `OrderType`; only `LIMIT` exists, and it is the default argument). The constructor throws `std::invalid_argument` on a zero sequence number or on any reason `malformedReason` returns, with that reason's `rejectionMessage` (one distinct message per `RejectionReason`, in `rejection_reason.hpp`).
- **Sequence numbers are assigned by the book**, from `OrderBook::nextSequenceNum`, via the private friend-only `Order::assignSequenceNum`; the value passed to the `Order` constructor is replaced on acceptance. They record acceptance order, which is what time priority within a level follows, and an order keeps its number for life (a resting remainder keeps the one it was given before matching). `submitOrder` consumes a number once validation passes, even if the order then fills completely or matching throws; `addOrder` consumes one only once the order has rested; rejected orders consume none. On overflow the counter wraps back to 1 (skipping zero) and numbers are silently reused; time priority within a level is queue position, so it is unaffected, but don't assume numbers are unique or increasing across a wrap. Internally, resting goes through private `restOrder` (no validation, no numbering) so the remainder isn't renumbered — don't route it back through `addOrder`.
- **`Order`** — tracks initial/remaining quantity and `FillStatus` (`NONE`/`PARTIAL`/`FILLED`, read and set with `getFillStatus`/`setFillStatus`; `isActive` means anything but `FILLED`); `fillQuantity` returns the unfilled leftover of the requested amount.

## Storage

- **`PriceLevel`** — FIFO `OrderQueue` (`std::list<Order, PoolAllocator<Order>>`, in `order_location.hpp`) at one price/side plus a cached aggregate `quantity`, a `std::uint64_t` (as is `PriceLevelSummary::totalQuantity`; its `orderCount` and `PriceLevel::getOrderCount` count orders, not quantity) so a level of many maximal orders cannot wrap it. `addOrder` returns an `OrderLocation`. Any mutation must keep `quantity` in sync with the list. The private `fillOldestOrder` (fills one order, popping it if fully filled) is reserved for its friend `OrderBook` (and tests). `OrderBook`'s private `consumeLevel` (multi-order fill at one level; it makes no trades and no events, so it is not a public command, and tests reach it through `OrderBookTestAccess`) loops `fillOldestOrder`, unindexing each fully filled order the moment it leaves the level, erases the level once empty, and returns a `ConsumptionResult` (status, per-order `OrderFill`s, unfilled remainder). Note the status naming: `SATISFIED` means the level is now empty, `LEVEL_EXHAUSTED` means quantity still rests there.
- **`LevelArray`** (`level_array.hpp`, ADR 0015) — all four level containers: a sorted `std::vector` of `{price, Level*}`, worst price first, so the best is the array's last element, with each level object in the pool (`PoolAllocator<Level>`, so the heap for a book with no pool). It reads like the `std::map` it replaced: iteration runs best first, an element has `.first` and `.second` (`Element`, a proxy, with `Arrow` behind `operator->`), and `find`, `at`, `contains`, `try_emplace`, `erase`, `key_comp` keep their names. `locate` gallops back from the best price, then bisects. Levels never move, so `PriceLevel*` and `StopLevel*` handles stay valid. `try_emplace` does everything that can throw (array growth, the block, construction) before the insert, so a failure changes nothing. A moved-from array is empty with a null pool, and `OrderBook`'s move assignment still clears the levels before replacing the pool, since a level must go back to the pool it came from. A new level far from the touch shifts every level better than it, which a client can do on purpose: 678 ns at 2,000 levels on a side, 4.9 µs at 20,000, and 55 µs at 200,000 on this machine, against 120 to 137 ns near the touch (unrecorded, from `new-level-far` and `new-level-near`). It is a documented tail event, so never call level insertion O(log L). `OrderBookTestAccess` is a friend so `invariant_tests` can put levels out of order.
- **`OrderBook`** — `bids` is a `LevelArray<PriceLevel, std::greater>` and `asks` a `LevelArray<..., std::less>`, so `begin()` is always best price on both sides. `orderIndex` (an `OrderIndex`, `order_index.hpp`: an open-addressed table of `pair<OrderId, OrderLocation>`, linear probing with a Fibonacci hash, at most three quarters full, backward-shift erase, ID 0 reserved as the empty marker so it cannot be emplaced; any emplace or erase may move entries and invalidates iterators, and iteration order is unspecified; tested against `std::unordered_map` by `order_index_tests`; a new table comes from `vector`'s range constructor over `RepeatedSlot`, a plain copy loop, since MSVC's fill constructor takes 30 times as long above about 4 MiB, and `reserve` plus `push_back` needs a `noexcept` default constructor that allocates with checked iterators, so a failure there terminates) gives O(1) cancel: `OrderLocation` stores price, side, an `OrderQueue::iterator` into the level's list (valid because `std::list` iterators are stable), and a `PriceLevel*` to the level itself (valid because a level object never moves and is erased only once empty), so `cancelOrder` reaches the level without searching the side; it checks that the handle names a level at the entry's price and side, and `checkInvariants` compares (never follows) it. `addOrder` and `submitOrder` both run the read-only `validateNewOrder` first. It returns a `RejectionReason`, checked in this order: `Order::malformedReason()` (rechecked because an order can be changed after it is built), a `FILLED` order, then an ID already resting (`DUPLICATE_ORDER_ID`). `addOrder` throws `std::invalid_argument` with that reason's `rejectionMessage`; `submitOrder` returns a REJECTED result. `addOrder` then also refuses an order at or through the best opposing price (`WOULD_CROSS_BOOK`, thrown the same way), since it never matches; so no public command leaves the book crossed. Either way nothing is mutated and no sequence number or trade ID is consumed. IDs of filled or cancelled orders may be reused, since the index tracks only live orders. `activeOrderCount()` is the number of resting orders (index entries), not of levels. `reserve(n)` is a capacity hint that sizes the index for `n` resting orders so it does not rehash while the book grows; it changes nothing the book reports, so it is the one non-const public member without an `InvariantBoundary`. `findActiveOrder`, `getBestBid`, and `getBestAsk` return `Order` copies (never a reference or iterator), so callers can neither mutate a resting order behind the level's cached `quantity` nor hold a reference that dangles once it is filled or removed; tests that need element identity use `OrderBookTestAccess::indexedOrder`. `OrderBook` is move-only: a copy would share the original's list iterators. `cancelOrder(id)` looks the order up in the index, takes its *remaining* quantity off the level aggregate, erases it from the list, unindexes it, and erases the level once empty. Its result is built before anything is mutated, and allocates nothing (its one event is held inline); once the lookup and a guard that the entry's level handle names a level at its price and side pass, nothing can throw; other orders keep their positions and iterators, and it consumes no sequence number or trade ID. An ID that is not resting (unknown, already cancelled, fully filled, or an incoming order that never rested) returns a rejected result (`ORDER_NOT_FOUND`) and leaves the book unchanged. Empty levels are erased on removal. `snapshot(depth)` returns top-N level summaries per side.
- **Node pool** (`node_pool.hpp`) — every level object and every level's queue takes its blocks from the book's `NodePool` (`std::unique_ptr` member declared first, so it outlives the levels and keeps its address when the book moves), through `PoolAllocator`, which falls back to the heap for arrays, for sizes beyond the pool's few size classes, and when it has no pool (a level built outside a book, or by a moved-from book). Freed blocks go on a per-size free list and are reused; chunks are freed only with the book, so a book keeps its peak node memory. The index and level arrays allocate only when they grow. `OrderBook`'s move assignment is hand-written (clear, then take the other's members, pool last), so a new member must be added there. It has six size classes (`NodePool::maxClasses`): the two list nodes, the two level objects, MSVC's checked-iterator proxy in Debug, and one to spare. In ASan builds a freed block is poisoned whole, since the pool never returns the memory, so only that can catch a stale pointer into one; `node_pool_poison_tests` proves it in a process of its own. `NodePool::check()` walks every free list without allocating and returns carved minus free per class, with `sound` false for a list longer than the blocks ever carved, which a double free's cycle makes. The pool's chunks come from plain `operator new` whenever the alignment allows, so the allocation-failure tests and allocation counters see them; a book that already holds an order usually has room in both, so a test of a new level's rollback fills them on purpose (`testNewLevelRollsBackWithArrayAndPoolExhausted`), and `testFirstOrderOnEmptyBookRollsBack` makes a queue node's allocation fail.

## Matching

- **Matching** — `submitOrder` runs `matchOrder` (loops while the incoming order has quantity and crosses the best opposing price), then rests any remainder at its own limit price via `restOrder`. Each loop step is one private `executeOnce`: it executes min(incoming, resting) against the oldest order at the best opposing level, at the resting price, and returns exactly one `Trade`. It validates everything and builds the `Trade` before mutating, so a throw leaves the book unchanged — preserve that ordering. `matchOrder` makes room in its trade vector before each `executeOnce`, so recording a trade cannot throw after the book changed. `submitOrder` is not atomic: if an allocation fails mid-match, while building the result, or while resting the remainder, executions already made stand (the book stays consistent) and their trades and events are lost with the exception. Everything the submitted order reports is recorded *before* its remainder rests, so resting is its last step that can fail and its remainder never rests behind a throw of its own; keep it that way (a cascade may follow, and may throw, after it). It unindexes the resting order only when fully filled (a partially filled one keeps its index entry and FIFO position) and erases the level once empty.

## Results and events

- **Result types** — Results hold their events and trades in `SmallVector<T, N>` (`small_vector.hpp`): trivially copyable elements, `N` inline, heap only beyond (`SubmissionTrades` 4 and `SubmissionEvents` 6, defined with their capacities in `result_recorder.hpp`; `CancellationEvents` 1), so a command's result allocates nothing unless it makes more than four trades. The getters return those types: they iterate, index, compare equal with a `std::vector`, and bind to `std::span<const T>`; a `std::vector` copy is `toVector()`, never implicit. It is not a drop-in `std::vector` (no erase, insert, clear, or resize), and moving a result whose elements are inline copies them, so don't hold pointers into a result across a move. `CancellationResult` (in `cancellation_results.hpp`) is what `cancelOrder` returns. Its constructor is private, so it is built only with `CancellationResult::cancelled(id, remaining)` (success, one `OrderCancelled`; throws on a zero ID or quantity) or `rejected(id, reason)` (one `CancelRejected`; echoes any ID; throws on `NONE`), and read through `isSuccess`, `getRejectionReason` (an `optional`), and `getEvents`. `submitOrder` and `addOrder` return `SubmissionResult`, whose `submissionId` is the incoming order's ID. Its constructors are private, so it is built only through `ResultRecorder` (`result_recorder.hpp`, an implementation-detail header, public so `result_type_tests` can test it directly), through `SubmissionResult::accepted`, or with `rejected`, which holds a reason, no trades, `FillStatus::NONE`, and the submitted quantity as remaining. The recorder opens with the submitted order's `OrderAccepted` (zero ID or quantity throws; price 0 means no limit price) and takes `trade(Trade)` (the trade and its `TradeExecuted`), `prevented(SelfTradePrevented, incomingSide)`, `expire(quantity)`, and `triggered(stop as an OrderAccepted, stopPrice, tradePrice)` as things happen, checking each append against the *current* order (the submitted one, or the stop that triggered last): its ID and side, its limit price (none at price 0), no more traded than it has open, and at most one `OrderExpired`, for exactly its open quantity, last in its part. A failed check throws `std::invalid_argument` (an engine bug) and changes nothing; `trade` makes room for both the trade and its event before pushing either. `finish()` yields the result once (later calls throw): every event in execution order, every trade (cascade included; preventions are events only), and the submitted order's remaining quantity (what it did not trade, rested or expired) and `FillStatus` (NONE if nothing traded, FILLED if nothing is left, PARTIAL otherwise), both fixed when its own part ends at the first `triggered` or at `finish`. `accepted(acceptance, trades, remaining)` is shorthand for a recorder fed only those trades (it also refuses price 0 and a `remaining` other than what is left); it takes the trades vector whole, so it allocates no more than v1 did. A rejection echoes the submitted ID even when it is the reserved 0; an accepted result requires a positive ID. Each `Trade` (in `SubmissionResult::getGeneratedTrades()`) stores resting (maker) and incoming (taker) IDs plus the incoming side, from which `getBuyOrderId`/`getSellOrderId` derive.
- **Lifecycle events** (`book_event.hpp`) — `BookEvent` is a `std::variant` of `OrderAccepted`, `OrderRejected`, `TradeExecuted`, `OrderCancelled`, `CancelRejected`, then (spec #40, since v2.0.0) `OrderExpired`, `SelfTradePrevented`, `StopTriggered`, `OrderReplaced`, `ReplaceRejected`, each a plain struct with defaulted `==`. `BookEvent`, `RejectionReason`, replay's `Command`, and `ParseErrorCode` are open sets: only ever append, never reorder (README's Public API). `RejectionReason` likewise gained the request and replace reasons after `WOULD_CROSS_BOOK`, each with its own `rejectionMessage` and `rejectionReasonName`; `formatEvent` prints an `OrderAccepted` at price 0 as `price=MARKET`. They are domain output held in the command's result (`SubmissionResult::getEvents()`, `CancellationResult::getEvents()`), not logging. `SubmissionResult` derives them in its factories, so its event rules hold by construction: `rejected` holds exactly one `OrderRejected`; `accepted` holds the `OrderAccepted` then one `TradeExecuted` (incoming/resting IDs, resting price, quantity) per trade in execution order; there is no resting event. `CancellationResult`'s factories likewise hold exactly one `OrderCancelled` (`cancelOrder` passes the remaining quantity at cancel time) or one `CancelRejected` (reusing `RejectionReason`). `addOrder` never matches, so its result holds only its `OrderAccepted`; it still throws on a rejection rather than returning one. Printing is separate: `formatEvent` (`event_format.hpp`) turns an event into one line of text, and only callers (the CLI) use it; the engine never prints events. Its only output of any kind is the line a failed invariant boundary writes to stderr just before `std::abort` (see Invariants).

## Invariants and errors

- **Invariants** (`invariants.hpp`, `src/order_book_invariants.cpp`) — `checkInvariants()` (public, `const noexcept`, never allocates) makes one O(N + L) pass and returns an `InvariantResult`. The result holds the first `InvariantViolation` found (none if the book is sound), plus the side, price, order ID, expected/actual values, and a string-literal `detail`; `formatInvariantResult` prints it on one line. The pass checks bids, then asks: level ordering, each level's own price and side, non-empty levels, then each order (quantity left, well formed via `malformedReason`, not FILLED, sequence number set, at its level's price and side, FIFO by sequence). Sequence order is judged by `sequenceAge`, relative to `nextSequenceNum`, so a level queued across a wrap passes. Then each level's aggregate. Then each side's pending stops (`checkStopLevels`: stop-level ordering, own stop price and side, non-empty; each stop passes `checks::requestReason`, is a stop type, numbered, at its level's stop price and side, FIFO by `sequenceAge`; violations `INVALID_STOP_ORDERING`, `MISPLACED_STOP_LEVEL`, `EMPTY_STOP_LEVEL`, `MALFORMED_PENDING_STOP`, `MISPLACED_PENDING_STOP`, `INVALID_STOP_FIFO_SEQUENCE`). Next, the index: every resting order needs an entry naming its side, price, and list position, with no ID resting twice. Any extra entry is stale and is found by key and recorded place alone, without using its possibly dangling iterator. The pending index gets the same checks (`checkIndexedStops`, `findStalePendingEntry`, reusing `MISSING_INDEX_ENTRY`, `INVALID_INDEX_ENTRY`, and `DUPLICATE_ORDER_ID` for an ID both resting and pending). Last, best bid must be strictly below best ask. A broken invariant is an engine bug, not a caller error. Each command that can mutate (the public `addOrder`, `submitOrder`, and `cancelOrder`, and the private, test-only `consumeLevel`) starts with an `InvariantBoundary` guard. When `invariantChecksAfterCommands` is set (from `ORDER_BOOK_INVARIANT_CHECKS`), the guard's destructor runs `enforceInvariants` once the command returns or throws. On failure that prints `order book invariant violated after <command>: <result>` to stderr and calls `std::abort`. Private steps (`executeOnce`, `restOrder`, `matchOrder`) are not boundaries: structures may be out of step between them. A new public mutating command needs the guard too.
- Errors are currently signaled via exceptions (`std::invalid_argument` / `std::runtime_error`); `getBestBid`/`getBestAsk` throw `std::runtime_error` on an empty side. The exceptions are `cancelOrder`, which reports a non-resting ID as a value (a rejected result with `ORDER_NOT_FOUND`) and throws only on internal inconsistency (an index entry whose level handle does not name a level at its price and side), since it never allocates, and `submitOrder`, which reports rejections as values and throws only on internal inconsistency or allocation failure. With automatic invariant checks on, every public mutating command also checks the book as an exception unwinds through it, so an internal-inconsistency throw the checker can see (such as `cancelOrder`'s missing-level case) aborts there instead of reaching the caller. Allocation failures leave the book sound, so they still propagate.
