# Benchmarks and profiling

Implementation notes. Methodology is in [`../../benchmarks/README.md`](../../benchmarks/README.md).

- **Benchmarks** (`benchmarks/`, library `order_book_benchmarking`, which links `order_book_replay` and `order_book_reference`; CLI `order_book_benchmarks`; methodology in `benchmarks/README.md`). Five built-in v1 workloads (`small-book`, `deep-book`, `matching-heavy`, `cancellation-heavy`, `mostly-resting`; `builtInWorkloads()`, compact `BenchmarkCommand`s through `submitOrder(Order)`, their commands unchanged since generator version 2, which `testV1WorkloadsUnchanged` checks through `workloadFingerprintV2`) and six behavior workloads (`quote-refresh`, `pending-stops`, `self-trade`, `immediate`, `matching-heavy-request`, `matching-heavy-owned`; `behaviorWorkloads()`, `WorkloadFamily::BEHAVIOR`, `BehaviorMix`, `BehaviorCommand`s through `submitOrder(OrderRequest)`/`replaceOrder`/`cancelOrder`, generated in `behavior_workload.cpp` on `ReferenceBook`, held in shape by floors and caps on resting orders and pending stops; the two matching-heavy ones replay matching-heavy's exact stream, owner 0 or owner = order ID; `replay` renders them as v2 rows), and three sizes (smoke 10k, standard 100k, extended 1M timed commands). `generateWorkload` builds the whole workload (preload, timed commands, predicted `WorkloadOutcome`) before anything is timed, from its own `WorkloadModel`, never an `OrderBook`, with the same RNG rules as the randomized harness (raw `mt19937_64`, own `below`, one draw per statement). `benchmark_harness_tests` pins each workload's fingerprint at the smoke size (now under `workloadGeneratorVersion` 3), so any change to what is generated must bump `workloadGeneratorVersion` and re-pin. `WorkloadOutcome` gained `replaces`, `expirations`, `preventions`, `stopsTriggered`, and `finalPendingStops`, appended to the CSV and JSON. The mixes are tuned so each book keeps its shape from 10k to 1M commands (see the comment above `makeWorkloads`), so re-check final orders and levels at every size after changing one. Each run reserves the book's index for `expectedBookSize` (preload or predicted final count, recorded as `reserved_orders`) before the untimed preload, so the baseline's mostly-resting numbers predate that. `runOnce` times only the timed commands: `core` calls `submitOrder`/`cancelOrder` directly, and `replay` parses in-memory CSV through `ReplayEngine` with validation `NONE`. It throws if the book's outcome differs from the prediction. The program exits 3 in a build that is not optimized (no `NDEBUG`, automatic invariant checks, ASan, or UBSan, which CMake reports through `ORDER_BOOK_UNDEFINED_SANITIZER` since GCC defines no macro for it) unless given `--allow-unoptimized`, which the CTest smoke run passes. The recorded baselines are in `docs/BENCHMARKS.md`: v2.0.0's (all eleven workloads) from `benchmarks/results/2026-10-29-order-behaviors/`, which also holds P3's paired regression check against v1.0.0 (`f22a8f4`; written up in `docs/OPTIMIZATION.md`, "The v2.0.0 regression check"), and the first, kept as history, from `benchmarks/results/2026-10-25-baseline/` (each `summarize.py` recomputes its tables). `ResultRecorder`'s per-trade path is inline in its header for that check's sake (a call per trade across translation units cost about 8%), and `ReplayEngine::run` reserves one event per record. It reports per-run throughput only: the harness never times a single command, so don't add per-command latency percentiles or low-latency claims, and don't compare with production exchanges. `docs/images/make_figures.py` draws `benchmark-baseline.svg`, `benchmark-v2-baseline.svg`, `optimization.svg`, and `replay-terminal.svg` from those results, `docs/OPTIMIZATION.md`'s tables, and `tests/replay/expected/`, so rerun it after changing any of them; the other four are hand-edited SVG whose books and trades were checked against the CLI, so recheck them if a matching rule changes.
- **Profiling** (`benchmarks/profiling/`, option `ORDER_BOOK_BUILD_PROFILING`, which needs the benchmarks; README there). `sampling_profiler` (Windows x64 only, dbghelp) profiles the benchmark program from outside, with inline frames, and writes a report plus folded stacks; `allocation_profile` counts allocations per command kind exactly, by replacing global `operator new`. Build them in a Release configuration with symbols added (`build/profile`, flags in the README), never in Debug. The baseline's profile is `benchmarks/results/2026-10-26-profile/` and its write-up, with the bottleneck hypotheses, is `docs/PROFILING.md`; `docs/OPTIMIZATION-EXPERIMENTS.md` designs one experiment per candidate change (bottleneck, hypothesis, predicted workloads, risks, readability cost, success measurement) and the shared measurement protocol, and records which were run and what they showed; `docs/OPTIMIZATION.md` is the report on them, with the final code's profile in `benchmarks/results/2026-10-26-final-profile/` (its README has the commands: since the node pool, `~OrderBook` is inlined into `runCore`, so profiles of current code need two more `--drop`s to exclude destroying the book). Shares in a report come from one run; identical-code folding can mislabel a frame (the results' event-vector destructor shows as `~vector<BenchmarkCommand>`), and `ntdll` internals resolve to the nearest export.
