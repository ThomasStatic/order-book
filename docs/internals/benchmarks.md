# Benchmarks and profiling

Implementation notes. Methodology is in [`../../benchmarks/README.md`](../../benchmarks/README.md).

- **Benchmarks** (`benchmarks/`, library `order_book_benchmarking`, which links `order_book_network`, `order_book_reference`, and `order_book_process_testing`; CLI `order_book_benchmarks`; methodology in `benchmarks/README.md`). Five built-in v1 workloads (`small-book`, `deep-book`, `matching-heavy`, `cancellation-heavy`, `mostly-resting`; `builtInWorkloads()`, compact `BenchmarkCommand`s through `submitOrder(Order)`, their commands unchanged since generator version 2, which `testV1WorkloadsUnchanged` checks through `workloadFingerprintV2`) and six behavior workloads (`quote-refresh`, `pending-stops`, `self-trade`, `immediate`, `matching-heavy-request`, `matching-heavy-owned`; `behaviorWorkloads()`, `WorkloadFamily::BEHAVIOR`, `BehaviorMix`, `BehaviorCommand`s through `submitOrder(OrderRequest)`/`replaceOrder`/`cancelOrder`, generated in `behavior_workload.cpp` on `ReferenceBook`, held in shape by floors and caps on resting orders and pending stops; the two matching-heavy ones replay matching-heavy's exact stream, owner 0 or owner = order ID; `replay` renders them as v2 rows), and three sizes (smoke 10k, standard 100k, extended 1M timed commands). `generateWorkload` builds the whole workload (preload, timed commands, predicted `WorkloadOutcome`) before anything is timed, from its own `WorkloadModel`, never an `OrderBook`, with the same RNG rules as the randomized harness (raw `mt19937_64`, own `below`, one draw per statement). `benchmark_harness_tests` pins each workload's fingerprint at the smoke size (now under `workloadGeneratorVersion` 3), so any change to what is generated must bump `workloadGeneratorVersion` and re-pin. `WorkloadOutcome` gained `replaces`, `expirations`, `preventions`, `stopsTriggered`, and `finalPendingStops`, appended to the CSV and JSON. The mixes are tuned so each book keeps its shape from 10k to 1M commands (see the comment above `makeWorkloads`), so re-check final orders and levels at every size after changing one. Each run reserves `expectedBookSize`, a `BookCapacity` of the model's peaks on `Workload::peak` (outside the fingerprint, recorded as `reserved_orders`, `reserved_stops`, and `reserved_levels`), plus one level for a replace in flight, before the untimed preload, and any nonzero `capacityGrowths` fails the run (`requireNoGrowth`). `ReferenceBook` and `WorkloadModel` track those peaks at each insertion, so what a cascade holds only inside a command counts too. `preloadBook`, `recordFinalBook`, and `describeOutcome` are exposed for the latency harness. `runOnce` times only the timed commands: `core` calls `submitOrder`/`cancelOrder` directly, and `replay` parses in-memory CSV through `ReplayEngine` with validation `NONE`. It throws if the book's outcome differs from the prediction. The program exits 3 in a build that is not optimized (no `NDEBUG`, automatic invariant checks, ASan, or UBSan, which CMake reports through `ORDER_BOOK_UNDEFINED_SANITIZER` since GCC defines no macro for it) unless given `--allow-unoptimized`, which the CTest smoke run passes. The recorded baselines are in `docs/BENCHMARKS.md`: v2.0.0's (all eleven workloads) from `benchmarks/results/2026-10-29-order-behaviors/`, which also holds P3's paired regression check against v1.0.0 (`f22a8f4`; written up in `docs/OPTIMIZATION.md`, "The v2.0.0 regression check"), and the first, kept as history, from `benchmarks/results/2026-10-25-baseline/` (each `summarize.py` recomputes its tables). `ResultRecorder`'s per-trade path is inline in its header for that check's sake (a call per trade across translation units cost about 8%), and `ReplayEngine::run` reserves one event per record. `order_book_benchmarks` reports per-run throughput only, so never derive latency from it. Latency numbers come only from the latency harness, under the claims rule in `docs/LATENCY.md`, each with its interval and run record. Never say "low latency" and never compare with production exchanges. `docs/images/make_figures.py` draws `benchmark-baseline.svg`, `benchmark-v2-baseline.svg`, `optimization.svg`, and `replay-terminal.svg` from those results, `docs/OPTIMIZATION.md`'s tables, and `tests/replay/expected/`, so rerun it after changing any of them; the other four are hand-edited SVG whose books and trades were checked against the CLI, so recheck them if a matching rule changes.
- **Component benchmarks** (`component_benchmark.hpp`, in `order_book_benchmarking`; program `order_book_component_benchmarks`, which takes `thread_setup` from `order_book_latency`, so its pins mean what the latency harness's do). `runCapacityGroup` times `grow-to` (the one `emplace` that grows an index filled to exactly three quarters, so an entry of `orderCounts` must be three quarters of a power of two or it throws), `reserve-orders`, and `new-level-near` and `new-level-far` on `ladderBook` (one order per level per side, two ticks apart, so odd ticks are gaps). A new-level pass rests a batch of one in twenty levels, at most 100, and cancels them untimed, so the book keeps its shape. `runControlGroup` runs `cpu-loop` (xorshift, no load or store) and `memory-walk` (a Sattolo cycle of cache lines, so each step is one load the prefetcher can't predict, in `walkBytes` sizes for L2, the shared L3, and past it) on every thread at once through a latch, with `setUpThread` pinning each first. `ComponentResult::operations` counts across passes, while the CSV's `passes` column keeps what the ticket fixed. `runLogGroup` and `runEntryGroup` run on real workload commands through `workloadRecords`, which also feeds `renderCommandLog` and the `replay-log` kind. `runEntryGroup` adds `symbol-lookup`, a hit in an `InstrumentDirectory` of 8, 64, and 512 instruments. The `shard` kind runs `ShardRun`, which holds one `Shard` on the calling thread, with one book per workload warmed to that workload's peak and preloaded through `Shard::process`, untimed. `instrumentWorkloads` gives each instrument its own unchanged `generateWorkload` stream, seeded from the run's seed plus its index, so instrument 0 is exactly today's stream and `workloadGeneratorVersion` stays 3. An interleaver seeded from the run's seed shares the commands out, each instrument keeping its own order, so each book's prediction holds, and `totalOutcome` sums them to the run's. A run's `instruments` is in the CSV, after `final_pending_stops`, and the JSON. `countCommand` counts from a command's events alone, in the timed region, as `core` counts from its results. The `queue` kind runs `QueueRun`: a real matching thread builds and preloads a `ShardRun`, so it owns the books, and destroys them, while the calling thread is its one producer, sending batches of up to 64 and draining responses at once. Events are counted at the producer and final shapes read on the matching thread after its stop. The matching thread itself is `MatchingThread`, which `QueueRun` and `GatewayRun` share. Everything that can fail before its loop runs, `MatchingLoop`'s own construction included, happens while its constructor is waiting and is rethrown there, so a producer never waits on a thread that didn't start. The loop always sends `SHARD_STOPPED`, and `join` rethrows what the thread found after that. `--tamper-prediction` adds a trade to a prediction, and `benchmark_queue_tampered` requires exit 1 with that message. `GatewayRun` puts a gateway thread with a `PollSocketSet` on port 0 in front of a `MatchingThread`, and builds every command frame before the timed region, counting each command there, since every frame built is sent or `run` throws. Waiting for each `Welcome`, `run`, and `finish` all give up if the gateway thread has failed, and `stopThreads` then sends the shard's stop marker itself, since with that thread gone this one may write its ring. `benchmark_gateway_tests`, `benchmark_gateway_smoke`, and `benchmark_gateway_tampered` are `threaded`. **Durability** (`benchmark_log.hpp`): `RunSettings::durability` is `RunDurability::NONE` (a benchmark-only shard with no log, the default), `PROCESS`, or `MACHINE`, for `queue` and `gateway`, and `--durability` and `--log-dir` set it and the parent directory, which `defaultLogParent` makes the system's temporary one. A `LogRing` (log ring, writer's doorbell, durable position) is built before the `MatchingThread`, whose `MatchingLoop` takes its `LogLink`, so every take reaches the log ring before it runs, as in the engine. `ShardRun::firstTimedPosition` is the shard's position once the preload has run through `Shard::process`, and a `RunLog` then starts shard 0's real `LogWriter` at that position on its own thread, over a `FileLogStorage` in a fresh directory from `freshLogDirectory`, with a `Housekeeping` whose `pass` makes the next file on the constructing thread before its own thread starts, so a run shorter than two files makes none while timed. `QueueRun` holds responses as a gateway thread does, stopping at a `HOLD` marker the durable position hasn't reached and counting it in `holdsWaited`, and `GatewayRun` gives its `ShardLink` the durable position. A `RunLog` that can't be made stops the matching thread before the error escapes. `finish` joins the matching thread, whose stop sent its writer the STOP, and then `RunLog::finish`, so a failure on either still finishes the log; the log's end and what it must hold are taken while the books exist, since the matching thread destroys them, and `check` requires the log to hold every timed command and nothing else. `RunLog`'s destructor deletes the directory once its files are closed. The `engine` kind runs at `PROCESS` always: `EngineOptions` carries a durability that can't be `NONE` and a log parent, and `EngineProcess` passes `--log-dir` with a fresh directory and `--durability`, removing it with the instrument list. CSV and JSON gained `durability`, after `shards`. `benchmark_queue_tests` and `benchmark_gateway_tests` run each kind at both levels against the prediction, show the directory deleted, the queue's responses held, a shard with no log never held, and a log directory that can't be made failing the run; `benchmark_queue_smoke_machine` and `benchmark_gateway_smoke_process` run the program with logs under the build directory. Not built: the zero-filled log files #33's durability sweep and V1's 10k/s row compare with extended ones, and V1's raw write-through loop. The gateway's client is `LoopbackClients`, which the `engine` kind and the round-trip interval share: frames built before the timed region with `commandFrames`, each correlation its index, one connection per book through `connectLoopback`, which waits for the `Welcome`, and counts from event frames alone, so any other frame, a `Refused` included, fails the run. `preload` sends each book's preload the same way, untimed, and `take` hands a connection to a client of its own. The `engine` kind runs `EngineRun`: an `EngineProcess` (`engine_process.hpp`) writes an instrument list to a temporary file, one book per workload as `instrumentSymbol(i)` (B0, B1, ...) on shard i modulo `--shards`, each at `declaredCapacity`, its `expectedBookSize` with every part at least 1, since the list takes no 0, starts the engine through `ChildProcess` with `--listen 127.0.0.1:0 --stop-on-stdin-close` and a fresh `--log-dir` at `--durability process`, and reads the port from the `listening` line. `stop` closes its stdin, requires exit 0, and reads the stop report through `parseStopReport`, failing a book whose capacity isn't the one declared or that grew. The engine reports no book's shape, so `EngineRun::outcomes` takes the final orders, levels, and pending stops from the prediction, and every counter from the frames. The engine path defaults to `engineBesideProgram(argv[0])`, and CMake builds the engine with the program. `benchmark_engine_tests` takes the engine's path, and with `benchmark_engine_smoke` (on two shards) and `benchmark_engine_tampered` it is `threaded`. CSV and JSON gained `shards`, 1 for every kind but `engine`. `compare_ab.py --exp-kind` reads one kind against another under the same interleaving, a kind's A/A floor comes first, and any option it doesn't know goes to both binaries, such as `--instruments 8`. `runEntryGroup` adds `check-entry`, and `runWireGroup` runs `frame-decode` and `event-encode`, on the same records. `event-encode`'s events come from running them on a book that starts empty, so a workload that needs a preload shows more rejections than it would. `runImageGroup` (`--group images`) times a book image's costs by size and by how scattered the book's nodes are, since the cost is chasing them, not moving bytes: books in `deep-book`'s shape at 1k, 10k, 100k, and 1M orders (its config with `initialOrders` set, over its 2,000 levels or half as many as orders if fewer) and in `mostly-resting`'s at 1M, each in three states: `restored` (the preloaded book rebuilt from its own image, so compact, as a worker starts), `aged` (after the workload's own 1M timed commands, so its size moves as the workload's does, which the row's order count reports), and `shuffled` (its preload rested in a random order, the worst case). Each runs `write-image`, `restore`, `check-invariants`, and `image-proof` (restore, then `writeImage` again and compare, the proof a checkpoint must pass), one per pass, five passes, with a 64 MiB walk evicting the caches before each; a restored book is destroyed outside the timer. #33 asked for `aged` after the workload's own 1M commands at each size, which the workloads don't hold to a fixed size; the order column says what each aged book held. `runDurabilityGroup` (`--group durability`, D4b) works in a fresh directory under `--log-dir` (default the system's temporary directory), which should be on the log's drive, through `FileLogStorage`, removing it after: `publish-checkpoint` times one `publishCheckpoint` (`.tmp`, write, flush, read back, rename, which flushes the directory) of `deep-book`'s preloaded book at 1k, 10k, 100k, and 1M orders, five passes, each removed untimed; `roll-pass` writes real closed log files through `Housekeeping` and a `LogWriter` at `process`, as many records as a default 256 MiB file holds (6.7M) shared by 8 books of `matching-heavy-request` on one shard, each with a stream of its own written in turn so only one book's commands are in memory, and the next file made ahead, so the first is closed; then each of three passes makes a `ShardRoller` untimed, which reads each book's empty checkpoint at 0, and times `roll`: every book restored, replayed, proved, and published at the file's end, so `ns_per_op` is per command, and the row's orders and levels are what the books held. The rolled checkpoints are removed untimed, so each pass starts from the empty ones. The log is two such files, so the second isn't closed when the first is rolled. `recover` (D5) then rolls the first untimed and times, each pass, a start's `surveyLog` and `recoverShard` on a shard built untimed: every book restored from its checkpoint at the first file's end, and the second file replayed, so `ns_per_op` is per command replayed. At `--size smoke` it publishes one 200-order book once and rolls 2,000 records over 2 books once.
- **Nightly** (`.github/workflows/nightly.yml`). Scheduled and manual, never on a push or pull request. It runs `randomized_tests --explore SEEDS --profile all` and `engine_randomized_tests --explore SEEDS` with invariant checks on, on Clang ASan+UBSan, GCC Release, and MSVC Release, and uploads a failure's saved stream. Later slices add real threads at 100 times the size.
- **Linux sanity** (`.github/workflows/linux-sanity.yml`). Manual only. v2.1.0 records no Linux numbers: spec #58 dropped the native Linux baseline on 2026-11-04, and this workflow stands in for it, for large effects only. On an `ubuntu-24.04` GCC Release runner and a `windows-2022` MSVC Release runner beside it, it runs `order_book_latency_benchmarks` on `small-book`, 9 runs each: durable wait closed-loop at `machine` and at `process`, durable wait on the timetable at `machine`, and the round trip at both levels (`--discard-seconds 0`, since a fast closed-loop run can end inside the default discard). Each report goes in the run's summary, and the results and the runner's description (`machine.txt`, passed as `--machine-record`) are uploaded. Read it ratio against ratio: `machine` over `process` on Linux beside the same on Windows, since a runner's disk is not the reference machine's. The harness still marks closed-loop rows `quotable: yes` (closed-loop service time may run unpinned, and it can't tell a shared runner from the reference machine), so it is `docs/LATENCY.md`'s claims rule that refuses quoting any of them. The first run, 41944201633, found `machine` durable wait about 41 times `process` at p50 on Linux and about 80 times on Windows, so `O_DSYNC` showed no gross problem. V1 adds its raw write-through loop and its idle-connection row (`poll` against epoll) here.
- **Profiling** (`benchmarks/profiling/`, option `ORDER_BOOK_BUILD_PROFILING`, which needs the benchmarks; README there). `sampling_profiler` (Windows x64 only, dbghelp) profiles the benchmark program from outside, with inline frames, and writes a report plus folded stacks; `allocation_profile` counts allocations per command kind exactly, by replacing global `operator new`. Build them in a Release configuration with symbols added (`build/profile`, flags in the README), never in Debug. The baseline's profile is `benchmarks/results/2026-10-26-profile/` and its write-up, with the bottleneck hypotheses, is `docs/PROFILING.md`; `docs/OPTIMIZATION-EXPERIMENTS.md` designs one experiment per candidate change (bottleneck, hypothesis, predicted workloads, risks, readability cost, success measurement) and the shared measurement protocol, and records which were run and what they showed; `docs/OPTIMIZATION.md` is the report on them, with the final code's profile in `benchmarks/results/2026-10-26-final-profile/` (its README has the commands: since the node pool, `~OrderBook` is inlined into `runCore`, so profiles of current code need two more `--drop`s to exclude destroying the book). Shares in a report come from one run; identical-code folding can mislabel a frame (the results' event-vector destructor shows as `~vector<BenchmarkCommand>`), and `ntdll` internals resolve to the nearest export.
