# Benchmarks and profiling

Implementation notes. Methodology is in [`../../benchmarks/README.md`](../../benchmarks/README.md).

- **Benchmarks** (`benchmarks/`, library `order_book_benchmarking`, which links `order_book_replay` and `order_book_reference`; CLI `order_book_benchmarks`; methodology in `benchmarks/README.md`). Five built-in v1 workloads (`small-book`, `deep-book`, `matching-heavy`, `cancellation-heavy`, `mostly-resting`; `builtInWorkloads()`, compact `BenchmarkCommand`s through `submitOrder(Order)`, their commands unchanged since generator version 2, which `testV1WorkloadsUnchanged` checks through `workloadFingerprintV2`) and six behavior workloads (`quote-refresh`, `pending-stops`, `self-trade`, `immediate`, `matching-heavy-request`, `matching-heavy-owned`; `behaviorWorkloads()`, `WorkloadFamily::BEHAVIOR`, `BehaviorMix`, `BehaviorCommand`s through `submitOrder(OrderRequest)`/`replaceOrder`/`cancelOrder`, generated in `behavior_workload.cpp` on `ReferenceBook`, held in shape by floors and caps on resting orders and pending stops; the two matching-heavy ones replay matching-heavy's exact stream, owner 0 or owner = order ID; `replay` renders them as v2 rows), and three sizes (smoke 10k, standard 100k, extended 1M timed commands). `generateWorkload` builds the whole workload (preload, timed commands, predicted `WorkloadOutcome`) before anything is timed, from its own `WorkloadModel`, never an `OrderBook`, with the same RNG rules as the randomized harness (raw `mt19937_64`, own `below`, one draw per statement). `benchmark_harness_tests` pins each workload's fingerprint at the smoke size (now under `workloadGeneratorVersion` 3), so any change to what is generated must bump `workloadGeneratorVersion` and re-pin. `WorkloadOutcome` gained `replaces`, `expirations`, `preventions`, `stopsTriggered`, and `finalPendingStops`, appended to the CSV and JSON. The mixes are tuned so each book keeps its shape from 10k to 1M commands (see the comment above `makeWorkloads`), so re-check final orders and levels at every size after changing one. Each run reserves `expectedBookSize`, a `BookCapacity` of the model's peaks on `Workload::peak` (outside the fingerprint, recorded as `reserved_orders`, `reserved_stops`, and `reserved_levels`), plus one level for a replace in flight, before the untimed preload, and any nonzero `capacityGrowths` fails the run (`requireNoGrowth`). `ReferenceBook` and `WorkloadModel` track those peaks at each insertion, so what a cascade holds only inside a command counts too. `preloadBook`, `recordFinalBook`, and `describeOutcome` are exposed for the latency harness. `runOnce` times only the timed commands: `core` calls `submitOrder`/`cancelOrder` directly, and `replay` parses in-memory CSV through `ReplayEngine` with validation `NONE`. It throws if the book's outcome differs from the prediction. The program exits 3 in a build that is not optimized (no `NDEBUG`, automatic invariant checks, ASan, or UBSan, which CMake reports through `ORDER_BOOK_UNDEFINED_SANITIZER` since GCC defines no macro for it) unless given `--allow-unoptimized`, which the CTest smoke run passes. The recorded baselines are in `docs/BENCHMARKS.md`: v2.0.0's (all eleven workloads) from `benchmarks/results/2026-10-29-order-behaviors/`, which also holds P3's paired regression check against v1.0.0 (`f22a8f4`; written up in `docs/OPTIMIZATION.md`, "The v2.0.0 regression check"), and the first, kept as history, from `benchmarks/results/2026-10-25-baseline/` (each `summarize.py` recomputes its tables). `ResultRecorder`'s per-trade path is inline in its header for that check's sake (a call per trade across translation units cost about 8%), and `ReplayEngine::run` reserves one event per record. `order_book_benchmarks` reports per-run throughput only, so never derive latency from it. Latency numbers come only from the latency harness, under the claims rule in `docs/LATENCY.md`, each with its interval and run record. Never say "low latency" and never compare with production exchanges. `docs/images/make_figures.py` draws `benchmark-baseline.svg`, `benchmark-v2-baseline.svg`, `optimization.svg`, and `replay-terminal.svg` from those results, `docs/OPTIMIZATION.md`'s tables, and `tests/replay/expected/`, so rerun it after changing any of them; the other four are hand-edited SVG whose books and trades were checked against the CLI, so recheck them if a matching rule changes.
- **Component benchmarks** (`component_benchmark.hpp`, in `order_book_benchmarking`; program `order_book_component_benchmarks`, which takes `thread_setup` from `order_book_latency`, so its pins mean what the latency harness's do). `runCapacityGroup` times `grow-to` (the one `emplace` that grows an index filled to exactly three quarters, so an entry of `orderCounts` must be three quarters of a power of two or it throws), `reserve-orders`, and `new-level-near` and `new-level-far` on `ladderBook` (one order per level per side, two ticks apart, so odd ticks are gaps). A new-level pass rests a batch of one in twenty levels, at most 100, and cancels them untimed, so the book keeps its shape. `runControlGroup` runs `cpu-loop` (xorshift, no load or store) and `memory-walk` (a Sattolo cycle of cache lines, so each step is one load the prefetcher can't predict, in `walkBytes` sizes for L2, the shared L3, and past it) on every thread at once through a latch, with `setUpThread` pinning each first. `ComponentResult::operations` counts across passes, while the CSV's `passes` column keeps what the ticket fixed. `runLogGroup` and `runEntryGroup` run on real workload commands through `workloadRecords`, which also feeds `renderCommandLog` and the `replay-log` kind. `runEntryGroup` adds `symbol-lookup`, a hit in an `InstrumentDirectory` of 8, 64, and 512 instruments. The `shard` kind runs `ShardRun`, which holds one `Shard` on the calling thread, with one book per workload warmed to that workload's peak and preloaded through `Shard::process`, untimed. `instrumentWorkloads` gives each instrument its own unchanged `generateWorkload` stream, seeded from the run's seed plus its index, so instrument 0 is exactly today's stream and `workloadGeneratorVersion` stays 3. A uniform interleaver shares the commands out, each instrument keeping its own order, so each book's prediction holds, and `totalOutcome` sums them to the run's. `countCommand` counts from a command's events alone, in the timed region, as `core` counts from its results. `compare_ab.py --exp-kind` reads one kind against another under the same interleaving, and a kind's A/A floor comes first. `runEntryGroup` adds `check-entry`, and `runWireGroup` runs `frame-decode` and `event-encode`, on the same records. `event-encode`'s events come from running them on a book that starts empty, so a workload that needs a preload shows more rejections than it would. Later slices add the images and durability groups.
- **Nightly** (`.github/workflows/nightly.yml`). Scheduled and manual, never on a push or pull request. It runs `randomized_tests --explore SEEDS --profile all` with invariant checks on, on Clang ASan+UBSan, GCC Release, and MSVC Release, and uploads a failure's saved stream. Later slices add real threads at 100 times the size.
- **Profiling** (`benchmarks/profiling/`, option `ORDER_BOOK_BUILD_PROFILING`, which needs the benchmarks; README there). `sampling_profiler` (Windows x64 only, dbghelp) profiles the benchmark program from outside, with inline frames, and writes a report plus folded stacks; `allocation_profile` counts allocations per command kind exactly, by replacing global `operator new`. Build them in a Release configuration with symbols added (`build/profile`, flags in the README), never in Debug. The baseline's profile is `benchmarks/results/2026-10-26-profile/` and its write-up, with the bottleneck hypotheses, is `docs/PROFILING.md`; `docs/OPTIMIZATION-EXPERIMENTS.md` designs one experiment per candidate change (bottleneck, hypothesis, predicted workloads, risks, readability cost, success measurement) and the shared measurement protocol, and records which were run and what they showed; `docs/OPTIMIZATION.md` is the report on them, with the final code's profile in `benchmarks/results/2026-10-26-final-profile/` (its README has the commands: since the node pool, `~OrderBook` is inlined into `runCore`, so profiles of current code need two more `--drop`s to exclude destroying the book). Shares in a report come from one run; identical-code folding can mislabel a frame (the results' event-vector destructor shows as `~vector<BenchmarkCommand>`), and `ntdll` internals resolve to the nearest export.
