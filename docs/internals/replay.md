# Replay format, parser, and engine

Implementation notes. The format itself is specified in [`../replay-format.md`](../replay-format.md).

- **Replay format** (`docs/replay-format.md`, ADR 0005): a CSV of `ADD`/`CANCEL` commands in six columns (v1), or `ADD`/`CANCEL`/`REPLACE` in twelve (v2: `order_type`, `time_in_force`, `stop_price`, `post_only`, `owner`, `self_trade_prevention` appended), the layout named by an exact header (`headerFormat`, `ReplayFormat`; `ReplayReader::format()`; three-argument `parseRow(row, format, previous)`, the two-argument one meaning v1). Every row-decidable request check is a parse error (presence rules, keywords, zero, and `INVALID_COMBINATION` for MARKET/STOP + GTC at `time_in_force` and post-only on a non-GTC-LIMIT `ADD` at `post_only`), so a parsed `ADD` is always a well-formed `OrderRequest`; `ParseErrorCode` appends five codes and, like replay's `Command` (with `ReplaceCommand` appended), is an open set. `ADD` always runs `submitOrder(OrderRequest)`, `REPLACE` runs `replaceOrder` (a `ReplaceRejected` is a book refusal), `CANCEL` may name a pending stop, and a cascade's events are tagged with its command's line. `ReplayStatistics` appends the replace counts and `selfTradesPrevented`/`ordersExpired`/`stopsTriggered`, counted from events, and `ReplayResult` gains `pendingStops` and `lastTradePrice`; the statistics always print every line, and `formatFinalBook(result)` (what `--book` prints) adds `last trade price: <ticks>|none`. `replay_engine_tests` also checks each sample's last trade price, that every v1 sample rewritten as v2 replays the same, and that the book accepts every parsed `ADD`; `replay_parser_tests` checks the rewrite parses the same. The original format, for v1: a six-column CSV of `ADD`/`CANCEL` commands for replaying a session. Parser, replay engine, and book are separate layers, and the book knows nothing about CSV. `ADD` maps to `submitOrder` (the request overload), never `addOrder`. A well-formed row the book refuses is a rejection event, and the replay continues. Any parse error stops the replay (exit 1) with no rollback. Numbers are digits only, leading zeros ignored (`000123` is 123), zero refused in every column. The parser (`replay_parser.hpp`, namespace `order_book::replay`) is its own library, `order_book_replay`, so don't add it to `order_book`; it never sees an `OrderBook` or opens a file. `parseRow(CsvRow, previousSequence)` is pure and returns a `ReplayRecord` or the first `ParseError` (line, `ParseErrorCode`, column, value, message) in the spec's checking order; `ReplayReader` feeds it from a `std::istream` (open files binary, or CRs vanish on Windows) and is sticky after an error or the end. It reads the stream in chunks (`readsome`, then `peek` to fetch more, so bytes delivered before a stream failure are kept), splits each line into one reused `CsvRow` with `splitRecordInto`, and so allocates nothing per record; it may read up to a chunk ahead of what it has returned, so give it a stream of its own. Its optional chunk size exists for tests, which read every input with tiny chunks to put boundaries inside records. The engine (`replay_engine.hpp`, same library and namespace, spec in `docs/replay-format.md`) reads a file into the records before its first error (`readReplayFile` → `ReplayInput`), then `ReplayEngine::run(records, book, options)` dispatches them in order and returns a `ReplayResult` (line-tagged events, `ReplayStatistics`, full-depth `BookSnapshot`) or a `ReplayError`, so a parse error still runs the prefix before it. `ReplayOptions::invariantValidation` (`NONE`/`FINAL`, the default/`PER_COMMAND`) is its own `checkInvariants` call, separate from the book's aborting boundary; tests that run a command on a deliberately broken book therefore run only when `invariantChecksAfterCommands` is false. Printing is `replay_summary.hpp` (`formatReplayStatistics`, `formatFinalBook`, and `formatReplaySummary`, the two together), kept locale-free and in fixed order so output is byte-identical everywhere; the CLI sets stdout and stderr to binary on Windows for the same reason. `tests/replay/valid/` and `tests/replay/malformed/` hold the agreed samples, and `tests/replay/README.md` lists each one's expected events or line/column/rule. `replay_parser_tests` (`tests/replay_parser_test.cpp`) reads every sample and fails on one it has no expectation for. `replay_engine_tests` (`tests/replay_engine_test.cpp`) replays every sample too, failing on any file in `valid/` it doesn't list (`.csv` or not), but it gives a malformed file it doesn't list the usual layout's expectation (stops at line 4 after two commands), so it checks that file wrongly rather than failing. A new valid sample needs entries in both tests and in the `replay_cli_*` `foreach` list in `CMakeLists.txt`, plus an `expected/<name>.stdout` (the full `--events --book` output); a new malformed sample needs a parser-test entry, and an engine-test entry unless it fits the usual layout. `tests/replay/expected/` holds the CLI's exact stdout/stderr per case, compared by `tests/replay/check_cli_output.cmake`; a new CLI case (an option, a usage error, help) is one `order_book_add_replay_cli_test` call in `CMakeLists.txt` (any CLI arguments, exit status, and optional expected stdout/stderr; a stream without one must be empty), and its expected files are written by hand from the README's events, not captured from the CLI. Samples and expected files are byte-exact (`-text`), so don't let an editor normalize them.
