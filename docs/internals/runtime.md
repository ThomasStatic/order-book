# Engine runtime

Library `order_book_runtime` (namespace `order_book::runtime`, headers in `include/order_book/runtime/`, sources in `src/runtime/`), linking `order_book_replay`. It is not public API: the engine's contract to the outside is its formats, its wire protocol, and its programs' flags and output. Terms are in `GLOSSARY.md`, and the decisions in ADRs 0007 and 0008.

- **`parseInstrumentList(text, shardCount)`** (`instruments.hpp`). The exact header `symbol,shard,orders,stops,levels`, then five fields per row, to the replay format's strictness: LF or CRLF, a last line with no ending, no quoting, blank lines, or comments, digits only, leading zeros ignored. It reports the first problem, with a line, column, and `InstrumentListErrorCode`, in the order record framing, `symbol`, duplicate, `shard`, `orders`, `stops`, `levels`. An empty field means the default. `shard` may be 0, unlike any replay column, and at or past `shardCount` is `SHARD_OUT_OF_RANGE`, a start error. The capacity columns refuse 0. Every number stops at `maxInstrumentListNumber`, 2^32 - 1, so a list means the same on any platform. The codes are the list's own, not `ParseErrorCode`, because `ParseErrorCode` is the replay format's and the list adds no column to it. `formatInstrumentListError` gives the start error's `<path>:<line>: <column>: <message>`, leaving out the column when there is none.
- **Placement.** `symbolHash` is 64-bit FNV-1a over the 8 stored bytes, padding included, and `hashedShard` takes it modulo the shard count. A log records the placement it was written under, so the hash is a format in all but name, never `std::hash`: `instrument_directory_tests` pins sample placements worked out apart from this code. A placement depends on nothing but the symbol and the shard count, or a pin, so adding instruments moves nothing while the count stays the same.
- **`InstrumentDirectory`.** Built once, then immutable, so any thread reads it without locks. It holds two sorted arrays, `bySymbol` for `find` (a bisection, returning a `BookLocation` of shard and slot) and `bySlot` for `onShard`. A shard's slots are in symbol order, so a list's line order means nothing. Slots are dense and private: no format holds one, and none is ever sent. The constructor throws `std::invalid_argument` for what the parser refuses, so a directory built any other way is just as sound. A shard may hold no instruments.
- **`BookSet`** (`book_set.hpp`). One shard's books by slot. Its owning thread is the one that builds it, and it never copies or moves, so "a book is touched only by its owning thread, from when it is built until destroyed" has one thing to check. `execute(slot, command)` and its `out` overload go through `replay::executeCommand`, the one place a command becomes a book call. `book(slot)` is read-only. Both abort in checked builds (`invariantChecksAfterCommands`) when called from another thread, printing `order book runtime: BookSet::<call> called off its owning thread: shard=<n> slot=<n>`, which `book_set_thread_execute` and `book_set_thread_book` match. The constructor warms each book with `reserve(capacityOf(instrument, defaults))`, where `defaultBookCapacity` is the 4,096 orders, 1,024 stops, and 256 levels per side of `--capacity-orders`, `--capacity-stops`, and `--capacity-levels`.
- **`Shard`** (`shard.hpp`). A plain single-threaded object, with the matching thread to come a thin loop around it. `process(command, slot)` takes no origin, so replay and tests call exactly what the matching thread will, and leaves its events in one `CommandResult`, reserved at 512 trades and 1,024 events by the constructor. Anything larger still comes back whole. The position counts every command taken, a rejected one included. Checked builds record the slot and position before running, in `lastProgress()`, for the abort handler to come, and other builds pay nothing. `checkInvariants` runs every book's own check, then that each slot maps back through the directory, then that the next log position is the first plus the commands taken, returning a `ShardViolation`. The durable position joins it with the log writer. `shard_invariant_tests` breaks each part through `OrderBookTestAccess`, which `Shard` befriends too. `matching_path_allocation_tests` holds a warm shard to exactly zero heap calls on all eleven workloads, counted per thread in a replaced `operator new`, along with the `out` overloads for every type and time in force, a cascade, `replaceOrder`'s paths, in place, moved back, crossing, and post-only expiring, `cancelOrder`, and `encodeLogRecord`. It first shows the count can move, on a book past its capacity.
- **The interleaver** lives apart, in `order_book_reference` (`tests/reference/interleaver.hpp`), so that tests and benchmarks share one: see [`randomized-tests.md`](randomized-tests.md).
