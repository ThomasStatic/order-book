# Engine runtime

Library `order_book_runtime` (namespace `order_book::runtime`, headers in `include/order_book/runtime/`, sources in `src/runtime/`), linking `order_book_replay`. It is not public API: the engine's contract to the outside is its formats, its wire protocol, and its programs' flags and output. Terms are in `GLOSSARY.md`, and the decisions in ADRs 0007, 0008, 0011, and 0013.

- **`parseInstrumentList(text, shardCount)`** (`instruments.hpp`). The exact header `symbol,shard,orders,stops,levels`, then five fields per row, to the replay format's strictness: LF or CRLF, a last line with no ending, no quoting, blank lines, or comments, digits only, leading zeros ignored. It reports the first problem, with a line, column, and `InstrumentListErrorCode`, in the order record framing, `symbol`, duplicate, `shard`, `orders`, `stops`, `levels`. An empty field means the default. `shard` may be 0, unlike any replay column, and at or past `shardCount` is `SHARD_OUT_OF_RANGE`, a start error. The capacity columns refuse 0. Every number stops at `maxInstrumentListNumber`, 2^32 - 1, so a list means the same on any platform. The codes are the list's own, not `ParseErrorCode`, because `ParseErrorCode` is the replay format's and the list adds no column to it. `formatInstrumentListError` gives the start error's `<path>:<line>: <column>: <message>`, leaving out the column when there is none.
- **Placement.** `symbolHash` is 64-bit FNV-1a over the 8 stored bytes, padding included, and `hashedShard` takes it modulo the shard count. A log records the placement it was written under, so the hash is a format in all but name, never `std::hash`: `instrument_directory_tests` pins sample placements worked out apart from this code. A placement depends on nothing but the symbol and the shard count, or a pin, so adding instruments moves nothing while the count stays the same.
- **`InstrumentDirectory`.** Built once, then immutable, so any thread reads it without locks. It holds two sorted arrays, `bySymbol` for `find` (a bisection, returning a `BookLocation` of shard and slot) and `bySlot` for `onShard`. A shard's slots are in symbol order, so a list's line order means nothing. Slots are dense and private: no format holds one, and none is ever sent. The constructor throws `std::invalid_argument` for what the parser refuses, so a directory built any other way is just as sound. A shard may hold no instruments.
- **`BookSet`** (`book_set.hpp`). One shard's books by slot. Its owning thread is the one that builds it, and it never copies or moves, so "a book is touched only by its owning thread, from when it is built until destroyed" has one thing to check. `execute(slot, command)` and its `out` overload go through `replay::executeCommand`, the one place a command becomes a book call. `book(slot)` is read-only, `reserve(slot, capacity)` warms a book further, which `Shard::reserve` forwards for recovery, and `replace(slot, book)` puts a book `OrderBook::restore` rebuilt on the owning thread in a slot, which `Shard::replaceBook` forwards and the engine harness's `RESTORE` lines use (recovery from checkpoints will too). All four abort in checked builds (`invariantChecksAfterCommands`) when called from another thread, printing `order book runtime: BookSet::<call> called off its owning thread: shard=<n> slot=<n>`, which `book_set_thread_execute` and `book_set_thread_book` match. The constructor warms each book with `reserve(capacityOf(instrument, defaults))`, where `defaultBookCapacity` is the 4,096 orders, 1,024 stops, and 256 levels per side of `--capacity-orders`, `--capacity-stops`, and `--capacity-levels`.
- **`Ring`** (`ring.hpp`; ADR 0011). One writer thread and one reader thread, lock-free, with a power-of-two capacity set when it is built, and the only allocation there. `tryPush` copies in and publishes with a release store; `drain(limit, take)` passes up to `limit` items to `take`, then gives their slots back together with one release store, so a batch costs one store. Indices count up for ever, so full and empty need no spare slot, and each side keeps its last view of the other's index on its own cache line, touching the shared line only when that runs out. That view is why a relaxed load of its own index and an acquire load of the other's are all it takes. `CommandElement` is 64 bytes and `ResponseRecord` 48, both trivially copyable, which the header proves at compile time. `ControlKind` sits outside `Command`, and the log accepts only a `Command`, so a stop marker can't reach the log, by type. A matching thread looks ahead before a take: `waiting(limit)` counts what is there and `peek(i)` sees each in place, `hasRoomFor(count)` asks the writer's side whether a whole take would fit, and `drainWhile` stops after the item its `take` returns false for, which is how a gateway thread stops at a hold marker. `ring_tests` runs a real second thread through two small rings, so both sides keep meeting full and empty, and it is labelled `threaded`.
- **`MatchingLoop`** (`matching_loop.hpp`). What a matching thread does, as a plain object, so `matching_path_allocation_tests` and `gateway_tests` can step `pass` on one thread and the real thread only calls `run`. A test's `waitInPlace` runs in place of the yield on a full response ring, so a command with more events than the ring has slots can finish on one thread, by playing the gateway from inside the wait. `pass` takes up to `takeBatch` (64) commands from each ring in turn, and that take order is the command sequence. Each command's events go back one record at a time on its own ring's responses, the last marked `LAST_EVENT`, and a full response ring waits in place, which can't deadlock while the producer keeps draining. `run` passes until every producer has sent a stop marker, then tells the log writer to finish, if there is one, and sends `SHARD_STOPPED` on every response ring. **With a log** (a `LogLink`, the log ring and the writer's doorbell), a take is no larger than the log ring, and before running it the matching thread counts its commands, waits until the log ring has room for all of them (a full ring makes it wait before a take, never mid-command), copies them in, rings the writer, and puts one `HOLD` marker on that ring's responses naming the position all of them need, `nextPosition()` plus their count. Every command of a take is on the log ring before any of it runs because the matching thread may then wait mid-take for room in a response ring that a gateway thread, held at that marker, is not draining: the writer can still make the whole take durable, so the gateway is released and the ring empties. Pushed only as each ran, the later commands of a take would wait behind a response ring the held gateway can't empty, and nothing would move. A take of stop markers alone pushes no marker. In the engine each gateway thread is a producer, with its own pair of rings to every shard, so M gateway threads on N shards make M×N pairs. An exception escaping a command aborts, naming the shard, symbol, position, and command through `fprintf` with no buffer of its own, since the failure may be that nothing can be allocated, though `fprintf` itself may use `malloc`, which `matching_abort_tests` doesn't fail: `submitOrder` can leave executions standing that replay wouldn't reproduce, so the engine declines to continue. `matching_abort_tests` fails allocations on a running book to show it.
- **`LogStorage`** (`log_storage.hpp`; ADR 0013). Every file the log touches goes through it, so the log writer and housekeeping are plain objects over it. `create(name, durability)` makes a new file and never opens an existing one, which throws `LogStorageError` of kind `EXISTS`, since old files' stale records still chain; a `LogFile` writes at an offset, flushes, extends to a size without writing it, cuts to a size, renames itself in its directory, and closes, and any failure throws `LogStorageError`. A rename never replaces another file (`EXISTS`), returns once the new name survives a machine crash, and from then the file's messages name it by its new name. `replace` is the same over a file of that name, in one step (`MOVEFILE_REPLACE_EXISTING` on Windows, plain `rename` on Linux), which only a placement change's rewrap uses; in memory it removes the old file as a remove does, and one an interrupted replace displaced is kept as `replacedOffDrive`, so a machine crash brings it back for certain, drawing nothing from the seed, and the name never holds neither file. `Durability`, the log ring's default of 65,536 records, and the log file's of 256 MiB are in `durability.hpp`, which `engine_settings.hpp` takes alone. `FileLogStorage` is the real one over one directory: `MACHINE` opens with `FILE_FLAG_WRITE_THROUGH` on Windows and `O_DSYNC` on Linux, so a write returns once the drive has it, and `PROCESS` with neither. A file is opened sharing delete on Windows, so `MoveFileExW` can rename it while its handle is open, with `MOVEFILE_WRITE_THROUGH`, which returns once the move is on the drive; Linux renames with `renameat2`'s `RENAME_NOREPLACE`, falling back to `rename` on a file system without it, then flushes the directory. Creating a file flushes nothing, since a lost temporary name loses nothing. Extending is `SetFileInformationByHandle`'s end of file on Windows, after which NTFS reads past the valid data as zeros and zero-fills only where a write lands, and `fallocate` on Linux, which allocates the space without writing it, so a full drive fails the extend while the current file still has room, and reads the unwritten extent as zeros; a file system without `fallocate` gets a sparse `ftruncate`, where a full drive fails a later write instead. NTFS allocates at the end-of-file change too; `log_writer_tests` reads both back as zeros on real files, which `TORN_TAIL` relies on. Everything that allocates comes before a file is made, so a failed create leaves nothing to refuse the next start on. `InMemoryLogStorage` holds files in memory under one lock, each shared with its open file so a remove leaves it writing where it was, and counts each file's writes, flushes, extends, renames, and cuts. A file's `bytes` end at its last write and its `size` is what it was extended to, so a 256 MiB file costs nothing, and `read` follows a file from an offset without its zeros. It fails a chosen create (`failCreateAfter`) or write (`failWriteAfter`), or every flush (`failFlushes`). A file's `closed` says the last handle to write, extend, or cut it closed it, or a crash did; reading leaves it as it was. It models both crashes, spec #58's seam 5. Each file holds what the OS has, `bytes` and `size`, which every read sees, and what the drive has, `onDrive` and `sizeOnDrive`: a write at `MACHINE` reaches both, as write-through does, one at `PROCESS` only the OS, and a flush takes the whole file, its size included, to the drive. The directory reaches the drive when a rename flushes it, as `makeLogFile`'s does: until then a created file's name (`nameOnDrive`) and a remove are the OS's alone, a removed file the drive still names being kept in `Contents::removed`. `crash(Crash::ENGINE, seed)` keeps what the OS has. `crash(Crash::MACHINE, seed)` keeps what the drive has, drops every file never renamed, and for each 4,096-byte page where the OS has other bytes, a seeded choice of all of them (one in two), none (one in four), or a torn write (one in four): of the 512-byte sectors that page holds, the first, at least one and never all, a sector being written whole or not at all. A size the OS has otherwise, an unflushed cut's or extend's, lands whole or not at all, and a cut writes nothing, so past it the drive's bytes stay unless its size lands. Each removed file the drive still names comes back, as the drive has it, or not. Both give every open file and the lock to the dead engine: the files are copied anew, so an old handle writes to nothing anyone sees, and a lock generation moves on, so a dead lock let go late frees nothing. `interruptWrites` makes everything from then until the crash reach the OS alone, whatever its durability: the write a machine crash meets on its way, which at `MACHINE` is the only place a crash can tear. `watch` calls a function after each create, write, extend, cut, flush, rename, and remove with the `Contents` of every file and every remove not yet on the drive, outside the lock, and `InMemoryLogStorage(contents)` holds just that, which is how `recovery_tests` crashes at every step. `logFileName(shard, position)` is #34's `log-<shard, 4 digits>-<first position, 20 digits>.oblog`, and `parseLogFileName` reads one back, `.tmp` included, while `namedLikeALogFile` says whether a name only looks like one. Recovery adds four calls. `names` lists every file, sorted, through `opendir` and `readdir` on Linux, not `directory_iterator`, since libstdc++'s builds its entries inside `noexcept` code, through the throwing overloads too, so an allocation failing there terminates, which `engine_start_allocation_tests`' backtrace showed on CI once the directory held a file; Windows keeps `directory_iterator`, which MSVC's library lets throw. `open` opens an existing file to read, cut, and flush, and a `LogFile`'s `read(offset, out)` returns what it copied, fewer bytes only at the end, with zeros past the written part up to `size()`; `create` opens for reading too, on both platforms. `lock` takes the directory's lock, held until the returned `StorageLock` is destroyed, and refuses with `Kind::LOCKED` while anyone else holds it: in `FileLogStorage` it is `engine.lock`, made empty if missing and never deleted, under `LockFileEx` on one byte past its end on Windows and `flock` on Linux, both per open file, so a second storage in the same process is refused as another process is, and both let go when the handle closes, which the system does however the process ends. Windows may let go of a killed process's lock a moment late, so `engine_end_to_end_tests` retries a restart refused on exactly that. In memory it is a flag the lock object clears. `log_writer_tests` runs one set of checks on both, real files included.
- **Log files and `Housekeeping`** (`log_files.hpp`; ADR 0013). A shard's log goes on files of at most `--log-file-size` bytes. `logFileShape` gives what stays the same from file to file, the header with the shard's placement and how many records fit after it, whole ones only, so a full file ends on a record and never reads as a torn tail; a size that can't hold the header and one record throws `std::invalid_argument`, and `leastLogFileBytes` is the largest shard's header and one record, which `runEngine` refuses below. Every file has the same number of records, so each file's first position is known before it is needed. `makeLogFile` makes one under its name plus `.tmp`: it writes the header, extends the file to its last record without writing it, so making a file doesn't compete with the log for the drive and nothing is written twice, flushes it, and renames it, so a log file anyone can see has its whole header; a failure removes both names, unless the name was already taken. `Housekeeping` is the engine's one housekeeping thread as a plain object, the way `LogWriter` is, with the real thread only calling `run`. `first(shard, position)` makes a shard's first file on the calling thread, which is the log writer's at start, so a failure refuses the start. From then it keeps one next file made for that shard: `pass` makes every next file wanted, one at a time, outside its lock, and `takeNext` hands it to the writer, which asks for the one after. The lock and condition variable are off every matching thread, and a writer takes them once a file. A next file that can't be made aborts at once, `order book runtime: housekeeping: cannot make shard 0's next log file: <reason>`, while the current file still has room, since the log could never go on, which `log_writer_abort_next_file` matches. `run` sleeps until a file is wanted or `stop`, looking for a stop before every pass, so a stop that comes first makes nothing. `waitForNext` says whether the file came, and a writer whose housekeeping stopped first, which only an abandoned engine can see, yields rather than spins. `removeUnused` closes and removes each next file no writer took, which a clean stop does once every writer is done; a forced stop or a crash leaves it, a header with no records, which the next start's recovery deletes as a trailing file with no records.
- **Retention** (`Housekeeping::retain`, `keepEveryFile`; D5). A `RollWorker` made with a `Rolled` callback reports each shard's `retentionFloor` after its roll, which the engine passes to `Housekeeping::retain`; a floor never goes down. Its next pass, on the housekeeping thread, lists the shard's log files by name and deletes each one whose successor starts at or before the floor, so a file is deleted only once closed, and a shard's three newest never are: the writer's, the one made ahead, and the one before them, which holds the log's last record while the writer's holds none yet. That matters after a clean stop, when every book can stand where the writer's file begins: a crash that lost the writer's records would otherwise leave recovery ending short of the books, on the records still on the drive, which `recovery_tests`' `testRetentionKeepsTheLastRecord` pins. In steady running the floor stands before the writer's file, so that file was never deletable anyway. A deletion that fails prints `order book runtime: housekeeping: cannot delete <name>: <why>` and is tried again once the floor next rises, not in a loop, since the file only takes room. `--keep-log` calls `keepEveryFile`, and nothing is deleted. `filesDeleted` counts them. The floor is the oldest checkpoint any book keeps, so a start that falls back still finds the log back to it.
- **`LogWriter`** (`log_writer.hpp`; ADR 0013). One per shard, as a plain object, the way `MatchingLoop` is, with the real thread only calling `run`. Its constructor takes the shard's first file from `Housekeeping`, named for its first position, its header holding the engine's version (the CMake project's, which the runtime library is built with), the first position, and the placement, the shard count, index, and the shard's symbols, which a shard's slots already hold in symbol order. A failure there throws, which refuses a start. `pass` drains up to 26,214 `LogEntry`s from the log ring, `mostBytesPerWrite` (1 MiB) of 40-byte records, and never more than its file has room for, so no write spans two files; it encodes each through `encodeLogRecord` into a buffer allocated once, chaining the checksum from its file's own header's seed, makes one write, then publishes the `DurablePosition` past them. There is no batching timer: a pass takes whatever has queued. A file it fills it flushes and closes at once, at both levels, before any write to the next, so only the last file can have an unsynced tail. The next record takes the next file from housekeeping; if none is made yet the pass writes nothing and `waitingForFile` says so, and `run` waits on housekeeping, so a slow drive reaches clients as backpressure. After the matching thread's STOP it writes the rest, cuts the file to its last record, so a clean stop leaves no zero tail, which would read as a crash, flushes, and closes it; at `PROCESS` that flush and the full files' are the only ones. A STOP on a file just filled has nothing left to finish and takes no next file. A failed write, flush, cut, or close aborts, printing `order book runtime: shard 0 log writer: <file>: <reason>` from fixed buffers, since a retry can't be trusted and no response has gone out for those commands; `log_writer_abort_write` and `log_writer_abort_flush` match it. `run` passes until the STOP, spinning for the spin window, then sleeping on its own `Doorbell`, which the matching thread rings after each take. `DurablePosition` (`durable_position.hpp`) is one atomic per shard, stored with release by the writer alone and loaded with acquire by gateway threads and the shard's own check: every position below it is durable. `log_writer_tests` reads everything written back through `CommandLogReader`, never through the encoder, and covers file shapes, making a file, the header, one write per pass, the 1 MiB cap, rolling across files with a wait for the next, a stop, a stop on a full file, a refused existing file, a writer and housekeeping on real threads, which labels it `threaded`, and the real files at both levels: an extended file reads as zeros past its writes on both platforms, a writer left unstopped leaves a last file that reads as `TORN_TAIL`, and a clean stop's files read whole.
- **`Doorbell`** (`doorbell.hpp`). One per shard, and one per log writer. On empty rings a matching thread spins for the spin window, then sleeps in `std::atomic::wait`. Producers ring after each batch. Every change to its one atomic is an exchange, sequentially consistent and never a fence, since GCC's `-Wtsan` fails a fence under warnings as errors. That rules out a lost wake-up: a producer's exchange after the sleeper's reads asleep and wakes it, and one before it sits in an unbroken chain of exchanges the sleeper's reads, so the sleeper's re-check of its rings sees the push. A plain store in `cancelSleep` would break that chain in C++'s model, though not on x86 or ARMv8, and ThreadSanitizer can't see the difference, so nothing tests it. A producer that only read a flag would not do either, because its load could pass its own earlier push. `matching_loop_tests` proves two parts on purpose: `testACommandBeforeTheSleepIsSeen` steps a ring into the gap before the announcement on one thread, which hangs without the re-check, and `testARingWakesASleeper` sends each command only once the thread has announced sleep, which hangs without the notify. The order of announcing before checking is not tested, because the gap between them can't be stepped into.
- **`EngineSettings`** (`engine_settings.hpp`). `order_book_engine`'s whole command line, since it has no config file and reads no environment. `parseEngineArguments` checks only shape: `--flag value`, with `--stop-on-stdin-close` the one flag with no value, required flags, no repeats, sizes with an optional binary `K`, `M`, or `G`, times with a unit (`ns`, `us`, `ms`, `s`) unless they are a bare `0`, and an IPv4 `ADDR:PORT`. A value that parses but can't run, such as a ring that isn't a power of two, is `runEngine`'s to refuse with exit 1, not a usage error. `--pin-matching` and `--pin-gateway` take numbers with commas between, and a core may repeat; how many there must be is `runEngine`'s to check. `--gateway-threads` takes a plain count up to 32 bits, as `--shards` does, defaults to 1, and is never derived from the machine; 0 is `runEngine`'s to refuse. `--log-dir` takes a path and is required, since D1c, when the `engine` benchmark kind began logging; an empty `logDir`, which only a caller in process can give, runs with no log, for the in-process tests that need no files. `--durability` takes `machine`, the default, or `process`, `--log-file-size` a size, 256 MiB by default, which `runEngine` refuses below `leastLogFileBytes`, and `--log-ring` a size like the other rings, 65,536 records by default, which `runEngine` refuses unless it is a power of two. `--roll-workers` is a count, 1 by default, which `runEngine` refuses unless it is from 1 to `--shards`, and the record prints it after `--log-ring`. `--checkpoint-dir DIR` (empty means the log directory) and the flag `--keep-log` print after `--log-dir` when given. `--pin-log-writers` takes cores as the other pins do. `--max-connections` is per gateway thread. `--thread-priority` takes `normal` or `high`. `formatEngineSettings` prints every flag with its value, defaults included, in a fixed order (`--gateway-threads` after `--max-connections`, and `--log-dir`, `--durability`, `--log-file-size`, and `--log-ring` and `--roll-workers` after `--stop-grace`), and parses back to the same settings: it is the record each run prints first. Counts print plainly and byte sizes in their largest exact unit. The pins print only when set, the log directory whenever it is, which from the command line is always, and the durability, log file size, log ring, and priority always. `engine_settings_tests` covers both.
- **Thread placement** (`thread_placement.hpp`). `pinThisThread(core)` and `setThisThreadPriority(priority)`, each on the calling thread, returning nothing once done or the system's reason for refusing. Pinning is `SetThreadAffinityMask` on Windows, so only the first processor group's 64 cores can be named, and `pthread_setaffinity_np` on Linux, up to `CPU_SETSIZE`. `HIGH` is `THREAD_PRIORITY_HIGHEST` on Windows and nice -10 on Linux through `setpriority` on the thread's own id, since Linux gives each thread its own nice value; `NORMAL` changes nothing. Other platforms refuse pinning and `HIGH`. `thread_placement_tests` reads each back through the system.
- **`AbortScope` and `describeAbort`** (`abort_report.hpp`). A matching thread holds an `AbortScope` naming its `Shard` once the shard is built, in a constant-initialized `thread_local`, and `describeAbort` writes the abort line for the calling thread into a caller's buffer: `order_book_engine: aborted: shard 2 symbol AAPL position 12345` from the shard's `lastProgress()` in a checked build, or `order_book_engine: aborted` with no scope or no checks. It formats digits by hand, cuts to fit, and allocates nothing, since `apps/`' SIGABRT handler calls it on the aborting thread. Reading the `thread_local` there is safe because `order_book_runtime` is a static library, linked into the executable, so its TLS needs no lazy allocation; made shared, it would need another way. Before a shard's first command it would name slot 0 at the first position.
- **`Shard`** (`shard.hpp`). A plain single-threaded object, with `MatchingLoop` a thin loop around it. `process(command, slot)` takes no origin, so replay and tests call exactly what the matching thread will, and leaves its events in one `CommandResult`, reserved at 512 trades and 1,024 events by the constructor. Anything larger still comes back whole. The position counts every command taken, a rejected one included. `resultGrowths()` counts commands that made the reused result reach the heap, found by comparing the capacities its public accessors expose before and after each command, so nothing in the public API changed for it, and a command that only refills what an earlier one grew isn't counted again. Checked builds record the slot and position before running, in `lastProgress()`, for the engine's abort handler to print when a book's own check aborts, and other builds pay nothing. `MatchingLoop`'s abort for an escaping exception has the element in hand and needs none of this. `checkInvariants` runs every book's own check, then that each slot maps back through the directory, then that the next log position is the first plus the commands taken, then, once `watchDurablePosition` has given it the shard's `DurablePosition`, that it never passes the next position and never goes back, from the first position or from what an earlier check saw, returning a `ShardViolation`. Matching never waits for the log, so a durable position behind the next one is sound. A durable position ahead of it is sound only mid-take, since a whole take reaches the log ring before any of it runs, so the check holds wherever no take is half run: at the end of a pass, at a stop, and wherever a test calls it. `shard_invariant_tests` breaks each part through `OrderBookTestAccess`, which `Shard` befriends too. `matching_path_allocation_tests` holds a warm shard to exactly zero heap calls on all eleven workloads, counted per thread in a replaced `operator new`, along with the `out` overloads for every type and time in force, a cascade, `replaceOrder`'s paths, in place, moved back, crossing, and post-only expiring, `cancelOrder`, and `encodeLogRecord`. It first shows the count can move, on a book past its capacity.
- **`Shard::skip` and `startAt`** (D5). Recovery starts a shard at its oldest book's position with `startAt`, before any command is taken (after one it throws `std::logic_error`), and passes a record its book's checkpoint already holds with `skip`, which moves the position on and counts the command as taken, so `checkInvariants`' next position is the first plus the commands taken still holds. The engine publishes the recovered end as the durable position before its writer starts, since a shard that starts past 0 may not find the durable position below its start.
- **Checkpoint file** (`checkpoint.hpp`; spec #58's D4a, ADR 0009; bytes in [`../checkpoint-format.md`](../checkpoint-format.md)). A pure codec, touching no file and no lock. `encodeCheckpoint(header, image)` writes format 1 at 64 header bytes, no section, and the XXH64 of `xxh64.hpp` (the command log's, seed 0), writing the header as given, so tests make refused files through it. `decodeCheckpoint(file)` returns a `DecodedCheckpoint`, the `CheckpointHeader` and a span into `file`, so the bytes must outlive it, and not yet a checkpoint in the glossary's sense, since nothing has proved it restores; it checks the magic, then the length, then the checksum before any field is read, then versions, header size, and lengths (the image, then each section, which must end exactly at the checksum, every subtraction made from the side already known to be smaller, so no length can wrap), then the fields by offset, sections' reserved words last. Decode and describe share one magic check. `CheckpointErrorCode` is an open set. `verifyCheckpoint` decodes and runs `OrderBook::restore`, destroying the book, and moves `restore`'s offset by the image's start in the file, so a fault behind a longer header lands where it lies; `CheckpointFault::Code` holds either layer's code. `describeCheckpoint` reads both headers raw, the image's through the library's `readImageHeader` at the stated header bytes, and `formatCheckpointDescription` prints them. D4b's worker and D5's recovery are its other callers to come.
- **Roll forward** (`roll_forward.hpp`; spec #58's D4b, ADR 0014). Plain objects over `LogStorage`, so the worker, the harness, and tests run the same pass. `checkpointFileName`/`parseCheckpointFileName` are `ckpt-<symbol>-<position, 20 digits>.obckpt`, `.tmp` while publishing; the prefix keeps `AUX`, `CON`, and `NUL` from being Windows device names. `proveImage` is the proof: `restore`, `checkInvariants`, and `writeImage` again, which must give the same bytes, so an image restore accepts but writes otherwise (a longer stated header) fails too; `requireProvedImage` aborts on a failure, naming the shard, symbol, and position. `publishCheckpoint` creates `<name>.tmp` (removing one an exception left, since only the lock holder makes them), writes, flushes, reads back through the same handle and decodes, which must give what was meant, then renames, which flushes the directory; any failure before the rename removes the `.tmp` and throws `LogStorageError`, and a failed close after it is ignored, since the rename published it. `ShardRoller` is one shard's roll over one store, on one thread at a time. When made, as at a start, it removes its books' leftover `.tmp` files, keeps each book's two newest checkpoints that decode as named, and removes anything older, which a machine crash undoing a removal can leave. It then knows each book's two positions without reading names again, and names come from symbol and position, so updating them never allocates. `roll(closedEnd)` reads any new log file's header (each lists every instrument on the shard) and walks the closed files once, oldest first, a file being closed once the next one starts at or before `closedEnd`. A file's pass takes the books standing at its first position: each is restored from its newest checkpoint on its first command, or starts empty with none, every command is replayed through `executeCommand`, each image is proved, and every book is published at the file's end, a book with no command getting a new wrapper around its image with no restore. Images are all made and proved before any is published. A failed publish counts `writesFailed`, reports, and leaves that book at its last checkpoint for the next call; the superseded third checkpoint is removed after the new one is in place, and a removal cut short stays pending for the next call. A `bad_alloc` anywhere counts `passesLost`, discards that pass's books, and ends the call, leaving any book already published known and whole; the next call makes the pass again. A checkpoint that no longer decodes or restores falls back to the older one and abandons the pass, reported but not counted. `filesBehind` counts closed files some book they list stands before the end of. A book with no checkpoint is an empty book at the first log file whose header lists it, which only tests reach, since a start refuses a lost checkpoint and gives a new instrument an empty one. A newest checkpoint that no longer decodes or restores mid-run is removed, since its book will publish at that position again and a rename never replaces a file, and the book falls back to its older one. `retentionFloor` is the oldest checkpoint any book keeps, its older one or its only one, and nothing while some book stands nowhere.
- **`ClosedLog` and `RollWorker`** (`closed_log.hpp`, `roll_forward.hpp`; D4b). `ClosedLog` holds, per shard, the end of the last file its log writer closed: a `LogWriter` given one says where it starts (every file before it is closed) and, after it flushes and closes a full file, where that file ended, then wakes any worker through a condition variable, the only lock it takes and only once a file. A clean stop's last file is not closed in this sense, since no file follows it, so the clean stop's last roll, `finish`, is told the log's end instead. `roll(closedEnd)` reads only the headers of files it knows are closed, from names alone, since on Windows the writer's file and the one made ahead allow no second handle. `RollWorker` holds a `ShardRoller` per shard it rolls, made on the starting thread, so leftover `.tmp` files go and checkpoints are read before it runs; `pass` rolls each to its shard's closed end, checking `ClosedLog::stopping` between passes, and `run` passes once, then after each close, reading the generation before each pass so a file closed during one wakes the next at once.
- **The clean stop's last three steps** (`clean_stop.hpp`, `ShardRoller::finish`, `RollWorker::finish`; spec #58's D6a, #30, #34, #35). Step 3 is `captureLiveImages(shard)`, on the matching thread once its loop has stopped: the full `Shard::checkInvariants`, which aborts on a violation with `order book runtime: clean stop: shard 0 AAPL: the live book fails its check: <why>` (no symbol for a position violation), since a book's index and level handles are in no image, so no comparison can see them, then each book's image into buffers allocated there, `LiveImages` by slot. A `bad_alloc` in a buffer gives no images and throws nothing; one in the check aborts (`..., and memory ran out describing it`), since `OrderBook::checkInvariants` is `noexcept` and a sound shard's check allocates nothing, so only describing a violation can run out, and the check is never skipped; with `images` false, as an engine with no log calls it, the check alone. Steps 4 and 5 are `ShardRoller::finish(logEnd, live)`, once the log writer has cut, flushed, and closed the last file and the unused next one is gone: it rolls every closed file a book still needs, as `roll(logEnd)` does, each published at its own end, then the last, short file, the newest named before `logEnd` that no roll has seen, read as ending at `logEnd`, with the books standing at its start; a book already standing at `logEnd` gives its newest checkpoint's image. Each of these images is compared byte for byte with its live one. A match is published at `logEnd`, or, already standing there, counts as published with nothing written; a mismatch publishes nothing for that book and saves the live image, wrapped in the checkpoint format under the header it would have had, as `liveImageFileName`'s `ckpt-<symbol>-<position, 20 digits>.live`, replacing one an earlier stop left at the same end, since a start reads no such name; it is written in place, not renamed, so a machine crash may lose or tear it, which harms nothing. "Publishes nothing for that book" is at `logEnd`: the closed files rolled on the way are published at their own ends, as any roll publishes them, since they come from the log alone, and a book whose full last file a worker already rolled stands at `logEnd` with the log's checkpoint and is still reported `DIFFERS`. `stopped(slot)` says what became of each book, a `StoppedBook`: `PUBLISHED`, `DIFFERS` with the first differing byte and whether `.live` was saved, `NO_IMAGE` (no live images: the closed files still roll and nothing is published at the end), `PUBLISH_FAILED` (counted in `writesFailed`), or `NOT_ROLLED`, for a book left behind the last file by an earlier failure or a lost pass. `finish` throws nothing: a `bad_alloc` counts a lost pass and leaves the rest `NOT_ROLLED`, and a read failure is reported. A pass abandoned for a checkpoint that no longer reads, whose book falls back to its older one, is made again at once (`finishOnce`, at most twice a book and once more), as the next roll would make it, so a damaged newest checkpoint doesn't leave its book unpublished at a clean stop. `filesBehind` then counts the last file too. `formatStoppedBook` gives #34's line for each book not published, without the engine's prefix, such as `clean stop incomplete: AAPL differs at byte 812, saved ckpt-AAPL-00000000000000000120.live; the next start recovers from the log`. `RollWorker::finish(byShard)` runs each of its shards' `finish` from a `ShardAtStop`, the log end and the live images. `pass` and `finish` share `imagesAt`, which replays a file and proves or rewraps each book needing it, and `publish`. `clean_stop_tests` runs it all on the in-memory storage, with a `Running` shard, log writer, housekeeping, and lagging roller on one thread.
- **Recovery** (`recovery.hpp`; spec #58's D2, ADR 0013). Since D5, from checkpoints: `surveyLog(logs, checkpoints, directory)` also lists each book's checkpoints by name, newest first, in `LogSurvey::checkpoints` (by shard, then slot), refuses a checkpoint naming a symbol off the list as a header would (`<name> names <symbol>, which is not on the instrument list`, exit 1), stops on a lost checkpoint, a listed instrument a header names that no checkpoint holds (`shard 0 symbol MSFT: a log file's header names it, and no checkpoint holds it: a lost checkpoint`), and puts each instrument named nowhere with none in `newBooks`, whose empty-book checkpoints the log writer publishes; `checkpointTemporaries` are `.tmp` files a crash left being published, for the engine to delete. `recoverShard(logs, checkpoints, directory, files, bookCheckpoints, shard, ...)` restores each book from the first checkpoint, newest first, that decodes, names its symbol and position, stands under this placement, and restores, counting `fellBack` when that isn't the newest; none restoring stops (`shard 0 symbol AAPL: no checkpoint restores: <name>: <why>; <name>: <why>`), and one written under another shard or shard count, which a placement change would have rewrapped, is `PLACEMENT_CHANGED` (`<name> was written by shard 0 of 3, and this start places AAPL on shard 0 of 2, though the logs' headers name this placement: a placement change was cut short, so start on the placement that checkpoint names to finish it`). It then calls `Shard::startAt` with the oldest book's position, `RecoveredShard::start`, and reads from the last file starting at or before it, ignoring records before it and passing each record older than its own book's position with `Shard::skip`, so a position still counts it; files before that one may be gone. A log that starts after the oldest book's position, its first file counted even if it holds no record, is a gap at that position, and a gap between files after it stops as before. After the replay, a book any of whose checkpoints, by name, one that didn't decode included, stands past the log's end, what the files hold, or where the first trailing file removed began, stops (`shard 0 position 40 symbol AAPL: its checkpoint stands past the log's end, 30: the disk lost data it had confirmed`). A shard with no book standing anywhere, as a placement change can leave one, or one holding only new books, reads only its last file, its records passed over and their chain still checked, and starts at its log's end, which only the reading tells, so `startAt` waits for it. Two plain calls, so `recovery_tests` runs them on the in-memory storage with no thread. `surveyLog` is the main thread's part, once the caller holds the lock and before any book exists, and changes nothing: it reads every file named like a log, `log-` and `.oblog` or `.oblog.tmp`, refusing one not named as an engine names one, and sets aside a `.tmp`, which a crash left being made and which held no record anyone heard of, for the engine to delete; the lock, `cut-` files, and anything else are not the log's. It reads only each file's header, through a stream cut at the header's stated length, so no zero tail is read here, and stops on a header the reader refuses, one whose shard or first position isn't its name's, or one with no placement, which no engine wrote. Then, in the spec's order, a symbol in any header off the instrument list refuses the start, then each current shard's newest header must have the directory's shard count and every symbol on its own shard, or the placement changed. A new instrument trips nothing. Files of a shard at or past the directory's count are a log a change left, which no shard writes: they stay, unread by recovery and roll forward, out of `LogSurvey::shards`, and moving nothing, so a later start finds no change in them; retention never deletes them. Their headers are still read, so a symbol they name can't leave the instrument list while they stand, and a later change back up to that count makes such a log a shard's own again, its books placed at its end. `LogSurvey::named` lists every symbol a header names, sorted and once each, so the engine can tell a new instrument, one named nowhere and with no checkpoint. `recoverShard` is each shard's part, on its matching thread, into a `Shard` just built at position 0: it removes trailing files with no record, one with nothing written past its header, as the next file made ahead is, or whose first record is torn with nothing valid after it, opening each file once at a time, since a file opened to cut shares no writing on Windows; replays the rest through `Shard::process`, discarding events, each file at the position the last one ended, through `CommandLogReader` over the storage, looking at the stop flag before every 1,024 records; runs `checkInvariants`; warms each book to the larger of what it declares and 1.5 times what `OrderBook::holding` says it holds, rounded up, each number apart; then cuts the last file at its torn tail, or at a hole that valid records follow if that lies within `tornWriteReach`, 1 MiB, of the end of what the file holds, rounded up to whole records, which is a write a machine crash tore, since one write is at most `LogWriter::mostBytesPerWrite` (a `static_assert` holds the two together), and flushes it. A cut that leaves the file no record removes it instead, as a trailing file with none, so the next file can start where it did. `tailCutBytes` counts the bytes a write reached that the cut or a removed file dropped, up to the last byte that isn't zero, so a zero tail alone is 0 and a record torn as it was written is what of it was written. The log writer then makes the next file at `replayed`. Every finding it can't explain is a `RecoveryError`: `START_REFUSED` (exit 1), `PLACEMENT_CHANGED` (exit 4), or `RECOVERY_STOPPED` (exit 5), whose message names the shard, position, file, and, for a record, the symbol and its row, as far as each is known; a record the reader refuses is named at its own position, one before the replay's start included, whose chain is still read. `RECOVERY_STOPPED` covers the rest of the findings table, each with its exact message pinned in `recovery_tests`: a header the reader refuses (`CORRUPT_HEADER`, `UNSUPPORTED_VERSION`, `UNKNOWN_FIELD`, `INVALID_SYMBOL`), a record it refuses for its fields, `TORN_TAIL` or `CORRUPT_RECORD` in a file before the last (", in a file before the last, which its log writer flushed whole"), a `CORRUPT_RECORD` further back than 1 MiB (", with N bytes of records from it to the end of what was written, more than one write's 1048576"), a first file not at 0, a gap, a record for another shard's instrument, and a book replay left broken. The table's last row, a checkpoint past the log's end, is the past-the-end stop above. A stop requested mid-replay throws `RecoveryInterrupted`, which the engine turns into exit 6. A refused start may already have removed empty trailing files or cut a tail, which only drops what no client heard of, so the next start finds the same books.
- **Placement changes** (`surveyLog`, `changePlacement`, `recovery.hpp`; spec #58's D6b, #30's start step 4). A changed shard count or a moved symbol, seen in some current shard's newest header, needs every tail empty: each book's newest checkpoint must decode, name its symbol and position, and stand at the end of the log its own header names, that log ending as a clean stop leaves it (`cleanEnd`: its trailing files with no record set aside, as a clean stop's last file or a start's first can be, the last that holds one read whole to its end through the log's own reader, no torn tail, a torn first record, or any finding allowed, and each file set aside starting at that end, so one whose records a crash zeroed while a later file stands is not mistaken for one), a shard with no log ending at 0. Otherwise the start is refused, `PLACEMENT_CHANGED` (exit 4), with #34's message, `<what> and the last run did not stop cleanly; restart on the old placement and stop cleanly first`, where `<what>` is `MSFT moved from shard 1 to shard 0` or `the log was written by 2 shards and this start has 3`; the first moved symbol is named, whichever book's tail is not empty. A clean stop that exited 7 leaves a book short of its end, so it is refused the same way. `LogSurvey::placement` is the `PlacementChange`: a `Rewrap` for each book whose header names another shard or count, to its current shard at that shard's log end, and in `dropped` the older checkpoints whose positions the change voids, where a fall-back would replay a log across it: every rewrapped book's, which a new count makes every book, and every book's on a shard some book left, whose log holds that book's records after them. A book on a shard that only gained one keeps its older checkpoint and can still fall back to it. A name a rewrap lands on is kept, which only an interrupted change leaves. `surveyLog` still changes nothing; `changePlacement` removes the dropped, then publishes each rewrap under its new header (this build's version, the new shard, count, and position) through `publishCheckpoint` with `replacing`, so a book whose shard number and position stay the same under a new count, whose name stays the same too, is replaced in one step (`LogFile::replace`), then removes the checkpoint it came from where the name differs. The engine prints `order_book_engine: placement changed: MSFT from shard 1 of 2 at 3 to shard 0 of 2 at 2` for each, then surveys again, which finds the same change with nothing left to do, every book now under its current shard at its end; its log writers' first files then carry the new placement, and a later start finds no change. A crash anywhere in `changePlacement` leaves a store the next start's survey finds the same change in, with less to do: the drops are older positions nothing needs, a rewrap either landed or its source stands, and a source removed only after its rewrap landed. A crash later in the start, once some shards' log writers made their first files under the new placement and others not, leaves those trailing files with no record, which `cleanEnd` sets aside, so the start goes on. A start on the old placement after a change cut short finds no change, the logs' headers still naming it, and `recoverShard` refuses the first rewrapped checkpoint, sending the operator to the placement that checkpoint names. Shards that lost every book start at their log's end, as above, and a shard new to the count starts at 0. A moved book's positions mean nothing in its new log, so `replay <log-dir>` refuses a symbol in two shards' logs, as #34 has it.
