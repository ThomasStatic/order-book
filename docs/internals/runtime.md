# Engine runtime

Library `order_book_runtime` (namespace `order_book::runtime`, headers in `include/order_book/runtime/`, sources in `src/runtime/`), linking `order_book_replay`. It is not public API: the engine's contract to the outside is its formats, its wire protocol, and its programs' flags and output. Terms are in `GLOSSARY.md`, and the decisions in ADRs 0007 and 0008.

- **`parseInstrumentList(text, shardCount)`** (`instruments.hpp`). The exact header `symbol,shard,orders,stops,levels`, then five fields per row, to the replay format's strictness: LF or CRLF, a last line with no ending, no quoting, blank lines, or comments, digits only, leading zeros ignored. It reports the first problem, with a line, column, and `InstrumentListErrorCode`, in the order record framing, `symbol`, duplicate, `shard`, `orders`, `stops`, `levels`. An empty field means the default. `shard` may be 0, unlike any replay column, and at or past `shardCount` is `SHARD_OUT_OF_RANGE`, a start error. The capacity columns refuse 0. Every number stops at `maxInstrumentListNumber`, 2^32 - 1, so a list means the same on any platform. The codes are the list's own, not `ParseErrorCode`, because `ParseErrorCode` is the replay format's and the list adds no column to it. `formatInstrumentListError` gives the start error's `<path>:<line>: <column>: <message>`, leaving out the column when there is none.
- **Placement.** `symbolHash` is 64-bit FNV-1a over the 8 stored bytes, padding included, and `hashedShard` takes it modulo the shard count. A log records the placement it was written under, so the hash is a format in all but name, never `std::hash`: `instrument_directory_tests` pins sample placements worked out apart from this code. A placement depends on nothing but the symbol and the shard count, or a pin, so adding instruments moves nothing while the count stays the same.
- **`InstrumentDirectory`.** Built once, then immutable, so any thread reads it without locks. It holds two sorted arrays, `bySymbol` for `find` (a bisection, returning a `BookLocation` of shard and slot) and `bySlot` for `onShard`. A shard's slots are in symbol order, so a list's line order means nothing. Slots are dense and private: no format holds one, and none is ever sent. The constructor throws `std::invalid_argument` for what the parser refuses, so a directory built any other way is just as sound. A shard may hold no instruments.
- **`BookSet`** (`book_set.hpp`). One shard's books by slot. Its owning thread is the one that builds it, and it never copies or moves, so "a book is touched only by its owning thread, from when it is built until destroyed" has one thing to check. `execute(slot, command)` and its `out` overload go through `replay::executeCommand`, the one place a command becomes a book call. `book(slot)` is read-only. Both abort in checked builds (`invariantChecksAfterCommands`) when called from another thread, printing `order book runtime: BookSet::<call> called off its owning thread: shard=<n> slot=<n>`, which `book_set_thread_execute` and `book_set_thread_book` match. The constructor warms each book with `reserve(capacityOf(instrument, defaults))`, where `defaultBookCapacity` is the 4,096 orders, 1,024 stops, and 256 levels per side of `--capacity-orders`, `--capacity-stops`, and `--capacity-levels`.
- **`Ring`** (`ring.hpp`; ADR 0011). One writer thread and one reader thread, lock-free, with a power-of-two capacity set when it is built, and the only allocation there. `tryPush` copies in and publishes with a release store; `drain(limit, take)` passes up to `limit` items to `take`, then gives their slots back together with one release store, so a batch costs one store. Indices count up for ever, so full and empty need no spare slot, and each side keeps its last view of the other's index on its own cache line, touching the shared line only when that runs out. That view is why a relaxed load of its own index and an acquire load of the other's are all it takes. `CommandElement` is 64 bytes and `ResponseRecord` 48, both trivially copyable, which the header proves at compile time. `ControlKind` sits outside `Command`, and the log accepts only a `Command`, so a stop marker can't reach the log, by type. `ring_tests` runs a real second thread through two small rings, so both sides keep meeting full and empty, and it is labelled `threaded`.
- **`MatchingLoop`** (`matching_loop.hpp`). What a matching thread does, as a plain object, so `matching_path_allocation_tests` and `gateway_tests` can step `pass` on one thread and the real thread only calls `run`. A test's `waitInPlace` runs in place of the yield on a full response ring, so a command with more events than the ring has slots can finish on one thread, by playing the gateway from inside the wait. `pass` takes up to `takeBatch` (64) commands from each ring in turn, and that take order is the command sequence. Each command's events go back one record at a time on its own ring's responses, the last marked `LAST_EVENT`, and a full response ring waits in place, which can't deadlock while the producer keeps draining. `run` passes until every producer has sent a stop marker, then sends `SHARD_STOPPED` on every response ring. An exception escaping a command aborts, naming the shard, symbol, position, and command through `fprintf` with no buffer of its own, since the failure may be that nothing can be allocated, though `fprintf` itself may use `malloc`, which `matching_abort_tests` doesn't fail: `submitOrder` can leave executions standing that replay wouldn't reproduce, so the engine declines to continue. `matching_abort_tests` fails allocations on a running book to show it.
- **`Doorbell`** (`matching_loop.hpp`). One per shard. On empty rings a matching thread spins for the spin window, then sleeps in `std::atomic::wait`. Producers ring after each batch. Every change to its one atomic is an exchange, sequentially consistent and never a fence, since GCC's `-Wtsan` fails a fence under warnings as errors. That rules out a lost wake-up: a producer's exchange after the sleeper's reads asleep and wakes it, and one before it sits in an unbroken chain of exchanges the sleeper's reads, so the sleeper's re-check of its rings sees the push. A plain store in `cancelSleep` would break that chain in C++'s model, though not on x86 or ARMv8, and ThreadSanitizer can't see the difference, so nothing tests it. A producer that only read a flag would not do either, because its load could pass its own earlier push. `matching_loop_tests` proves two parts on purpose: `testACommandBeforeTheSleepIsSeen` steps a ring into the gap before the announcement on one thread, which hangs without the re-check, and `testARingWakesASleeper` sends each command only once the thread has announced sleep, which hangs without the notify. The order of announcing before checking is not tested, because the gap between them can't be stepped into.
- **`EngineSettings`** (`engine_settings.hpp`). `order_book_engine`'s whole command line, since it has no config file and reads no environment. `parseEngineArguments` checks only shape: `--flag value`, with `--stop-on-stdin-close` the one flag with no value, required flags, no repeats, sizes with an optional binary `K`, `M`, or `G`, times with a unit (`ns`, `us`, `ms`, `s`) unless they are a bare `0`, and an IPv4 `ADDR:PORT`. A value that parses but can't run, such as a ring that isn't a power of two, is `runEngine`'s to refuse with exit 1, not a usage error. `formatEngineSettings` prints every flag with its value, defaults included, in a fixed order, and parses back to the same settings: it is the record each run prints first. Counts print plainly and byte sizes in their largest exact unit. `engine_settings_tests` covers both.
- **`Shard`** (`shard.hpp`). A plain single-threaded object, with `MatchingLoop` a thin loop around it. `process(command, slot)` takes no origin, so replay and tests call exactly what the matching thread will, and leaves its events in one `CommandResult`, reserved at 512 trades and 1,024 events by the constructor. Anything larger still comes back whole. The position counts every command taken, a rejected one included. `resultGrowths()` counts commands that made the reused result reach the heap, found by comparing the capacities its public accessors expose before and after each command, so nothing in the public API changed for it, and a command that only refills what an earlier one grew isn't counted again. Checked builds record the slot and position before running, in `lastProgress()`, for the engine's abort handler to print when a book's own check aborts, and other builds pay nothing. `MatchingLoop`'s abort for an escaping exception has the element in hand and needs none of this. `checkInvariants` runs every book's own check, then that each slot maps back through the directory, then that the next log position is the first plus the commands taken, returning a `ShardViolation`. The durable position joins it with the log writer. `shard_invariant_tests` breaks each part through `OrderBookTestAccess`, which `Shard` befriends too. `matching_path_allocation_tests` holds a warm shard to exactly zero heap calls on all eleven workloads, counted per thread in a replaced `operator new`, along with the `out` overloads for every type and time in force, a cascade, `replaceOrder`'s paths, in place, moved back, crossing, and post-only expiring, `cancelOrder`, and `encodeLogRecord`. It first shows the count can move, on a book past its capacity.
- **The interleaver** lives apart, in `order_book_reference` (`tests/reference/interleaver.hpp`), so that tests and benchmarks share one: see [`randomized-tests.md`](randomized-tests.md).
