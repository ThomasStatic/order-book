# Engine runtime

Library `order_book_runtime` (namespace `order_book::runtime`, headers in `include/order_book/runtime/`, sources in `src/runtime/`), linking `order_book_replay`. It is not public API: the engine's contract to the outside is its formats, its wire protocol, and its programs' flags and output. Terms are in `GLOSSARY.md`, and the decisions in ADRs 0007, 0008, 0011, and 0013.

- **`parseInstrumentList(text, shardCount)`** (`instruments.hpp`). The exact header `symbol,shard,orders,stops,levels`, then five fields per row, to the replay format's strictness: LF or CRLF, a last line with no ending, no quoting, blank lines, or comments, digits only, leading zeros ignored. It reports the first problem, with a line, column, and `InstrumentListErrorCode`, in the order record framing, `symbol`, duplicate, `shard`, `orders`, `stops`, `levels`. An empty field means the default. `shard` may be 0, unlike any replay column, and at or past `shardCount` is `SHARD_OUT_OF_RANGE`, a start error. The capacity columns refuse 0. Every number stops at `maxInstrumentListNumber`, 2^32 - 1, so a list means the same on any platform. The codes are the list's own, not `ParseErrorCode`, because `ParseErrorCode` is the replay format's and the list adds no column to it. `formatInstrumentListError` gives the start error's `<path>:<line>: <column>: <message>`, leaving out the column when there is none.
- **Placement.** `symbolHash` is 64-bit FNV-1a over the 8 stored bytes, padding included, and `hashedShard` takes it modulo the shard count. A log records the placement it was written under, so the hash is a format in all but name, never `std::hash`: `instrument_directory_tests` pins sample placements worked out apart from this code. A placement depends on nothing but the symbol and the shard count, or a pin, so adding instruments moves nothing while the count stays the same.
- **`InstrumentDirectory`.** Built once, then immutable, so any thread reads it without locks. It holds two sorted arrays, `bySymbol` for `find` (a bisection, returning a `BookLocation` of shard and slot) and `bySlot` for `onShard`. A shard's slots are in symbol order, so a list's line order means nothing. Slots are dense and private: no format holds one, and none is ever sent. The constructor throws `std::invalid_argument` for what the parser refuses, so a directory built any other way is just as sound. A shard may hold no instruments.
- **`BookSet`** (`book_set.hpp`). One shard's books by slot. Its owning thread is the one that builds it, and it never copies or moves, so "a book is touched only by its owning thread, from when it is built until destroyed" has one thing to check. `execute(slot, command)` and its `out` overload go through `replay::executeCommand`, the one place a command becomes a book call. `book(slot)` is read-only. Both abort in checked builds (`invariantChecksAfterCommands`) when called from another thread, printing `order book runtime: BookSet::<call> called off its owning thread: shard=<n> slot=<n>`, which `book_set_thread_execute` and `book_set_thread_book` match. The constructor warms each book with `reserve(capacityOf(instrument, defaults))`, where `defaultBookCapacity` is the 4,096 orders, 1,024 stops, and 256 levels per side of `--capacity-orders`, `--capacity-stops`, and `--capacity-levels`.
- **`Ring`** (`ring.hpp`; ADR 0011). One writer thread and one reader thread, lock-free, with a power-of-two capacity set when it is built, and the only allocation there. `tryPush` copies in and publishes with a release store; `drain(limit, take)` passes up to `limit` items to `take`, then gives their slots back together with one release store, so a batch costs one store. Indices count up for ever, so full and empty need no spare slot, and each side keeps its last view of the other's index on its own cache line, touching the shared line only when that runs out. That view is why a relaxed load of its own index and an acquire load of the other's are all it takes. `CommandElement` is 64 bytes and `ResponseRecord` 48, both trivially copyable, which the header proves at compile time. `ControlKind` sits outside `Command`, and the log accepts only a `Command`, so a stop marker can't reach the log, by type. A matching thread looks ahead before a take: `waiting(limit)` counts what is there and `peek(i)` sees each in place, `hasRoomFor(count)` asks the writer's side whether a whole take would fit, and `drainWhile` stops after the item its `take` returns false for, which is how a gateway thread stops at a hold marker. `ring_tests` runs a real second thread through two small rings, so both sides keep meeting full and empty, and it is labelled `threaded`.
- **`MatchingLoop`** (`matching_loop.hpp`). What a matching thread does, as a plain object, so `matching_path_allocation_tests` and `gateway_tests` can step `pass` on one thread and the real thread only calls `run`. A test's `waitInPlace` runs in place of the yield on a full response ring, so a command with more events than the ring has slots can finish on one thread, by playing the gateway from inside the wait. `pass` takes up to `takeBatch` (64) commands from each ring in turn, and that take order is the command sequence. Each command's events go back one record at a time on its own ring's responses, the last marked `LAST_EVENT`, and a full response ring waits in place, which can't deadlock while the producer keeps draining. `run` passes until every producer has sent a stop marker, then tells the log writer to finish, if there is one, and sends `SHARD_STOPPED` on every response ring. **With a log** (a `LogLink`, the log ring and the writer's doorbell), a take is no larger than the log ring, and before running it the matching thread counts its commands, waits until the log ring has room for all of them (a full ring makes it wait before a take, never mid-command), copies them in, rings the writer, and puts one `HOLD` marker on that ring's responses naming the position all of them need, `nextPosition()` plus their count. Every command of a take is on the log ring before any of it runs because the matching thread may then wait mid-take for room in a response ring that a gateway thread, held at that marker, is not draining: the writer can still make the whole take durable, so the gateway is released and the ring empties. Pushed only as each ran, the later commands of a take would wait behind a response ring the held gateway can't empty, and nothing would move. A take of stop markers alone pushes no marker. In the engine each gateway thread is a producer, with its own pair of rings to every shard, so M gateway threads on N shards make M×N pairs. An exception escaping a command aborts, naming the shard, symbol, position, and command through `fprintf` with no buffer of its own, since the failure may be that nothing can be allocated, though `fprintf` itself may use `malloc`, which `matching_abort_tests` doesn't fail: `submitOrder` can leave executions standing that replay wouldn't reproduce, so the engine declines to continue. `matching_abort_tests` fails allocations on a running book to show it.
- **`LogStorage`** (`log_storage.hpp`; ADR 0013). Every file the log touches goes through it, so the log writer is a plain object over it. `create(name, durability)` makes a new file and never opens an existing one, which throws `LogStorageError` of kind `EXISTS`, since old files' stale records still chain; a `LogFile` writes at an offset, flushes, cuts to a size, and closes, and any failure throws `LogStorageError`. `Durability` and the log ring's default, 65,536 records, are in `durability.hpp`, which `engine_settings.hpp` takes alone. `FileLogStorage` is the real one over one directory: `MACHINE` opens with `FILE_FLAG_WRITE_THROUGH` on Windows and `O_DSYNC` on Linux, so a write returns once the drive has it, and `PROCESS` with neither. On Linux, creating a file also flushes the directory, since otherwise a machine crash could lose the name and every record with it; NTFS journals that. Everything that allocates comes before the file is made, and a create that fails after it removes it, so a failed create leaves nothing to refuse the next start on. `InMemoryLogStorage` holds files in memory under one lock, counts each file's writes, flushes, and cuts, follows a file from an offset (`read`), and fails a chosen write (`failWriteAfter`) or every flush (`failFlushes`). Crashes are D2's to model. `logFileName(shard, position)` is #34's `log-<shard, 4 digits>-<first position, 20 digits>.oblog`.
- **`LogWriter`** (`log_writer.hpp`; ADR 0013). One per shard, as a plain object, the way `MatchingLoop` is, with the real thread only calling `run`. Its constructor makes the shard's file, named for its first position, and writes the header: the engine's version (the CMake project's, which the runtime library is built with), the first position, and the placement, the shard count, index, and the shard's symbols, which a shard's slots already hold in symbol order. A failure there throws, which refuses a start, and a header that can't be written removes the file. `pass` drains up to 26,214 `LogEntry`s from the log ring, `mostBytesPerWrite` (1 MiB) of 40-byte records, encodes each through `encodeLogRecord` into a buffer allocated once, chaining the checksum from the header's seed, makes one write, then publishes the `DurablePosition` past them. There is no batching timer: a pass takes whatever has queued. After the matching thread's STOP it writes the rest, flushes, cuts the file to its last record (a no-op until D1b extends files ahead of time), and closes it; at `PROCESS` that flush is the only one. A failed write, flush, cut, or close aborts, printing `order book runtime: shard 0 log writer: <file>: <reason>` from fixed buffers, since a retry can't be trusted and no response has gone out for those commands; `log_writer_abort_write` and `log_writer_abort_flush` match it. `run` passes until the STOP, spinning for the spin window, then sleeping on its own `Doorbell`, which the matching thread rings after each take. `DurablePosition` (`durable_position.hpp`) is one atomic per shard, stored with release by the writer alone and loaded with acquire by gateway threads and the shard's own check: every position below it is durable. `log_writer_tests` reads everything written back through `CommandLogReader`, never through the encoder, and covers the header, one write per pass, the 1 MiB cap, the stop, a refused existing file, and the real files at both levels.
- **`Doorbell`** (`doorbell.hpp`). One per shard, and one per log writer. On empty rings a matching thread spins for the spin window, then sleeps in `std::atomic::wait`. Producers ring after each batch. Every change to its one atomic is an exchange, sequentially consistent and never a fence, since GCC's `-Wtsan` fails a fence under warnings as errors. That rules out a lost wake-up: a producer's exchange after the sleeper's reads asleep and wakes it, and one before it sits in an unbroken chain of exchanges the sleeper's reads, so the sleeper's re-check of its rings sees the push. A plain store in `cancelSleep` would break that chain in C++'s model, though not on x86 or ARMv8, and ThreadSanitizer can't see the difference, so nothing tests it. A producer that only read a flag would not do either, because its load could pass its own earlier push. `matching_loop_tests` proves two parts on purpose: `testACommandBeforeTheSleepIsSeen` steps a ring into the gap before the announcement on one thread, which hangs without the re-check, and `testARingWakesASleeper` sends each command only once the thread has announced sleep, which hangs without the notify. The order of announcing before checking is not tested, because the gap between them can't be stepped into.
- **`EngineSettings`** (`engine_settings.hpp`). `order_book_engine`'s whole command line, since it has no config file and reads no environment. `parseEngineArguments` checks only shape: `--flag value`, with `--stop-on-stdin-close` the one flag with no value, required flags, no repeats, sizes with an optional binary `K`, `M`, or `G`, times with a unit (`ns`, `us`, `ms`, `s`) unless they are a bare `0`, and an IPv4 `ADDR:PORT`. A value that parses but can't run, such as a ring that isn't a power of two, is `runEngine`'s to refuse with exit 1, not a usage error. `--pin-matching` and `--pin-gateway` take numbers with commas between, and a core may repeat; how many there must be is `runEngine`'s to check. `--gateway-threads` takes a plain count up to 32 bits, as `--shards` does, defaults to 1, and is never derived from the machine; 0 is `runEngine`'s to refuse. `--log-dir` takes a path, and with none the engine runs with no log; it becomes required once the `engine` benchmark kind logs too. `--durability` takes `machine`, the default, or `process`, and `--log-ring` a size like the other rings, 65,536 records by default, which `runEngine` refuses unless it is a power of two. `--pin-log-writers` takes cores as the other pins do. `--max-connections` is per gateway thread. `--thread-priority` takes `normal` or `high`. `formatEngineSettings` prints every flag with its value, defaults included, in a fixed order (`--gateway-threads` after `--max-connections`, and `--log-dir`, `--durability`, and `--log-ring` after `--stop-grace`), and parses back to the same settings: it is the record each run prints first. Counts print plainly and byte sizes in their largest exact unit. The log directory and the pins print only when set, and the durability, log ring, and priority always. `engine_settings_tests` covers both.
- **Thread placement** (`thread_placement.hpp`). `pinThisThread(core)` and `setThisThreadPriority(priority)`, each on the calling thread, returning nothing once done or the system's reason for refusing. Pinning is `SetThreadAffinityMask` on Windows, so only the first processor group's 64 cores can be named, and `pthread_setaffinity_np` on Linux, up to `CPU_SETSIZE`. `HIGH` is `THREAD_PRIORITY_HIGHEST` on Windows and nice -10 on Linux through `setpriority` on the thread's own id, since Linux gives each thread its own nice value; `NORMAL` changes nothing. Other platforms refuse pinning and `HIGH`. `thread_placement_tests` reads each back through the system.
- **`AbortScope` and `describeAbort`** (`abort_report.hpp`). A matching thread holds an `AbortScope` naming its `Shard` once the shard is built, in a constant-initialized `thread_local`, and `describeAbort` writes the abort line for the calling thread into a caller's buffer: `order_book_engine: aborted: shard 2 symbol AAPL position 12345` from the shard's `lastProgress()` in a checked build, or `order_book_engine: aborted` with no scope or no checks. It formats digits by hand, cuts to fit, and allocates nothing, since `apps/`' SIGABRT handler calls it on the aborting thread. Reading the `thread_local` there is safe because `order_book_runtime` is a static library, linked into the executable, so its TLS needs no lazy allocation; made shared, it would need another way. Before a shard's first command it would name slot 0 at the first position.
- **`Shard`** (`shard.hpp`). A plain single-threaded object, with `MatchingLoop` a thin loop around it. `process(command, slot)` takes no origin, so replay and tests call exactly what the matching thread will, and leaves its events in one `CommandResult`, reserved at 512 trades and 1,024 events by the constructor. Anything larger still comes back whole. The position counts every command taken, a rejected one included. `resultGrowths()` counts commands that made the reused result reach the heap, found by comparing the capacities its public accessors expose before and after each command, so nothing in the public API changed for it, and a command that only refills what an earlier one grew isn't counted again. Checked builds record the slot and position before running, in `lastProgress()`, for the engine's abort handler to print when a book's own check aborts, and other builds pay nothing. `MatchingLoop`'s abort for an escaping exception has the element in hand and needs none of this. `checkInvariants` runs every book's own check, then that each slot maps back through the directory, then that the next log position is the first plus the commands taken, then, once `watchDurablePosition` has given it the shard's `DurablePosition`, that it never passes the next position and never goes back, from the first position or from what an earlier check saw, returning a `ShardViolation`. Matching never waits for the log, so a durable position behind the next one is sound. A durable position ahead of it is sound only mid-take, since a whole take reaches the log ring before any of it runs, so the check holds wherever no take is half run: at the end of a pass, at a stop, and wherever a test calls it. `shard_invariant_tests` breaks each part through `OrderBookTestAccess`, which `Shard` befriends too. `matching_path_allocation_tests` holds a warm shard to exactly zero heap calls on all eleven workloads, counted per thread in a replaced `operator new`, along with the `out` overloads for every type and time in force, a cascade, `replaceOrder`'s paths, in place, moved back, crossing, and post-only expiring, `cancelOrder`, and `encodeLogRecord`. It first shows the count can move, on a book past its capacity.
- **The interleaver** lives apart, in `order_book_reference` (`tests/reference/interleaver.hpp`), so that tests and benchmarks share one: see [`randomized-tests.md`](randomized-tests.md).
