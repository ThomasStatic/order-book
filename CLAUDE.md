# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A correctness-first C++20 limit-order-book and matching-engine library (`order_book` static lib), with a small demo CLI (`order_book_cli`) that prints a scripted session's events, and optional benchmarks. The storage layer (price levels, order index, snapshots) and price-time-priority matching via `submitOrder`, and cancellation via `cancelOrder` are implemented. `submitOrder` reports each submission as a `SubmissionResults`, and both commands return the lifecycle events they produced.

## Build and test

Out-of-source builds under `build/`. README documents Ninja:

```bash
cmake -S . -B build/debug -G Ninja -DCMAKE_BUILD_TYPE=Debug
cmake --build build/debug
ctest --test-dir build/debug --output-on-failure
```

On this machine `build/` is currently configured with the **Visual Studio 17 2022** multi-config generator, so pass the config explicitly:

```bash
cmake --build build --config Debug
ctest --test-dir build -C Debug --output-on-failure
```

Run a single test by CTest name with `-R` (names: `order_book_smoke`, `order_tests`, `result_type_tests`, `price_level_tests`, `execution_tests`, `matching_tests`, `cancellation_tests`, `submission_tests`, `event_tests`, `event_format_tests`, `allocation_failure_tests`, `invariant_tests`, `scenario_tests`, `randomized_seeds`, `randomized_regressions`, `randomized_harness_tests`, and `invariant_boundary_addOrder`/`_submitOrder`/`_cancelOrder`/`_consumeLevel`/`_cancelOrderThrows`), e.g. `ctest --test-dir build -C Debug -R price_level_tests --output-on-failure`, or build and run one target directly (`cmake --build build --config Debug --target price_level_tests`).

CMake options: `ORDER_BOOK_BUILD_BENCHMARKS`, `ORDER_BOOK_ENABLE_ASAN` (GCC/Clang/MSVC; on MSVC it strips `/RTC1` from Debug flags and copies `clang_rt.asan_dynamic-*.dll` next to each executable), `ORDER_BOOK_ENABLE_UBSAN` (GCC/Clang only, with `-fno-sanitize-recover` so a finding fails the test; ignored with a warning on MSVC), `ORDER_BOOK_WARNINGS_AS_ERRORS`, `ORDER_BOOK_INVARIANT_CHECKS` (`AUTO`, the default, checks the whole book after each public command only where `NDEBUG` is undefined, i.e. Debug; `ON` or `OFF` defines the macro of the same name as 1 or 0, PUBLIC, for every configuration). Warnings are high (`/W4`, or `-Wall -Wextra -Wpedantic -Wconversion -Wshadow`), so watch for sign/narrowing conversions.

CI (`.github/workflows/ci.yml`) runs on every push and pull request with `ORDER_BOOK_WARNINGS_AS_ERRORS=ON`: GCC and Clang Debug/Release and ASan+UBSan on Linux, MSVC Debug/Release and ASan on Windows. Code that builds cleanly with MSVC can still fail there on a GCC/Clang warning.

## Tests

- `execution_tests` drives single `executeOnce` steps; `matching_tests` drives the full `submitOrder` loop (both incoming sides, multi-order and multi-level sweeps, remainders, sequence numbering, a scripted replay for deterministic event ordering) and checks after each step that the book is consistent, uncrossed, and in sequence order within each level. `cancellation_tests` covers `cancelOrder` on both sides (only/oldest/middle/newest/partially filled orders, unknown and repeat IDs, aggregates, empty-level erasure, best-price transitions) and compares full captured before/after `BookState`s, including each surviving order's address, to show that unrelated state and FIFO positions are untouched.
- `submission_tests` covers submission acceptance and rejection: duplicate active IDs, reuse of cancelled and fully filled IDs, malformed orders (built by corrupting fields through `OrderBookTestAccess`, since the `Order` constructor refuses them), fully and partially filled incoming orders, multi-level sweeps, and `activeOrderCount` through a scripted sequence of events. Every rejection compares full captured before/after `BookState`s (levels, aggregates, order addresses, index, next sequence and trade IDs).
- `event_tests` checks the exact event vector each command returns: one `OrderRejected` for a refused submission; `OrderAccepted` (with the submitted, not post-fill, quantity) then one `TradeExecuted` per match in price-time order, with no resting event; only `OrderAccepted` from `addOrder`, which throws rather than rest a crossing order; one `OrderCancelled` with the remaining quantity or one `CancelRejected`. It also replays a scripted sequence of submits, adds, and cancels on two fresh books against a hand-worked stream. `event_format_tests` checks the printer's one-line text per event.
- `invariant_tests` checks `OrderBook::checkInvariants` directly. Sound books pass (scripted sessions, a level queued across a sequence wrap). Then each test breaks one structure through `OrderBookTestAccess` (an empty or misplaced level, a zero-quantity, malformed, misplaced, or reordered order, a stale aggregate, a missing, wrong, or stale index entry, a duplicate ID in one level or across sides, a crossed or locked book). Each checks the exact violation, side, price, order ID, and expected/actual values, plus that the checker stops at the first violation and how results are formatted. The ordering violations can't be produced through `std::map`, so they're untested. `invariant_boundary_tests` breaks a level's aggregate, runs the command named on its command line, and should abort there; `cancelOrderThrows` instead breaks an index entry so `cancelOrder` throws, and checks the boundary still aborts as the exception unwinds. It turns the expected `SIGABRT` into a normal exit (CTest otherwise fails any test killed by a signal), and CTest passes it on the abort message (`PASS_REGULAR_EXPRESSION`) and reports it Skipped in builds without automatic checks.
- `scenario_tests` runs longer command sequences through the public API, checking the whole book after every command: alternating buys and sells, hundreds of orders at one price and hundreds of levels per side, repeated partial fills of one maker, every order cancelled (and each cancel repeated) against a captured expected `BookState`, resubmission after cancellation (it loses time priority), emptying one side, refused commands mixed into a script (each leaves the book unchanged, and dropping them changes nothing else), maximal prices, IDs, and quantities, level aggregates at and beyond one `Quantity`, sequence and trade-ID wraps, and a 3000-command seeded script (its own LCG, so it is the same on every platform) replayed on fresh books with identical outcomes, checked against a ledger that follows each order's open quantity through the events alone.
- **Randomized command testing** (`tests/randomized/`, library `order_book_randomized`, CLI `randomized_tests`). This is seeded pseudorandom testing, not fuzzing; don't call it fuzzing. `RandomCommandGenerator` (`std::mt19937_64` raw output with its own unbiased `below`, never `std::*_distribution`) draws submissions and cancellations per a `WorkloadProfile` (`balanced` is the agreed 70/30 submit/cancel, 80/20 valid/invalid, 50/50 sides, near-touch prices, mostly small sizes; the others are `aggressive`, `passive`, `cancel-heavy`, `queue`, `one-sided`, `invalid-heavy`, `limits`). It reads only `ReferenceBook`, an independent plain model of the book, never the engine, so a stream depends only on seed + profile + `generatorVersion`. `CommandReplayer` runs each command against the book and the model, then checks, in order: an unexpected exception, `checkInvariants` (skipped when `invariantChecksAfterCommands`, since the command's boundary has just run it), the exact result and events against the model's prediction, and every level and FIFO queue against the model. It stops at the first failure; `CommandRecorder` then holds the executed prefix, which is saved and shrunk (`shrinkFailingStream`, ddmin to a 1-minimal stream) to `--out-dir`, and `formatFailureReport` prints seed, config, command index, command, failure, book/model state, preceding commands, and replay lines. With automatic checks on, the engine aborts first; `abort_reporter` then prints seed, command, and a reproduce line, and a Release / `ORDER_BOOK_INVARIANT_CHECKS=OFF` build gives the full report and shrinking. `randomized_harness_tests` pins a fingerprint of each profile's output: any change to what the generator draws or to a profile must bump `generatorVersion` and re-pin. Saved streams (`tests/randomized/regressions/*.txt`, replayed by `randomized_regressions`) are the durable regressions; the seed list in `randomized_main.cpp` is valid only for its generator version. Only `submitOrder` and `cancelOrder` are generated, not `addOrder`. `OrderBookTestAccess` is defined once, in `command_replayer.cpp`; don't define another in a file linked with `order_book_randomized`.
- The hand-written consistency helpers (`expectBookConsistent`/`expectIndexConsistent`) also assert `checkInvariants().isValid()`. A test that corrupts state on purpose must undo the corruption before calling one, and must not call a public command while the book is still corrupted: with automatic checks on, the command's boundary aborts. `execution_tests`' corrupted `consumeLevel` case therefore runs only when `invariantChecksAfterCommands` is false (e.g. Release).
- No test framework: each `tests/*.cpp` is its own executable with a `main()` using local `expect(cond, msg)` / `expectThrows(fn, msg)` helpers that print `FAILED:` and `exit(EXIT_FAILURE)`.
- Each test file needs its own `add_executable` + `order_book_enable_warnings` + `order_book_enable_sanitizers` + `add_test` block in `CMakeLists.txt`. New library `.cpp` files must be added to the `order_book` target source list.
- `tests/allocation_failure_test.cpp` replaces global `operator new` to fail each allocation in turn and checks the book stays consistent (e.g. `addOrder` rolls back, `cancelOrder` fails before removing anything). MSVC Debug builds' checked iterators allocate inside `noexcept` container members, so there it exits 77 and CTest reports it **Skipped**; run `cmake --build build --config Release` and `ctest --test-dir build -C Release` to exercise it.
- Tests reach private members only through the `OrderBookTestAccess` friend (declared in `OrderBook`, `PriceLevel`, and `Order`, and defined separately in each test executable that needs it), so keep those definitions in mind when renaming private members. Don't `#define private public`: redefining a keyword around standard headers is undefined behavior, Clang rejects it under `-Werror` (`-Wkeyword-macro`), and on MSVC it fails to link for member functions, since access level is part of the mangled name.

## Architecture

All code lives in namespace `order_book`; headers in `include/order_book/`, implementations in `src/`.

- **Prices are integer ticks** (`unsigned int`), assuming a fixed $0.01 tick size. IDs, sequence numbers, and quantities are also `unsigned int` (aliases `Price`, `Quantity`, `OrderId`, `TradeId`, `SequenceNum` in `types.hpp`), and zero is invalid for all of them. Field checks live once, in the private `Order::malformedReason()` (a zero ID, price, or remaining quantity, an invalid `Side`, or an unsupported `OrderType`; only `LIMIT` exists, and it is the default argument). The constructor throws `std::invalid_argument` on a zero sequence number or on any reason `malformedReason` returns, with that reason's `rejectionMessage` (one distinct message per `RejectionReason`, in `rejection_reason.hpp`).
- **Sequence numbers are assigned by the book**, from `OrderBook::nextSequenceNum`, via the private friend-only `Order::assignSequenceNum`; the value passed to the `Order` constructor is replaced on acceptance. They record acceptance order, which is what time priority within a level follows, and an order keeps its number for life (a resting remainder keeps the one it was given before matching). `submitOrder` consumes a number once validation passes, even if the order then fills completely or matching throws; `addOrder` consumes one only once the order has rested; rejected orders consume none. On overflow the counter wraps back to 1 (skipping zero) and numbers are silently reused; time priority within a level is queue position, so it is unaffected, but don't assume numbers are unique or increasing across a wrap. Internally, resting goes through private `restOrder` (no validation, no numbering) so the remainder isn't renumbered — don't route it back through `addOrder`.
- **`Order`** — tracks initial/remaining quantity and `FillStatus` (`NONE`/`PARTIAL`/`FILLED`); `fillQuantity` returns the unfilled leftover of the requested amount.
- **`PriceLevel`** — FIFO `std::list<Order>` at one price/side plus a cached aggregate `quantity`, a `std::uint64_t` (as is `PriceLevelSummary::totalQuantity`) so a level of many maximal orders cannot wrap it. `addOrder` returns an `OrderLocation`; `consumeQuantity` fills oldest-first, pops fully filled orders, and returns a `ConsumptionResult` (status, per-order `OrderFill`s, unfilled remainder). Note the status naming: `SATISFIED` means the level is now empty, `LEVEL_EXHAUSTED` means quantity still rests there. Any mutation must keep `quantity` in sync with the list. The private `fillOldestOrder` (fills one order, popping it if fully filled) is reserved for its friend `OrderBook`. Don't call `consumeQuantity` on a level inside a book directly — go through `OrderBook::consumeLevel` (multi-order fill at one level, currently used only by tests), which loops `fillOldestOrder` itself, unindexing each fully filled order the moment it leaves the level, and erases the level once empty.
- **`OrderBook`** — `bids` is `std::map<Price, PriceLevel, std::greater>` and `asks` is `std::map<..., std::less>`, so `begin()` is always best price on both sides. `orderIndex` (`unordered_map<OrderId, OrderLocation>`) gives O(1) cancel: `OrderLocation` stores price, side, and a `std::list<Order>::iterator` into the level's list (valid because `std::list` iterators are stable). `addOrder` and `submitOrder` both run the read-only `validateNewOrder` first. It returns a `RejectionReason`, checked in this order: `Order::malformedReason()` (rechecked because an order can be changed after it is built), a `FILLED` order, then an ID already resting (`DUPLICATE_ORDER_ID`). `addOrder` throws `std::invalid_argument` with that reason's `rejectionMessage`; `submitOrder` returns a REJECTED result. `addOrder` then also refuses an order at or through the best opposing price (`WOULD_CROSS_BOOK`, thrown the same way), since it never matches; so no public command leaves the book crossed. Either way nothing is mutated and no sequence number or trade ID is consumed. IDs of filled or cancelled orders may be reused, since the index tracks only live orders. `activeOrderCount()` is the number of resting orders (index entries), not of levels. `findActiveOrder`, `getBestBid`, and `getBestAsk` return `Order` copies (never a reference or iterator), so callers can neither mutate a resting order behind the level's cached `quantity` nor hold a reference that dangles once it is filled or removed; tests that need element identity use `OrderBookTestAccess::indexedOrder`. `OrderBook` is move-only: a copy would share the original's list iterators. `cancelOrder(id)` looks the order up in the index, takes its *remaining* quantity off the level aggregate, erases it from the list, unindexes it, and erases the level once empty. Its result (with its event, which allocates) is built before anything is mutated; once the lookup and a level-exists guard pass, nothing can throw; other orders keep their positions and iterators, and it consumes no sequence number or trade ID. An ID that is not resting (unknown, already cancelled, fully filled, or an incoming order that never rested) returns a rejected result (`ORDER_NOT_FOUND`) and leaves the book unchanged. Empty levels are erased on removal. `snapshot(depth)` returns top-N level summaries per side.
- **Matching** — `submitOrder` runs `matchOrder` (loops while the incoming order has quantity and crosses the best opposing price), then rests any remainder at its own limit price via `restOrder`. Each loop step is one private `executeOnce`: it executes min(incoming, resting) against the oldest order at the best opposing level, at the resting price, and returns exactly one `Trade`. It validates everything and builds the `Trade` before mutating, so a throw leaves the book unchanged — preserve that ordering. `matchOrder` makes room in its trade vector before each `executeOnce`, so recording a trade cannot throw after the book changed. `submitOrder` is not atomic: if an allocation fails mid-match, while building the result, or while resting the remainder, executions already made stand (the book stays consistent) and their trades and events are lost with the exception. The result, events included, is built *before* the remainder rests, so resting is the last step that can fail and a remainder never rests behind a throw; keep it that way. It unindexes the resting order only when fully filled (a partially filled one keeps its index entry and FIFO position) and erases the level once empty.
- **Result types** — `CancellationResult` (in `cancellation_results.hpp`) is what `cancelOrder` returns. Its constructor is private, so it is built only with `CancellationResult::cancelled(id, remaining)` (success, one `OrderCancelled`; throws on a zero ID or quantity) or `rejected(id, reason)` (one `CancelRejected`; echoes any ID; throws on `NONE`), and read through `isSuccess`, `getRejectionReason` (an `optional`), and `getEvents`. `submitOrder` and `addOrder` return `SubmissionResults`, whose `submissionId` is the incoming order's ID. Its constructors are private, so it is built only with `SubmissionResults::accepted`, which takes the `OrderAccepted` the book captured before matching (its `orderId` is the submission ID), throws `std::invalid_argument` on a zero quantity or price or unless every trade is for that order, on its side, and within its limit price and the traded quantities plus the remainder sum to the accepted quantity, and holds the trades and the remaining quantity and sets `FillStatus` to NONE if nothing traded, FILLED if nothing is left, PARTIAL otherwise, or with `rejected`, which holds a reason, no trades, `FillStatus::NONE`, and the submitted quantity as remaining. A rejection echoes the submitted ID even when it is the reserved 0; an accepted result requires a positive ID. Each `Trade` (in `SubmissionResults::getGeneratedTrades()`) stores resting (maker) and incoming (taker) IDs plus the incoming side, from which `getBuyOrderId`/`getSellOrderId` derive.
- **Lifecycle events** (`book_event.hpp`) — `BookEvent` is a `std::variant` of `OrderAccepted`, `OrderRejected`, `TradeExecuted`, `OrderCancelled`, `CancelRejected`, each a plain struct with defaulted `==`. They are domain output held in the command's result (`SubmissionResults::getEvents()`, `CancellationResult::getEvents()`), not logging. `SubmissionResults` derives them in its factories, so its event rules hold by construction: `rejected` holds exactly one `OrderRejected`; `accepted` holds the `OrderAccepted` then one `TradeExecuted` (incoming/resting IDs, resting price, quantity) per trade in execution order; there is no resting event. `CancellationResult`'s factories likewise hold exactly one `OrderCancelled` (`cancelOrder` passes the remaining quantity at cancel time) or one `CancelRejected` (reusing `RejectionReason`). `addOrder` never matches, so its result holds only its `OrderAccepted`; it still throws on a rejection rather than returning one. Printing is separate: `formatEvent` (`event_format.hpp`) turns an event into one line of text, and only callers (the CLI) use it; the engine never prints events. Its only output of any kind is the line a failed invariant boundary writes to stderr just before `std::abort` (see Invariants).
- **Invariants** (`invariants.hpp`, `src/order_book_invariants.cpp`) — `checkInvariants()` (public, `const noexcept`, never allocates) makes one O(N + L) pass and returns an `InvariantResult`. The result holds the first `InvariantViolation` found (none if the book is sound), plus the side, price, order ID, expected/actual values, and a string-literal `detail`; `formatInvariantResult` prints it on one line. The pass checks bids, then asks: level ordering, each level's own price and side, non-empty levels, then each order (quantity left, well formed via `malformedReason`, not FILLED, sequence number set, at its level's price and side, FIFO by sequence). Sequence order is judged by `sequenceAge`, relative to `nextSequenceNum`, so a level queued across a wrap passes. Then each level's aggregate. Next, the index: every resting order needs an entry naming its side, price, and list position, with no ID resting twice. Any extra entry is stale and is found by key and recorded place alone, without using its possibly dangling iterator. Last, best bid must be strictly below best ask. A broken invariant is an engine bug, not a caller error. Each public command that can mutate (`addOrder`, `submitOrder`, `cancelOrder`, `consumeLevel`) starts with an `InvariantBoundary` guard. When `invariantChecksAfterCommands` is set (from `ORDER_BOOK_INVARIANT_CHECKS`), the guard's destructor runs `enforceInvariants` once the command returns or throws. On failure that prints `order book invariant violated after <command>: <result>` to stderr and calls `std::abort`. Private steps (`executeOnce`, `restOrder`, `matchOrder`) are not boundaries: structures may be out of step between them. A new public mutating command needs the guard too.
- Errors are currently signaled via exceptions (`std::invalid_argument` / `std::runtime_error`); `getBestBid`/`getBestAsk` throw `std::runtime_error` on an empty side. The exceptions are `cancelOrder`, which reports a non-resting ID as a value (a rejected result with `ORDER_NOT_FOUND`) and throws only on internal inconsistency (an indexed order whose level is missing) or allocation failure (before anything is mutated), and `submitOrder`, which reports rejections as values and throws only on internal inconsistency or allocation failure. With automatic invariant checks on, every public mutating command also checks the book as an exception unwinds through it, so an internal-inconsistency throw the checker can see (such as `cancelOrder`'s missing-level case) aborts there instead of reaching the caller. Allocation failures leave the book sound, so they still propagate.
