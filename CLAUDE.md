# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A correctness-first C++20 limit-order-book and matching-engine library (`order_book` static lib), with a small non-interactive CLI (`order_book_cli`: `replay <file.csv> [--trades] [--events] [--book] [--validate none|final|per-command]` replays a CSV command file through library `order_book_replay` and prints its statistics; `demo` prints a scripted session's events; `--help`; no arguments is a usage error), and optional benchmarks (`order_book_benchmarks`, see Tests). The storage layer (price levels, order index, snapshots) and price-time-priority matching via `submitOrder`, and cancellation via `cancelOrder` are implemented. `submitOrder` reports each submission as a `SubmissionResult`, and both commands return the lifecycle events they produced. Released as `v1.0.0` (the CMake project version); README's "Public API" section lists which headers are the API and which are implementation detail, so treat changes to the former as breaking.

## Build and test

Out-of-source builds under `build/`. README documents Ninja:

```bash
cmake -S . -B build/debug -G Ninja -DCMAKE_BUILD_TYPE=Debug
cmake --build build/debug
ctest --test-dir build/debug --output-on-failure
```

On this machine `build/` is currently configured with the **Visual Studio 17 2022** multi-config generator, so pass the config explicitly:

```bash
cmake --build build --config Debug
ctest --test-dir build -C Debug --output-on-failure
```

Run a single test by CTest name with `-R` (names: `order_book_smoke`, `order_tests`, `result_type_tests`, `small_vector_tests`, `node_pool_tests`, `order_index_tests`, `price_level_tests`, `execution_tests`, `matching_tests`, `cancellation_tests`, `submission_tests`, `event_tests`, `event_format_tests`, `allocation_failure_tests`, `invariant_tests`, `scenario_tests`, `replay_parser_tests`, `replay_engine_tests`, `replay_cli_<sample>` (e.g. `replay_cli_basic`; `-R replay` runs all replay tests), `randomized_seeds`, `randomized_regressions`, `randomized_harness_tests`, `invariant_boundary_addOrder`/`_submitOrder`/`_cancelOrder`/`_consumeLevel`/`_cancelOrderThrows`, and, only with `ORDER_BOOK_BUILD_BENCHMARKS=ON`, `benchmark_harness_tests` and `benchmark_cli_smoke`), e.g. `ctest --test-dir build -C Debug -R price_level_tests --output-on-failure`, or build and run one target directly (`cmake --build build --config Debug --target price_level_tests`).

CMake options: `ORDER_BOOK_BUILD_BENCHMARKS`, `ORDER_BOOK_ENABLE_ASAN` (GCC/Clang/MSVC; on MSVC it strips `/RTC1` from Debug flags and copies `clang_rt.asan_dynamic-*.dll` next to each executable), `ORDER_BOOK_ENABLE_UBSAN` (GCC/Clang only, with `-fno-sanitize-recover` so a finding fails the test; ignored with a warning on MSVC), `ORDER_BOOK_WARNINGS_AS_ERRORS`, `ORDER_BOOK_INVARIANT_CHECKS` (`AUTO`, the default, checks the whole book after each public command only where `NDEBUG` is undefined, i.e. Debug; `ON` or `OFF` defines the macro of the same name as 1 or 0, PUBLIC, for every configuration). Warnings are high (`/W4`, or `-Wall -Wextra -Wpedantic -Wconversion -Wshadow`), so watch for sign/narrowing conversions.

CI (`.github/workflows/ci.yml`) runs on every push and pull request with `ORDER_BOOK_WARNINGS_AS_ERRORS=ON`: on Linux, GCC and Clang Debug/Release, GCC and Clang ASan+UBSan Debug, and Clang ASan+UBSan RelWithDebInfo; on Windows, MSVC Debug/Release and ASan Debug/Release. A new push to a pull request cancels that pull request's run still in progress; push runs are never cancelled. Code that builds cleanly with MSVC can still fail there on a GCC/Clang warning.

## Tests

- `execution_tests` drives single `executeOnce` steps; `matching_tests` drives the full `submitOrder` loop (both incoming sides, multi-order and multi-level sweeps, remainders, sequence numbering, a scripted replay for deterministic event ordering) and checks after each step that the book is consistent, uncrossed, and in sequence order within each level. `cancellation_tests` covers `cancelOrder` on both sides (only/oldest/middle/newest/partially filled orders, unknown and repeat IDs, aggregates, empty-level erasure, best-price transitions) and compares full captured before/after `BookState`s, including each surviving order's address, to show that unrelated state and FIFO positions are untouched.
- `submission_tests` covers submission acceptance and rejection: duplicate active IDs, reuse of cancelled and fully filled IDs, malformed orders (built by corrupting fields through `OrderBookTestAccess`, since the `Order` constructor refuses them), fully and partially filled incoming orders, multi-level sweeps, and `activeOrderCount` through a scripted sequence of events. Every rejection compares full captured before/after `BookState`s (levels, aggregates, order addresses, index, next sequence and trade IDs).
- `event_tests` checks the exact event vector each command returns: one `OrderRejected` for a refused submission; `OrderAccepted` (with the submitted, not post-fill, quantity) then one `TradeExecuted` per match in price-time order, with no resting event; only `OrderAccepted` from `addOrder`, which throws rather than rest a crossing order; one `OrderCancelled` with the remaining quantity or one `CancelRejected`. It also replays a scripted sequence of submits, adds, and cancels on two fresh books against a hand-worked stream. `event_format_tests` checks the printer's one-line text per event.
- `invariant_tests` checks `OrderBook::checkInvariants` directly. Sound books pass (scripted sessions, a level queued across a sequence wrap). Then each test breaks one structure through `OrderBookTestAccess` (an empty or misplaced level, a zero-quantity, malformed, misplaced, or reordered order, a stale aggregate, a missing, wrong, or stale index entry, a duplicate ID in one level or across sides, a crossed or locked book). Each checks the exact violation, side, price, order ID, and expected/actual values, plus that the checker stops at the first violation and how results are formatted. The ordering violations can't be produced through `std::map`, so they're untested. `invariant_boundary_tests` breaks a level's aggregate, runs the command named on its command line, and should abort there; `cancelOrderThrows` instead breaks an index entry so `cancelOrder` throws, and checks the boundary still aborts as the exception unwinds. It turns the expected `SIGABRT` into a normal exit (CTest otherwise fails any test killed by a signal), and CTest passes it on the abort message (`PASS_REGULAR_EXPRESSION`) and reports it Skipped in builds without automatic checks.
- `scenario_tests` runs longer command sequences through the public API, checking the whole book after every command: alternating buys and sells, hundreds of orders at one price and hundreds of levels per side, repeated partial fills of one maker, every order cancelled (and each cancel repeated) against a captured expected `BookState`, resubmission after cancellation (it loses time priority), emptying one side, refused commands mixed into a script (each leaves the book unchanged, and dropping them changes nothing else), maximal prices, IDs, and quantities, level aggregates at and beyond one `Quantity`, sequence and trade-ID wraps, and a 3000-command seeded script (its own LCG, so it is the same on every platform) replayed on fresh books with identical outcomes, checked against a ledger that follows each order's open quantity through the events alone.
- **Randomized command testing** (`tests/randomized/`, library `order_book_randomized`, CLI `randomized_tests`). This is seeded pseudorandom testing, not fuzzing; don't call it fuzzing. `RandomCommandGenerator` (`std::mt19937_64` raw output with its own unbiased `below`, never `std::*_distribution`) draws submissions and cancellations per a `WorkloadProfile` (`balanced` is the agreed 70/30 submit/cancel, 80/20 valid/invalid, 50/50 sides, near-touch prices, mostly small sizes; the others are `aggressive`, `passive`, `cancel-heavy`, `queue`, `one-sided`, `invalid-heavy`, `limits`). It reads only `ReferenceBook`, an independent plain model of the book, never the engine, so a stream depends only on seed + profile + `generatorVersion`. `CommandReplayer` runs each command against the book and the model, then checks, in order: an unexpected exception, `checkInvariants` (skipped when `invariantChecksAfterCommands`, since the command's boundary has just run it), the exact result and events against the model's prediction, and every level and FIFO queue against the model. It stops at the first failure; `CommandRecorder` then holds the executed prefix, which is saved and shrunk (`shrinkFailingStream`, ddmin to a 1-minimal stream) to `--out-dir`, and `formatFailureReport` prints seed, config, command index, command, failure, book/model state, preceding commands, and replay lines. With automatic checks on, the engine aborts first; `abort_reporter` then prints seed, command, and a reproduce line, and a Release / `ORDER_BOOK_INVARIANT_CHECKS=OFF` build gives the full report and shrinking. `randomized_harness_tests` pins a fingerprint of each profile's output: any change to what the generator draws or to a profile must bump `generatorVersion` and re-pin. Make each random draw in its own statement, never as two arguments of one call or two operands of one operator other than `&&`, `||`, `?:`, or `,`: their evaluation order is unspecified, so the stream would differ between compilers (GCC and MSVC evaluate arguments right to left, Clang left to right). Saved streams (`tests/randomized/regressions/*.txt`, replayed by `randomized_regressions`) are the durable regressions; the seed list in `randomized_main.cpp` is valid only for its generator version. Only `submitOrder` and `cancelOrder` are generated, not `addOrder`. `OrderBookTestAccess` is defined once, in `command_replayer.cpp`; don't define another in a file linked with `order_book_randomized`.
- **Replay format** (`docs/replay-format.md`): a six-column CSV of `ADD`/`CANCEL` commands for replaying a session. Parser, replay engine, and book are separate layers, and the book knows nothing about CSV. `ADD` maps to `submitOrder`, never `addOrder`. A well-formed row the book refuses is a rejection event, and the replay continues. Any parse error stops the replay (exit 1) with no rollback. Numbers are digits only, leading zeros ignored (`000123` is 123), zero refused in every column. The parser (`replay_parser.hpp`, namespace `order_book::replay`) is its own library, `order_book_replay`, so don't add it to `order_book`; it never sees an `OrderBook` or opens a file. `parseRow(CsvRow, previousSequence)` is pure and returns a `ReplayRecord` or the first `ParseError` (line, `ParseErrorCode`, column, value, message) in the spec's checking order; `ReplayReader` feeds it from a `std::istream` (open files binary, or CRs vanish on Windows) and is sticky after an error or the end. It reads the stream in chunks (`readsome`, then `peek` to fetch more, so bytes delivered before a stream failure are kept), splits each line into one reused `CsvRow` with `splitRecordInto`, and so allocates nothing per record; it may read up to a chunk ahead of what it has returned, so give it a stream of its own. Its optional chunk size exists for tests, which read every input with tiny chunks to put boundaries inside records. The engine (`replay_engine.hpp`, same library and namespace, spec in `docs/replay-format.md`) reads a file into the records before its first error (`readReplayFile` → `ReplayInput`), then `ReplayEngine::run(records, book, options)` dispatches them in order and returns a `ReplayResult` (line-tagged events, `ReplayStatistics`, full-depth `BookSnapshot`) or a `ReplayError`, so a parse error still runs the prefix before it. `ReplayOptions::invariantValidation` (`NONE`/`FINAL`, the default/`PER_COMMAND`) is its own `checkInvariants` call, separate from the book's aborting boundary; tests that run a command on a deliberately broken book therefore run only when `invariantChecksAfterCommands` is false. Printing is `replay_summary.hpp` (`formatReplayStatistics`, `formatFinalBook`, and `formatReplaySummary`, the two together), kept locale-free and in fixed order so output is byte-identical everywhere; the CLI sets stdout and stderr to binary on Windows for the same reason. `tests/replay/valid/` and `tests/replay/malformed/` hold the agreed samples, and `tests/replay/README.md` lists each one's expected events or line/column/rule. `replay_parser_tests` (`tests/replay_parser_test.cpp`) reads every sample and fails on one it has no expectation for. `replay_engine_tests` (`tests/replay_engine_test.cpp`) replays every sample too, failing on any file in `valid/` it doesn't list (`.csv` or not), but it gives a malformed file it doesn't list the usual layout's expectation (stops at line 4 after two commands), so it checks that file wrongly rather than failing. A new valid sample needs entries in both tests and in the `replay_cli_*` `foreach` list in `CMakeLists.txt`, plus an `expected/<name>.stdout` (the full `--events --book` output); a new malformed sample needs a parser-test entry, and an engine-test entry unless it fits the usual layout. `tests/replay/expected/` holds the CLI's exact stdout/stderr per case, compared by `tests/replay/check_cli_output.cmake`; a new CLI case (an option, a usage error, help) is one `order_book_add_replay_cli_test` call in `CMakeLists.txt` (any CLI arguments, exit status, and optional expected stdout/stderr; a stream without one must be empty), and its expected files are written by hand from the README's events, not captured from the CLI. Samples and expected files are byte-exact (`-text`), so don't let an editor normalize them.
- **Benchmarks** (`benchmarks/`, library `order_book_benchmarking`, which links `order_book_replay`; CLI `order_book_benchmarks`; methodology in `benchmarks/README.md`). Five built-in workloads (`small-book`, `deep-book`, `matching-heavy`, `cancellation-heavy`, `mostly-resting`) and three sizes (smoke 10k, standard 100k, extended 1M timed commands). `generateWorkload` builds the whole workload (preload, timed commands, predicted `WorkloadOutcome`) before anything is timed, from its own `WorkloadModel`, never an `OrderBook`, with the same RNG rules as the randomized harness (raw `mt19937_64`, own `below`, one draw per statement). `benchmark_harness_tests` pins each workload's fingerprint at the smoke size, so any change to what is generated must bump `workloadGeneratorVersion` and re-pin. The mixes are tuned so each book keeps its shape from 10k to 1M commands (see the comment above `makeWorkloads`), so re-check final orders and levels at every size after changing one. Each run reserves the book's index for `expectedBookSize` (preload or predicted final count, recorded as `reserved_orders`) before the untimed preload, so the baseline's mostly-resting numbers predate that. `runOnce` times only the timed commands: `core` calls `submitOrder`/`cancelOrder` directly, and `replay` parses in-memory CSV through `ReplayEngine` with validation `NONE`. It throws if the book's outcome differs from the prediction. The program exits 3 in a build that is not optimized (no `NDEBUG`, automatic invariant checks, ASan, or UBSan, which CMake reports through `ORDER_BOOK_UNDEFINED_SANITIZER` since GCC defines no macro for it) unless given `--allow-unoptimized`, which the CTest smoke run passes. The recorded baseline is `docs/BENCHMARKS.md`, from the raw output in `benchmarks/results/2026-10-25-baseline/` (its `summarize.py` recomputes the tables). It reports per-run throughput only: the harness never times a single command, so don't add per-command latency percentiles or low-latency claims, and don't compare with production exchanges.
- **Profiling** (`benchmarks/profiling/`, option `ORDER_BOOK_BUILD_PROFILING`, which needs the benchmarks; README there). `sampling_profiler` (Windows x64 only, dbghelp) profiles the benchmark program from outside, with inline frames, and writes a report plus folded stacks; `allocation_profile` counts allocations per command kind exactly, by replacing global `operator new`. Build them in a Release configuration with symbols added (`build/profile`, flags in the README), never in Debug. The baseline's profile is `benchmarks/results/2026-10-26-profile/` and its write-up, with the bottleneck hypotheses, is `docs/PROFILING.md`; `docs/OPTIMIZATION-EXPERIMENTS.md` designs one experiment per candidate change (bottleneck, hypothesis, predicted workloads, risks, readability cost, success measurement) and the shared measurement protocol, and records which were run and what they showed; `docs/OPTIMIZATION.md` is the report on them, with the final code's profile in `benchmarks/results/2026-10-26-final-profile/` (its README has the commands: since the node pool, `~OrderBook` is inlined into `runCore`, so profiles of current code need two more `--drop`s to exclude destroying the book). Shares in a report come from one run; identical-code folding can mislabel a frame (the results' event-vector destructor shows as `~vector<BenchmarkCommand>`), and `ntdll` internals resolve to the nearest export.
- The hand-written consistency helpers (`expectBookConsistent`/`expectIndexConsistent`) also assert `checkInvariants().isValid()`. A test that corrupts state on purpose must undo the corruption before calling one, and must not call a public command while the book is still corrupted: with automatic checks on, the command's boundary aborts. `execution_tests`' corrupted `consumeLevel` case therefore runs only when `invariantChecksAfterCommands` is false (e.g. Release).
- No test framework: each `tests/*.cpp` is its own executable with a `main()` using local `expect(cond, msg)` / `expectThrows(fn, msg)` helpers that print `FAILED:` and `exit(EXIT_FAILURE)`.
- Each test file needs its own `add_executable` + `order_book_enable_warnings` + `order_book_enable_sanitizers` + `add_test` block in `CMakeLists.txt`. New `.cpp` files of the `order_book` library must be added to its target source list (the replay parser and engine are deliberately in their own library, `order_book_replay`).
- `tests/allocation_failure_test.cpp` replaces global `operator new` to fail each allocation in turn and checks the book stays consistent (e.g. `addOrder` and a resting `submitOrder` roll back, a six-trade sweep that outgrows the result's inline storage leaves every execution made standing and no remainder resting). It also pins that `cancelOrder` never allocates, whether it cancels an order or refuses. MSVC Debug builds' checked iterators allocate inside `noexcept` container members, so there it exits 77 and CTest reports it **Skipped**; run `cmake --build build --config Release` and `ctest --test-dir build -C Release` to exercise it.
- Tests reach private members only through the `OrderBookTestAccess` friend (declared in `OrderBook`, `PriceLevel`, and `Order`, and defined separately in each test executable that needs it), so keep those definitions in mind when renaming private members. Don't `#define private public`: redefining a keyword around standard headers is undefined behavior, Clang rejects it under `-Werror` (`-Wkeyword-macro`), and on MSVC it fails to link for member functions, since access level is part of the mangled name.

## Architecture

All code lives in namespace `order_book`; headers in `include/order_book/`, implementations in `src/`.

- **Prices are integer ticks** (`unsigned int`), assuming a fixed $0.01 tick size. IDs, sequence numbers, and quantities are also `unsigned int` (aliases `Price`, `Quantity`, `OrderId`, `TradeId`, `SequenceNum` in `types.hpp`, which public signatures use rather than `unsigned int`), and zero is invalid for all of them. Field checks live once, in the private `Order::malformedReason()` (a zero ID, price, or remaining quantity, an invalid `Side`, or an unsupported `OrderType`; only `LIMIT` exists, and it is the default argument). The constructor throws `std::invalid_argument` on a zero sequence number or on any reason `malformedReason` returns, with that reason's `rejectionMessage` (one distinct message per `RejectionReason`, in `rejection_reason.hpp`).
- **Sequence numbers are assigned by the book**, from `OrderBook::nextSequenceNum`, via the private friend-only `Order::assignSequenceNum`; the value passed to the `Order` constructor is replaced on acceptance. They record acceptance order, which is what time priority within a level follows, and an order keeps its number for life (a resting remainder keeps the one it was given before matching). `submitOrder` consumes a number once validation passes, even if the order then fills completely or matching throws; `addOrder` consumes one only once the order has rested; rejected orders consume none. On overflow the counter wraps back to 1 (skipping zero) and numbers are silently reused; time priority within a level is queue position, so it is unaffected, but don't assume numbers are unique or increasing across a wrap. Internally, resting goes through private `restOrder` (no validation, no numbering) so the remainder isn't renumbered — don't route it back through `addOrder`.
- **`Order`** — tracks initial/remaining quantity and `FillStatus` (`NONE`/`PARTIAL`/`FILLED`, read and set with `getFillStatus`/`setFillStatus`; `isActive` means anything but `FILLED`); `fillQuantity` returns the unfilled leftover of the requested amount.
- **`PriceLevel`** — FIFO `OrderQueue` (`std::list<Order, PoolAllocator<Order>>`, in `order_location.hpp`) at one price/side plus a cached aggregate `quantity`, a `std::uint64_t` (as is `PriceLevelSummary::totalQuantity`; its `orderCount` and `PriceLevel::getOrderCount` count orders, not quantity) so a level of many maximal orders cannot wrap it. `addOrder` returns an `OrderLocation`. Any mutation must keep `quantity` in sync with the list. The private `fillOldestOrder` (fills one order, popping it if fully filled) is reserved for its friend `OrderBook` (and tests). `OrderBook`'s private `consumeLevel` (multi-order fill at one level; it makes no trades and no events, so it is not a public command, and tests reach it through `OrderBookTestAccess`) loops `fillOldestOrder`, unindexing each fully filled order the moment it leaves the level, erases the level once empty, and returns a `ConsumptionResult` (status, per-order `OrderFill`s, unfilled remainder). Note the status naming: `SATISFIED` means the level is now empty, `LEVEL_EXHAUSTED` means quantity still rests there.
- **`OrderBook`** — `bids` is `std::map<Price, PriceLevel, std::greater>` and `asks` is `std::map<..., std::less>`, so `begin()` is always best price on both sides. `orderIndex` (an `OrderIndex`, `order_index.hpp`: an open-addressed table of `pair<OrderId, OrderLocation>`, linear probing with a Fibonacci hash, at most three quarters full, backward-shift erase, ID 0 reserved as the empty marker so it cannot be emplaced; any emplace or erase may move entries and invalidates iterators, and iteration order is unspecified; tested against `std::unordered_map` by `order_index_tests`) gives O(1) cancel: `OrderLocation` stores price, side, an `OrderQueue::iterator` into the level's list (valid because `std::list` iterators are stable), and a `PriceLevel*` to the level itself (valid because `std::map` never moves its elements and a level is erased only once empty), so `cancelOrder` reaches the level without searching the map; it checks that the handle names a level at the entry's price and side, and `checkInvariants` compares (never follows) it. `addOrder` and `submitOrder` both run the read-only `validateNewOrder` first. It returns a `RejectionReason`, checked in this order: `Order::malformedReason()` (rechecked because an order can be changed after it is built), a `FILLED` order, then an ID already resting (`DUPLICATE_ORDER_ID`). `addOrder` throws `std::invalid_argument` with that reason's `rejectionMessage`; `submitOrder` returns a REJECTED result. `addOrder` then also refuses an order at or through the best opposing price (`WOULD_CROSS_BOOK`, thrown the same way), since it never matches; so no public command leaves the book crossed. Either way nothing is mutated and no sequence number or trade ID is consumed. IDs of filled or cancelled orders may be reused, since the index tracks only live orders. `activeOrderCount()` is the number of resting orders (index entries), not of levels. `reserve(n)` is a capacity hint that sizes the index for `n` resting orders so it does not rehash while the book grows; it changes nothing the book reports, so it is the one non-const public member without an `InvariantBoundary`. `findActiveOrder`, `getBestBid`, and `getBestAsk` return `Order` copies (never a reference or iterator), so callers can neither mutate a resting order behind the level's cached `quantity` nor hold a reference that dangles once it is filled or removed; tests that need element identity use `OrderBookTestAccess::indexedOrder`. `OrderBook` is move-only: a copy would share the original's list iterators. `cancelOrder(id)` looks the order up in the index, takes its *remaining* quantity off the level aggregate, erases it from the list, unindexes it, and erases the level once empty. Its result is built before anything is mutated, and allocates nothing (its one event is held inline); once the lookup and a guard that the entry's level handle names a level at its price and side pass, nothing can throw; other orders keep their positions and iterators, and it consumes no sequence number or trade ID. An ID that is not resting (unknown, already cancelled, fully filled, or an incoming order that never rested) returns a rejected result (`ORDER_NOT_FOUND`) and leaves the book unchanged. Empty levels are erased on removal. `snapshot(depth)` returns top-N level summaries per side.
- **Node pool** (`node_pool.hpp`) — every level's queue takes its nodes from the book's `NodePool` (`std::unique_ptr` member declared first, so it outlives the levels and keeps its address when the book moves), through `PoolAllocator`, which falls back to the heap for arrays, for sizes beyond the pool's few size classes, and when it has no pool (a level built outside a book, or by a moved-from book). Freed blocks go on a per-size free list and are reused; chunks are freed only with the book, so a book keeps its peak node memory. Map nodes still use the heap; the index allocates only when its table grows. `OrderBook`'s move assignment is hand-written (clear, then take the other's members, pool last), so a new member must be added there. The pool's chunks come from plain `operator new` whenever the alignment allows, so the allocation-failure tests and allocation counters see them; on a book that already holds an order the pool usually has blocks to spare, so only `testFirstOrderOnEmptyBookRollsBack` makes a queue node's allocation fail.
- **Matching** — `submitOrder` runs `matchOrder` (loops while the incoming order has quantity and crosses the best opposing price), then rests any remainder at its own limit price via `restOrder`. Each loop step is one private `executeOnce`: it executes min(incoming, resting) against the oldest order at the best opposing level, at the resting price, and returns exactly one `Trade`. It validates everything and builds the `Trade` before mutating, so a throw leaves the book unchanged — preserve that ordering. `matchOrder` makes room in its trade vector before each `executeOnce`, so recording a trade cannot throw after the book changed. `submitOrder` is not atomic: if an allocation fails mid-match, while building the result, or while resting the remainder, executions already made stand (the book stays consistent) and their trades and events are lost with the exception. The result, events included, is built *before* the remainder rests, so resting is the last step that can fail and a remainder never rests behind a throw; keep it that way. It unindexes the resting order only when fully filled (a partially filled one keeps its index entry and FIFO position) and erases the level once empty.
- **Result types** — Results hold their events and trades in `SmallVector<T, N>` (`small_vector.hpp`): trivially copyable elements, `N` inline, heap only beyond (`SubmissionTrades` 4, `SubmissionEvents` 5, `CancellationEvents` 1), so a command's result allocates nothing unless it makes more than four trades. The getters return those types: they iterate, index, compare equal with a `std::vector`, and bind to `std::span<const T>`; a `std::vector` copy is `toVector()`, never implicit. It is not a drop-in `std::vector` (no erase, insert, clear, or resize), and moving a result whose elements are inline copies them, so don't hold pointers into a result across a move. `CancellationResult` (in `cancellation_results.hpp`) is what `cancelOrder` returns. Its constructor is private, so it is built only with `CancellationResult::cancelled(id, remaining)` (success, one `OrderCancelled`; throws on a zero ID or quantity) or `rejected(id, reason)` (one `CancelRejected`; echoes any ID; throws on `NONE`), and read through `isSuccess`, `getRejectionReason` (an `optional`), and `getEvents`. `submitOrder` and `addOrder` return `SubmissionResult`, whose `submissionId` is the incoming order's ID. Its constructors are private, so it is built only with `SubmissionResult::accepted`, which takes the `OrderAccepted` the book captured before matching (its `orderId` is the submission ID), throws `std::invalid_argument` on a zero quantity or price or unless every trade is for that order, on its side, and within its limit price and the traded quantities plus the remainder sum to the accepted quantity, and holds the trades and the remaining quantity and sets `FillStatus` to NONE if nothing traded, FILLED if nothing is left, PARTIAL otherwise, or with `rejected`, which holds a reason, no trades, `FillStatus::NONE`, and the submitted quantity as remaining. A rejection echoes the submitted ID even when it is the reserved 0; an accepted result requires a positive ID. Each `Trade` (in `SubmissionResult::getGeneratedTrades()`) stores resting (maker) and incoming (taker) IDs plus the incoming side, from which `getBuyOrderId`/`getSellOrderId` derive.
- **Lifecycle events** (`book_event.hpp`) — `BookEvent` is a `std::variant` of `OrderAccepted`, `OrderRejected`, `TradeExecuted`, `OrderCancelled`, `CancelRejected`, each a plain struct with defaulted `==`. They are domain output held in the command's result (`SubmissionResult::getEvents()`, `CancellationResult::getEvents()`), not logging. `SubmissionResult` derives them in its factories, so its event rules hold by construction: `rejected` holds exactly one `OrderRejected`; `accepted` holds the `OrderAccepted` then one `TradeExecuted` (incoming/resting IDs, resting price, quantity) per trade in execution order; there is no resting event. `CancellationResult`'s factories likewise hold exactly one `OrderCancelled` (`cancelOrder` passes the remaining quantity at cancel time) or one `CancelRejected` (reusing `RejectionReason`). `addOrder` never matches, so its result holds only its `OrderAccepted`; it still throws on a rejection rather than returning one. Printing is separate: `formatEvent` (`event_format.hpp`) turns an event into one line of text, and only callers (the CLI) use it; the engine never prints events. Its only output of any kind is the line a failed invariant boundary writes to stderr just before `std::abort` (see Invariants).
- **Invariants** (`invariants.hpp`, `src/order_book_invariants.cpp`) — `checkInvariants()` (public, `const noexcept`, never allocates) makes one O(N + L) pass and returns an `InvariantResult`. The result holds the first `InvariantViolation` found (none if the book is sound), plus the side, price, order ID, expected/actual values, and a string-literal `detail`; `formatInvariantResult` prints it on one line. The pass checks bids, then asks: level ordering, each level's own price and side, non-empty levels, then each order (quantity left, well formed via `malformedReason`, not FILLED, sequence number set, at its level's price and side, FIFO by sequence). Sequence order is judged by `sequenceAge`, relative to `nextSequenceNum`, so a level queued across a wrap passes. Then each level's aggregate. Next, the index: every resting order needs an entry naming its side, price, and list position, with no ID resting twice. Any extra entry is stale and is found by key and recorded place alone, without using its possibly dangling iterator. Last, best bid must be strictly below best ask. A broken invariant is an engine bug, not a caller error. Each command that can mutate (the public `addOrder`, `submitOrder`, and `cancelOrder`, and the private, test-only `consumeLevel`) starts with an `InvariantBoundary` guard. When `invariantChecksAfterCommands` is set (from `ORDER_BOOK_INVARIANT_CHECKS`), the guard's destructor runs `enforceInvariants` once the command returns or throws. On failure that prints `order book invariant violated after <command>: <result>` to stderr and calls `std::abort`. Private steps (`executeOnce`, `restOrder`, `matchOrder`) are not boundaries: structures may be out of step between them. A new public mutating command needs the guard too.
- Errors are currently signaled via exceptions (`std::invalid_argument` / `std::runtime_error`); `getBestBid`/`getBestAsk` throw `std::runtime_error` on an empty side. The exceptions are `cancelOrder`, which reports a non-resting ID as a value (a rejected result with `ORDER_NOT_FOUND`) and throws only on internal inconsistency (an index entry whose level handle does not name a level at its price and side), since it never allocates, and `submitOrder`, which reports rejections as values and throws only on internal inconsistency or allocation failure. With automatic invariant checks on, every public mutating command also checks the book as an exception unwinds through it, so an internal-inconsistency throw the checker can see (such as `cancelOrder`'s missing-level case) aborts there instead of reaching the caller. Allocation failures leave the book sound, so they still propagate.
