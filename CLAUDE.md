# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A correctness-first C++20 limit-order-book and matching-engine library (`order_book` static lib), with a small demo CLI (`order_book_cli`) that prints a scripted session's events, and optional benchmarks. The storage layer (price levels, order index, snapshots) and price-time-priority matching via `submitOrder`, and cancellation via `cancelOrder` are implemented. `submitOrder` reports each submission as a `SubmissionResults`, and both commands return the lifecycle events they produced.

## Build and test

Out-of-source builds under `build/`. README documents Ninja:

```bash
cmake -S . -B build/debug -G Ninja -DCMAKE_BUILD_TYPE=Debug
cmake --build build/debug
ctest --test-dir build/debug --output-on-failure
```

On this machine `build/` is currently configured with the **Visual Studio 17 2022** multi-config generator, so pass the config explicitly:

```bash
cmake --build build --config Debug
ctest --test-dir build -C Debug --output-on-failure
```

Run a single test by CTest name with `-R` (names: `order_book_smoke`, `order_tests`, `result_type_tests`, `price_level_tests`, `execution_tests`, `matching_tests`, `cancellation_tests`, `submission_tests`, `event_tests`, `event_format_tests`, `allocation_failure_tests`), e.g. `ctest --test-dir build -C Debug -R price_level_tests --output-on-failure`, or build and run one target directly (`cmake --build build --config Debug --target price_level_tests`).

CMake options: `ORDER_BOOK_BUILD_BENCHMARKS`, `ORDER_BOOK_ENABLE_ASAN` (GCC/Clang/MSVC; on MSVC it strips `/RTC1` from Debug flags and copies `clang_rt.asan_dynamic-*.dll` next to each executable), `ORDER_BOOK_ENABLE_UBSAN` (GCC/Clang only; ignored with a warning on MSVC), `ORDER_BOOK_WARNINGS_AS_ERRORS`. Warnings are high (`/W4`, or `-Wall -Wextra -Wpedantic -Wconversion -Wshadow`), so watch for sign/narrowing conversions.

## Tests

- `execution_tests` drives single `executeOnce` steps; `matching_tests` drives the full `submitOrder` loop (both incoming sides, multi-order and multi-level sweeps, remainders, sequence numbering, a scripted replay for deterministic event ordering) and checks after each step that the book is consistent, uncrossed, and in sequence order within each level. `cancellation_tests` covers `cancelOrder` on both sides (only/oldest/middle/newest/partially filled orders, unknown and repeat IDs, aggregates, empty-level erasure, best-price transitions) and compares full captured before/after `BookState`s, including each surviving order's address, to show that unrelated state and FIFO positions are untouched.
- `submission_tests` covers submission acceptance and rejection: duplicate active IDs, reuse of cancelled and fully filled IDs, malformed orders (built by corrupting fields through `OrderBookTestAccess`, since the `Order` constructor refuses them), fully and partially filled incoming orders, multi-level sweeps, and `activeOrderCount` through a scripted sequence of events. Every rejection compares full captured before/after `BookState`s (levels, aggregates, order addresses, index, next sequence and trade IDs).
- `event_tests` checks the exact event vector each command returns: one `OrderRejected` for a refused submission; `OrderAccepted` (with the submitted, not post-fill, quantity) then one `TradeExecuted` per match in price-time order, with no resting event; one `OrderCancelled` with the remaining quantity or one `CancelRejected`. It also replays a scripted command sequence on two fresh books against a hand-worked stream. `event_format_tests` checks the printer's one-line text per event.
- No test framework: each `tests/*.cpp` is its own executable with a `main()` using local `expect(cond, msg)` / `expectThrows(fn, msg)` helpers that print `FAILED:` and `exit(EXIT_FAILURE)`.
- Each test file needs its own `add_executable` + `order_book_enable_warnings` + `order_book_enable_sanitizers` + `add_test` block in `CMakeLists.txt`. New library `.cpp` files must be added to the `order_book` target source list.
- `tests/allocation_failure_test.cpp` replaces global `operator new` to fail each allocation in turn and checks the book stays consistent (e.g. `addOrder` rolls back, `cancelOrder` fails before removing anything). MSVC Debug builds' checked iterators allocate inside `noexcept` container members, so there it exits 77 and CTest reports it **Skipped**; run `cmake --build build --config Release` and `ctest --test-dir build -C Release` to exercise it.
- `tests/order_book_test.cpp` uses `#define private public` around includes to seed `OrderBook::bids`/`asks` directly — keep that in mind when renaming private members. The hack only works for private **data members** on MSVC: access level is part of MSVC's mangled function names, so calling a private member function this way fails to link (LNK2019). To test private member functions, use the `OrderBookTestAccess` friend (declared in `OrderBook`, `PriceLevel`, and `Order`, and defined separately in each test file that needs it) and don't combine it with the `#define` hack in the same file.

## Architecture

All code lives in namespace `order_book`; headers in `include/order_book/`, implementations in `src/`.

- **Prices are integer ticks** (`unsigned int`), assuming a fixed $0.01 tick size. IDs, sequence numbers, and quantities are also `unsigned int` (aliases `Price`, `Quantity`, `OrderId`, `TradeId`, `SequenceNum` in `types.hpp`), and zero is invalid for all of them. Field checks live once, in the private `Order::malformedReason()` (a zero ID, price, or remaining quantity, an invalid `Side`, or an unsupported `OrderType`; only `LIMIT` exists, and it is the default argument). The constructor throws `std::invalid_argument` on a zero sequence number or on any reason `malformedReason` returns, with that reason's `rejectionMessage` (one distinct message per `RejectionReason`, in `rejection_reason.hpp`).
- **Sequence numbers are assigned by the book**, from `OrderBook::nextSequenceNum`, via the private friend-only `Order::assignSequenceNum`; the value passed to the `Order` constructor is replaced on acceptance. They record acceptance order, which is what time priority within a level follows, and an order keeps its number for life (a resting remainder keeps the one it was given before matching). `submitOrder` consumes a number once validation passes, even if the order then fills completely or matching throws; `addOrder` consumes one only once the order has rested; rejected orders consume none. On overflow the counter wraps back to 1 (skipping zero) and numbers are silently reused; time priority within a level is queue position, so it is unaffected, but don't assume numbers are unique or increasing across a wrap. Internally, resting goes through private `restOrder` (no validation, no numbering) so the remainder isn't renumbered — don't route it back through `addOrder`.
- **`Order`** — tracks initial/remaining quantity and `FillStatus` (`NONE`/`PARTIAL`/`FILLED`); `fillQuantity` returns the unfilled leftover of the requested amount.
- **`PriceLevel`** — FIFO `std::list<Order>` at one price/side plus a cached aggregate `quantity`. `addOrder` returns an `OrderLocation`; `consumeQuantity` fills oldest-first, pops fully filled orders, and returns a `ConsumptionResult` (status, per-order `OrderFill`s, unfilled remainder). Note the status naming: `SATISFIED` means the level is now empty, `LEVEL_EXHAUSTED` means quantity still rests there. Any mutation must keep `quantity` in sync with the list. The private `fillOldestOrder` (fills one order, popping it if fully filled) is reserved for its friend `OrderBook`. Don't call `consumeQuantity` on a level inside a book directly — go through `OrderBook::consumeLevel` (multi-order fill at one level, currently used only by tests), which loops `fillOldestOrder` itself, unindexing each fully filled order the moment it leaves the level, and erases the level once empty.
- **`OrderBook`** — `bids` is `std::map<Price, PriceLevel, std::greater>` and `asks` is `std::map<..., std::less>`, so `begin()` is always best price on both sides. `orderIndex` (`unordered_map<OrderId, OrderLocation>`) gives O(1) cancel: `OrderLocation` stores price, side, and a `std::list<Order>::iterator` into the level's list (valid because `std::list` iterators are stable). `addOrder` and `submitOrder` both run the read-only `validateNewOrder` first. It returns a `RejectionReason`, checked in this order: `Order::malformedReason()` (rechecked because an order can be changed after it is built), a `FILLED` order, then an ID already resting (`DUPLICATE_ORDER_ID`). `addOrder` throws `std::invalid_argument` with that reason's `rejectionMessage`; `submitOrder` returns a REJECTED result. Either way nothing is mutated and no sequence number or trade ID is consumed. IDs of filled or cancelled orders may be reused, since the index tracks only live orders. `activeOrderCount()` is the number of resting orders (index entries), not of levels. `findActiveOrder`, `getBestBid`, and `getBestAsk` return `Order` copies (never a reference or iterator), so callers can neither mutate a resting order behind the level's cached `quantity` nor hold a reference that dangles once it is filled or removed; tests that need element identity use `OrderBookTestAccess::indexedOrder`. `OrderBook` is move-only: a copy would share the original's list iterators. `cancelOrder(id)` looks the order up in the index, takes its *remaining* quantity off the level aggregate, erases it from the list, unindexes it, and erases the level once empty. Its result (with its event, which allocates) is built before anything is mutated; once the lookup and a level-exists guard pass, nothing can throw; other orders keep their positions and iterators, and it consumes no sequence number or trade ID. An ID that is not resting (unknown, already cancelled, fully filled, or an incoming order that never rested) returns `{false, ORDER_NOT_FOUND}` and leaves the book unchanged. Empty levels are erased on removal. `snapshot(depth)` returns top-N level summaries per side.
- **Matching** — `submitOrder` runs `matchOrder` (loops while the incoming order has quantity and crosses the best opposing price), then rests any remainder at its own limit price via `restOrder`. Each loop step is one private `executeOnce`: it executes min(incoming, resting) against the oldest order at the best opposing level, at the resting price, and returns exactly one `Trade`. It validates everything and builds the `Trade` before mutating, so a throw leaves the book unchanged — preserve that ordering. `matchOrder` makes room in its trade vector before each `executeOnce`, so recording a trade cannot throw after the book changed. `submitOrder` is not atomic: if an allocation fails mid-match, while building the result, or while resting the remainder, executions already made stand (the book stays consistent) and their trades and events are lost with the exception. The result, events included, is built *before* the remainder rests, so resting is the last step that can fail and a remainder never rests behind a throw; keep it that way. It unindexes the resting order only when fully filled (a partially filled one keeps its index entry and FIFO position) and erases the level once empty.
- **Result types** — `CancellationResult` (`bool success`, `std::optional<RejectionReason>`, `std::vector<BookEvent> events`, in `cancellation_results.hpp`) is what `cancelOrder` returns. `submitOrder` returns `SubmissionResults`, whose `submissionId` is the incoming order's ID. Its constructors are private, so it is built only with `SubmissionResults::accepted`, which takes the `OrderAccepted` the book captured before matching (its `orderId` is the submission ID) and holds the trades and the remaining quantity and sets `FillStatus` to NONE if nothing traded, FILLED if nothing is left, PARTIAL otherwise, or with `rejected`, which holds a reason, no trades, `FillStatus::NONE`, and the submitted quantity as remaining. A rejection echoes the submitted ID even when it is the reserved 0; an accepted result requires a positive ID. Each `Trade` (in `SubmissionResults::getGeneratedTrades()`) stores resting (maker) and incoming (taker) IDs plus the incoming side, from which `getBuyOrderId`/`getSellOrderId` derive.
- **Lifecycle events** (`book_event.hpp`) — `BookEvent` is a `std::variant` of `OrderAccepted`, `OrderRejected`, `TradeExecuted`, `OrderCancelled`, `CancelRejected`, each a plain struct with defaulted `==`. They are domain output held in the command's result (`SubmissionResults::getEvents()`, `CancellationResult::events`), not logging. `SubmissionResults` derives them in its factories, so its event rules hold by construction: `rejected` holds exactly one `OrderRejected`; `accepted` holds the `OrderAccepted` then one `TradeExecuted` (incoming/resting IDs, resting price, quantity) per trade in execution order; there is no resting event. `CancellationResult` is still a plain aggregate, so `cancelOrder` itself builds exactly one `OrderCancelled` (remaining quantity at cancel time) or one `CancelRejected` (reusing `RejectionReason`). `addOrder` emits nothing. Printing is separate: `formatEvent` (`event_format.hpp`) turns an event into one line of text, and only callers (the CLI) use it; the engine never prints.
- Errors are currently signaled via exceptions (`std::invalid_argument` / `std::runtime_error`); `getBestBid`/`getBestAsk` throw `std::runtime_error` on an empty side. The exceptions are `cancelOrder`, which reports a non-resting ID as a value (`{false, ORDER_NOT_FOUND}`) and throws only on internal inconsistency (an indexed order whose level is missing) or allocation failure (before anything is mutated), and `submitOrder`, which reports rejections as values and throws only on internal inconsistency or allocation failure.
